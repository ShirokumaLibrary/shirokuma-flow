# 検証 V1〜V5（dependency-flow・軽量レーン）

軽量レーンの `submit` 前に回す検証段。「CI 緑は必要条件であって十分条件ではない」という不変則の本体は `.shirokuma/rules/dependency-update.md` が正本で、ここは**その不変則を満たすための段と順序**を持つ。

**実走（V3 / V4）は `dependency-verify-worker` へ委任する**（独立で規模の大きい作業はサブエージェント）。同 worker は PR head を隔離ツリーへ取り出して実走する専用 worker で、**責務・安全設計・受容している範囲は worker 定義が正本**（ここには書き写さない）。入口が負うのは**入力を渡すこと**と**返ってきた判定の使い方**だけ。

## 委任ブリーフに渡す入力（必須は欠けたら委任しない・任意は worker の既定へ倒れる）

入力の閉じた集合と、欠けたときの worker 側の倒れ方は **worker 定義が正本**（ここでは件数を持たない）。入口が負うのは供給元の解決と写し方だけ。

| 入力 | 供給元 |
|---|---|
| 対象 PR 番号 | 発見段で確定した番号 |
| 結果ファイルの絶対パス | 入口が決めて渡す。`<base 側 cwd>/.shirokuma/tmp/dependency-verify-<PR#>.md`（標準命名は `.shirokuma/tmp/dependency-verify-<PR#>.md` だが、**base 側 cwd を前置した絶対パスへ展開してから渡す**——worker は相対パスを自分で解決せず、渡された絶対パスへ書く。**依存更新レーンには Issue 番号が無い**ので、他 worker の `<種別>-<番号>.md` 形に揃えつつ番号を PR 番号にする） |
| base 側 cwd | 入口が動いている人の作業ツリーの**絶対パス** |
| 出自の照合値（期待する author と head ブランチ接頭辞） | `shirokuma-flow config get dependency.botAuthors` ／ `shirokuma-flow config get dependency.botBranchPrefixes` |
| マニフェスト／ロックファイルの判定リスト（各エントリに分類ラベル ＋ **分類ごとの想定件数**） | `shirokuma-flow config get dependency.manifestFiles` の各要素に `マニフェスト`、`shirokuma-flow config get dependency.lockFiles` の各要素に `ロックファイル` を付ける。想定件数は**それぞれの配列の要素数をそのまま**添える |
| 隔離ツリーの絶対パス（head 側・base 側の 2 つ） | `shirokuma-flow config get dependency.isolatedTreeRoot` が返す置き場所の配下に、入口が head 側・base 側の 2 パスを組み立てる。**ツリー名の正本は `shirokuma-flow gate vocab` が返す隔離ツリー名の宣言**（`isolatedTreeName`）で、**ここには逐語を持たない**——同じ命名は値域検査の側も判別に使うので、写しを置くと命名が動いた回に片方だけが古い形で残る。宣言が課す `<PR#>` の形（10 進数字のみ）は必ず守る——発見段が PR API から得た番号をそのまま使い、加工も補間もしない。数字以外を許すと組み立てたパスが宣言された置き場所の外を指し、`worktree add` / `worktree remove --force` の対象がそこへ向く。**渡す前に置き場所を `mkdir -p` ＋ `chmod 700` で用意し、所有者専用であることを確認する**。**未宣言なら渡さない**（worker は渡されなければ `mktemp -d` の出力配下に倒す） |
| 展開する submodule パスの一覧（リポジトリ相対） | `shirokuma-flow config get dependency.isolatedTreeSubmodules` が返す JSON 配列の各要素を、**そのまま**（加工も絶対パス化もせず）渡す。**未宣言なら渡さない**（worker は渡されなければ展開しない＝submodule 依存の検査はその回 skip される）。**`invalid-value` は人へ渡す**（未宣言と混ぜない）——空配列・配列でない値もここへ落ちる。**値域の正本はコードのレジストリ**で、条件は `shirokuma-flow gate vocab` の `isolatedTreeSubmodulesAllowlist` から引く（ここに逐語を持たない）。**入口は展開そのものを行わない**（`git submodule update` を含め、人の作業ツリーに対する submodule 操作をしない）——展開は worker の責務 4-4 / 責務 6 が隔離ツリーに対して行う |
| V4 発火要否（「否」と断定できるときだけ） | 下記「V4 出力比較」の断定条件に当てる。**断定できなければ渡さない**（worker は渡されなければ「要」に倒す） |

- **`config get` は配列を JSON 配列の文字列で返す**（`["…","…"]`）。ブリーフへ写すときは要素へ分解し、どちらのキーから来たかで分類ラベルを付ける。**ラベルの無いエントリ・2 分類以外のラベルを混ぜない**（worker はそれを実行構成の混入として実走しない側に倒す）。
- **想定件数は分類ごとに 1 つずつ渡す**（マニフェスト＝`manifestFiles` の要素数・ロックファイル＝`lockFiles` の要素数）。渡さないと worker は**各分類 1 件を上限**として扱うので、マニフェストやロックファイルを 2 件以上宣言したプロジェクトでは件数超過で毎回実走しなくなる。**宣言されたリストの件数がそのまま想定件数**であり、入口がそれ以上に見積もって渡さない（想定件数を水増しすると worker の allowlist 健全性検査がそのぶん緩む）。
- **この渡し方の限界を申告しておく**。想定件数を宣言リストの要素数から機械導出する以上、worker の件数超過検査は**判定リストを広げる方向には原理的に発火しない**（リストを広げれば想定件数も一緒に広がるため）。この検査が捉えるのは「観測したエントリが宣言されたリストより多い」場合だけで、**宣言されたリスト自体が妥当か（実行構成にあたるファイルを含んでいないか）は検査していない**。そこは宣言を足す変更をレビューで見る側の責務になる。
- **出自の照合値（2 キー）と判定リスト（2 キー）は、未宣言なら委任しない**。`config get` は未宣言のキーで非 0 と `設定キー '…' が見つかりません` を返す。この 4 キーのいずれかが引けなければ、その PR を軽量レーンに乗せず「判定リスト／照合値が宣言されていない」ことを報告して人に渡す（**値を推測して埋めない**——判定リストを広く推測すると worker の実走 allowlist がそのぶん広がる）。
- 判定リストは**レーン判定と同じ config キー**を使う（`reference/lane-decision.md`）。入口の判定と worker の allowlist を別の値で持たない。
- **未宣言でも委任するキーは 2 つ**（`dependency.isolatedTreeRoot` と `dependency.isolatedTreeSubmodules`）。どちらも倒れる向きが出自の照合値・判定リストの 4 キーと逆で、未宣言は「レーンが機能しない」ではなく **degraded** だからである——**前者は `mktemp -d` の出力配下へ、後者は「submodule を展開しない」へ倒れる**（どちらも fail-closed ではない）。以下の条件は前者（置き場所）についてのもので、後者の条件と受け渡しは本節の最後の箇条書きが持つ。宣言が要るのは**リポジトリルートが TMPDIR 配下にあると壊れる検査を持つプロジェクト**で、そこでは未宣言のまま実走すると依存更新と無関係な理由で V3 が fail する。
  - **degraded を選んだ代償は、既定へ倒れたことが何のエラーも出さないこと**（fail-open）。これを可視化に置き換えるため、**どちらを使ったかを worker が結果ファイルの隔離ツリー欄に出所として記録し、入口はそれを V5 へ転記する**（本ファイル「V5 記録と限界の申告」節）。fail-closed（未宣言なら実走しない）を採らないのは、この衝突が**一部のプロジェクトに限られ**、キーを必要としない配布先の検証まで一律に止めることになるため。
  - **値の条件は 5 つ**（⑤は次の箇条書き）——①**絶対パス**である（worker は相対パスを自分で解決せず、相対値は `git -C` の起点＝人の作業ツリーの内側へ着地する） ②**TMPDIR 配下でない**（配下だと、上の「リポジトリルートが TMPDIR 配下にあると壊れる検査」との衝突がそのまま起きる） ③**人の作業ツリーと入れ子にならない**（内側は不可。内包も原則不可だが、**置き場所が保持するために在る隔離ツリーそれ自身は例外**——そうでないと隔離ツリーの中で走る検査が自分の置き場所を「汎用の親」と誤判定する。**例外の正確な条件はレジストリが正本**で、ここには逐語を持たない） ④**シェルのコマンド行へ補間しても語として閉じる文字だけ**（英数字と `/` `.` `_` `-` のみ。空白・制御文字・改行・`$` / バッククォート / 引用符 / バックスラッシュを含まず、`-` で始まらず、`.` / `..` / 重複スラッシュ / 末尾スラッシュを含まない正規形）。**④が要るのは、worker が組み立て後のパスを `git worktree add` / `chmod` / `(cd "<パス>" && <コマンド>)` / `worktree remove --force` のコマンド行へ二重引用符で補間するから**である——二重引用符は語分割とグロブを止めるが `$(…)` / バッククォートは止めない。**③の後半（内包しない）が要る理由は入れ子ではない**——置き場所が作業ツリーの親であるとき、組み立てた 2 パスは作業ツリーの兄弟であって入れ子にならない。要るのは、置き場所が**隔離のための専用ディレクトリ**であること（下の第 5 条件が所有者専用のモードを課す作用先）を保つためで、人の作業ツリーを内包する汎用の親ディレクトリはその対象にできない。
  - **⑤置き場所は所有者専用**（実行ユーザーの所有・group / other から書き込めない）。入口は渡す前に `mkdir -p` ＋ `chmod 700` で用意し、モードを確認する。**worker 側も同じ確認を `worktree add` の前に行う**（責務 4-3・満たせなければ実走しない）。**二重にするのは、ツリーの名前が宣言された命名で予測可能だから**で、置き場所が他ユーザーから書き込めると、不在確認とツリー作成の間にこれから実行されるファイルを差し替える窓が開く。
  - **条件を満たさない値の倒れ先は 1 つに揃える**——①〜⑤のいずれを満たさない値も**宣言の誤りとして人へ渡し、既定へは倒さない**。**既定へ倒さないのは、既定＝`mktemp -d` も TMPDIR 配下なので、②違反を既定へ倒すと同じ違反が戻って是正にならず、他の条件だけを既定へ倒すと「①③④⑤は既定で問題ない」と読まれるから**である（キーを宣言しているのはリポジトリルートが TMPDIR 配下だと壊れる検査を持つプロジェクトなので、既定へ倒れた回は依存更新と無関係な理由で V3 が fail する）。**未宣言（キーが無い）とは別の事象**なので混ぜない——未宣言は degraded（`mktemp -d`）へ倒す。
  - **`config get` は値域外の値を非 0 で返す**（`dependency.isolatedTreeRoot` は値検査を持つ数少ないキーの 1 つ）。**未宣言と値域違反はエラーの `reason` で区別できる**——`declared-but-unset` は degraded へ、`invalid-value` は人へ渡す。**値域の正本はコードのレジストリ**で、条件と実測の根拠は `shirokuma-flow gate vocab` の `isolatedTreeRootAllowlist` から引く（ここに逐語を持たない）。
  - **判定 JSON の `build` ブロック（`sourceMatch` / `dirty` / `degraded`・欠落した回の読み方を含む）の読み方は `shirokuma-flow gate limits --sub limits` の `H19` が正本**（ここに写さない）。**`stale` を名乗った回・`build` ブロックそのものが無い回は、その判定を現ソースの値として読まない。** **`stale` と `build.dirty: true` が同時に立つ回は、その判定を根拠に使わない。** **`build.dirty: null`（焼いていない）は、再現性の担保が無い側として `build.dirty: true` と同じに読む。**
- **隔離ツリーへ展開する submodule（`dependency.isolatedTreeSubmodules`）も、未宣言のまま委任する**。`git worktree add` は submodule を展開しないので、宣言が無い回は隔離ツリーの submodule が空のまま残り、**それに依存する検査は skip される**（skip は終了コードに出ないので実走は緑に見える＝**fail-open かつ fail-silent**）。**入口が負うのは値を渡すことだけ**で、展開は worker が人の側の submodule から同じ gitlink SHA を `git worktree add --detach` で行う（**ネットワーク取得はしない**）。展開できた／できなかったは worker の結果ファイルの `submodule 展開（隔離ツリー）` 欄が申告し、入口はそれを V5 へ転記する。
  - **値の条件は上の 5 条件とは別**（同じではない）——非空の配列であること・各要素が空でない単一行の**リポジトリ相対パス**（`/` 始まり禁止・`-` 始まり禁止・許可文字集合・正規形）・**重複を含まないこと**（宣言は集合として扱う）。**置き場所が絶対パスを要求するのと逆向き**なのは、展開先が `<隔離ツリー絶対パス>/<要素>` として組み立てられるからである（`/` 始まりの要素は隔離ツリーの外を指す）。**逐語は本ファイルに持たない**——正本はレジストリで、`shirokuma-flow gate vocab` の `isolatedTreeSubmodulesAllowlist` から引く。
  - **空配列を degraded へ倒さない**（`config get` が `invalid-value` で非 0 を返す）。宣言が在るのに 0 件という形は、宣言し忘れ（展開しない）と区別が付かないまま「展開 0 件」を空虚に成立させる。
  - **宣言するのは検査が必要とする submodule に限る**——別 org の submodule を宣言すると、その `package.json` が prepare の実行面に入りうる（実走 allowlist を広げるのと同じ向きの危険で、レビューは**足す変更**を厳しく見る）。

## 返ってきた判定の使い方

- worker は `依存更新検証:`（V3 / V4 の結果）と `軽量レーン可否:`（`可` / `不可` ＋根拠）の 2 行を返し、レポート全文を結果ファイルへ書く。
- **`軽量レーン可否` が `可` のときだけ軽量レーンを続行する**。`可` 以外・2 行が揃わない・結果ファイルが実在しない・結果ファイルの検証母集団の欄の機械検証が欠落を出したときは、いずれも**課題化レーンへ回す**（fail-closed）。欄検査の手順と射程は SKILL.md の軽量レーン手順 2 が正本（ここには写さない）。
- **実施（pass）以外を「問題が無かった」と読み替えない**。実走しなかった理由（`未実施（…）`）は「検証が通った」ではなく「検証していない」である。理由トークンの閉じた列挙は worker 定義が正本なので、**ここでも報告でも列挙を複製せず、返ってきた文字列をそのまま転記する**。
- V5 の PR コメントは入口が書く。結果ファイルの V1〜V4 と、worker が申告した限界（エントリの射程外・確認していないこと）を**転記する**（要約し直して射程を落とさない）。

## 段の一覧

| 段 | 何をするか | 必須度 |
|---|---|---|
| **V1 宣言差分** | マニフェストの差分を取り、**何がどの規模（major / minor / patch）で更新されるか**を確定する | 必須 |
| **V2 実効差分** | ロックファイルの差分を取り、**宣言に現れない推移的更新の有無と件数**を確定する | 必須 |
| **V3 CI 等価検査の実走** | 更新後のツリーで、そのプロジェクトが CI で回す検査と等価な集合を手元で実走する | 必須 |
| **V4 出力比較** | 更新前後で出力を比較し、差が無いことを確認する | 条件付き必須（発火条件は下記） |
| **V5 記録と限界の申告** | V1〜V4 で**何を実走し、何を確認していないか**を PR コメントに残す | 必須 |

## V1 宣言差分

- マニフェストのファイル名はエコシステム依存。差分から更新規模を読む（PR 本文の表ではなく差分を読む）。
- 規模が読み切れない記法に当たったら、そこで検証を止めてレーン判定へ戻す（fail-closed 既定＝課題化）。
- **差分が切り詰められていないかを毎回確認する**。`pr diff` はファイル一覧を切り詰めても patch 本文を落としても正常に返る（申告は `files_truncated` と各ファイルの `patch_omitted`）。真なら読み切れなかったものとして扱い、レーン判定へ戻す（fail-closed 既定＝課題化）。

## V2 実効差分

- ロックファイルの差分から、**宣言に無い依存が入れ替わっていないか**を件数つきで確定する。宣言 1 件の更新が推移的に複数件を動かすのは通常のことなので、「宣言が minor だから影響は minor」と読み替えない。
- **ロックファイルの patch が返っていることを確認してから件数を数える**。`patch_omitted` が真のまま数えると 0 件に見えるが、それは「推移的更新が無い」ではなく「読めていない」である（fail-closed＝課題化へ戻す）。
- **ロックファイルを持たないエコシステムでは V2 を未検証にする**。そのときは「実効差分を確認する手段が無い」と V5 に明示して申告する（黙って省略しない）。

## V3 CI 等価検査の実走

**この段は入口が実行しない**。実行エントリの解決も隔離ツリーの用意も実走も worker の責務で、入口は委任ブリーフの入力（本文「委任ブリーフに渡す入力」）を渡して結果を受け取るだけ（手順の正本は worker 定義）。入口側の規律は次の 2 つ。

- **未検証のまま先へ進めない**。worker が実走しなかった（エントリが宣言されていない・前提が整わない等）場合、検査を skip して `submit` する劣化動作は**採らない**——未検証のまま Review に置くと「Review にあるものは検証済み」という読みが嘘になる。課題化レーンへ回すか、人に渡す。
- **レーン判定を飛ばしてこの段に入らない**。実走は更新後のツリー＝PR 側の設定を読んで走るので、マニフェスト／ロック以外を同梱した PR がここまで来ると PR 側が用意した実行構成の上で走る。その経路はレーン判定で閉じてある。
- 実行エントリが印字した**射程外**と、worker が結果ファイルに申告した**限界**（実走が開くベクタを含む）は、**そのまま V5 へ転記する**。実走した事実だけを報告して射程を落とさない。

## V4 出力比較

- **発火条件**: 更新対象が **linter / formatter / compiler / bundler / codegen**——すなわち**出力を生む道具**を含むとき。
- **発火要否を判定するのが入口の仕事**で、比較の実走は worker が行う。差があれば worker の報告内容を V5 に書き、判断を人に渡す。
- **この種別リストは網羅ではない**。対象が出力を生む道具かどうか迷ったら **V4 を回す側に倒す**（回して差が無いことの確認コストは、出力が変わったことを見落とすコストより小さい）。

### 「否」と断定できる条件（渡し方の向き）

worker は発火要否が**渡されなければ「要」に倒す**安全既定を持つ。入口が「否」を渡すとこの既定が上書きされ、**V4 が skip されたまま `軽量レーン可否: 可` が成立しうる**（fail-open）。だから「否」は**断定できるときだけ**渡す。

- **「否」と断定できる**のは、次を**すべて**満たすときに限る。**射程は宣言された更新対象だけでなく、推移的に入れ替わるものまで**——宣言 1 件の更新が推移的に bundler / codegen を入れ替えることがあり、宣言側だけを見て「否」と断定すると出力を生む道具の入れ替わりが V4 を素通りする。
  1. 宣言差分（V1）と実効差分（V2）の**双方を読み切れている**（`files_truncated` が偽で、マニフェスト・ロックファイルの**いずれについても** `patch_omitted` が偽）。**ロックファイルを持たないエコシステムでは V2 を読む手段が無いので、この条件を満たさない**（＝断定できない）。
  2. 入れ替わるものを**1 件残らず列挙できている**（宣言された更新対象と、ロックファイルに現れる推移的な入れ替わりの**両方**を含む集合が確定している）。
  3. 列挙した**すべて**について、出力を生む道具でないと言える（1 件でも判断がつかないものがあれば断定できない）。
- **3 条件のうち 1 つでも満たさなければ「否」を渡さない**。「要」と書いて渡してもよいが、**何も渡さない**のが既定の使い方で、迷いを worker の安全既定へ委ねる形になる。
- **「否」と渡した場合は、その根拠（列挙した宣言・推移的の両方の入れ替わりと、道具でないと判断した理由）を V5 に残す**。V4 が回らなかったことを「差が無かった」と後から読めなくするため。

## V5 記録と限界の申告

PR コメントに次を残す（`shirokuma-flow issue comment <PR#> -`・stdin）。

- V1: 更新対象と規模（件数つき）。
- V2: 推移的更新の件数。手段が無いなら「未検証」とその理由。
- V3: worker が返した結果（実施 / 未実施とその理由）と、エントリが申告した**射程外**。
- V4: 発火したか（しないなら発火条件に当たらなかった理由）・比較結果。
- **`実体版照合` 欄をそのまま転記する**（結果ファイルの「検証母集団」欄。責務 5-1 / 6-1 の照合結果）。**`成立` の回も省略しない**——「更新が実際に届いたツリーで検査したのか」は V3 の緑の意味を決める情報で、要約すると落ちる。`不成立` / `不能` / `未実施` の回は括弧内の理由トークンごと転記する。
- **隔離ツリーの出所（`ブリーフ指定` / `mktemp fallback`）を 1 行残す**（結果ファイルの隔離ツリー欄）。**欄をそのまま転記しない**——用意した回の欄値は `<絶対パス>（出所: <ブリーフ指定|mktemp fallback>）` の形なので、**括弧内の `出所: ` に続く値だけ**を取り出して載せ、**絶対パスは載せない**（PR コメントは外向き成果物で、環境固有値を出さない）。用意しなかった回・残置した回の欄値（`未作成（<理由>）` / `残置: <絶対パス>（<理由>）`）は出所を持たないので、**その事実（未作成 / 残置）と理由だけを載せ、残置のパスは載せない**。置き場所の宣言が外れて既定へ倒れた回は何のエラーも出ないので、この 1 行が唯一の痕跡になる。
- **`submodule 展開（隔離ツリー）` 欄を定型行で残す**（結果ファイルの「検証母集団」欄）。**次の 1 行を、`<>` の中だけを埋めてそのまま投稿する**——`。` から後ろも投稿本文であって worker 向けの説明ではない（skip の射程を読み手へ届けるのがこの行の役目なので、後半を落とすと目的が達成されない）。

  ```
  - **submodule 依存の検査:** <submodule 展開（隔離ツリー） 欄の値をそのまま>。未展開の submodule に依存する検査は隔離ツリーでは skip され、この実走の緑はそれらを含まない（倒れる向き: fail-open・skip は終了コードに出ない）。
  ```

  - **この行は定型で、欄値が「展開済み」だけの回も省略しない**——省略すると「submodule 依存の検査まで含む緑なのか」が V5 から消える。skip は終了コードに出ないので、**実走が緑だったという事実からは読めない**（読み手が射程を広く取る向きに倒れる）。
  - 埋めるのは `<>` の中だけで、要約し直さない。**未展開・該当なしを「問題なし」と言い換えない**——2 つの「該当なし」は読み分けが要る値（`宣言 0 件` は展開対象の宣言が無い・`gitlink 0 件` はリポジトリが submodule を持たない）で、言い換えるとその区別が落ちる。**worker が gitlink を計数できなかった回も `宣言 0 件` に倒れる**（宣言が無い事実だけは確実なので、submodule を持たないリポの側へは寄せない）——したがって `宣言 0 件` からは「gitlink が在った」とも「無かった」とも読まない。計数できなかったことは終了コードにも欄値にも出ない（fail-silent）。
  - **欄値がパス一覧を含む回（`展開済み: <パス一覧>` / `未展開: <パス一覧（理由）>`）は、リポジトリ相対のパスだけを載せる**——隔離ツリーの絶対パスは載せない（**この節の隔離ツリー欄と同じ carve-out**。PR コメントは外向き成果物で、環境固有値を出さない）。相対形にできない値は載せず、その旨を書く。
- **`V4 除外箇所` 欄をそのまま転記する**（同欄。比較から除いた箇所の件数と種別数）。**除外は V4 を pass させる方向にしか働かない**ので、除外の存在を落とすと「差分なし」だけが残って比較の実効が読めなくなる。件数が 0 件でない回は、結果ファイル本文の 3 点記録（種別・箇所の形・根拠）も要旨を落とさずに載せる。
  - **worker が施した無害化を解かない**: 除外箇所の実際の行と観測した実体版は**第三者コードが印字した untrusted な文字列**で、worker 側で無害化（外部データである旨のラベル・コードフェンスでの囲い込み・長さ上限・制御文字の可視化）を経ている。**転記はその形のまま行い**、読みやすさのためにラベルを外す・フェンスを解く・地の文へ混ぜることをしない（PR コメントは他の AI の入力になるため）。無害化を保ったまま載せられないなら**載せずにその旨を書く**。
- **据え置き中の依存が対象に含まれる回は、その「再挑戦条件」が今どこまで満たされたかを 1 行残す**（本ファイル「再挑戦条件」節の台帳＝open のまま残っている追従 Issue が待っている依存。宣言差分・実効差分のどちらに現れた場合も対象）。**依存更新の回に後乗りさせるだけ**で、常設の監視機構・別台帳は作らない（回が来なければ記録も要らない）。
- **確認していないこと**を明示する。peer 依存の警告を放置と判断したなら、その判断自体もここに残す（放置なのか気づいていないのかを次の人が区別できるように）。**worker が結果ファイルに申告した限界**（実走が開くベクタ・観測できていない範囲）もここへ転記する。
- **転記するのは結果の要約であり、秘匿情報は載せない**。PR コメントは外向き成果物なので、トークン・認証情報・環境変数の値・ホスト名や絶対パスなどの環境固有値をローカル実走の出力からそのまま貼らない（`.shirokuma/rules/trust-boundary.md` の外向き扱いと同方向）。

## 再挑戦条件（据え置きの台帳）

据え置き（更新先に依存する側のツールチェーンが未対応など、いま取り込めないと判断した場合）は、**追従 Issue 本文の固定節「再挑戦条件」**に残す。

- 書くこと: 何を待っているか（どの依存が、どの条件を満たしたら再開できるか）・据え置いた時点で分かっている影響。
- **追従 Issue は据え置き中 open のまま**にする。close すると台帳が消え、次に同じ PR が作り直されたときに同じ判定をやり直すことになる。
- 台帳用のファイルを新設しない。Issue はどのプロジェクトにもあるが、台帳ファイルの置き場はプロジェクトごとに違う。
