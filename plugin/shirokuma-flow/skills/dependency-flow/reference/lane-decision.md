# レーン判定（dependency-flow）

依存更新 PR を軽量レーン／課題化レーンのどちらに落とすかを決める。判定の Why（なぜ CI 緑が十分条件でないか・なぜ major を軽量に乗せないか）は `.shirokuma/rules/dependency-update.md` が正本で、ここは**判定の手続き**だけを持つ。

## 依存更新 PR の識別（config が正本）

`pr list --state open` の返り値に含まれる `head`（ブランチ名）と `author`（login）で分類する。照合値は **config が正本**で、この文書は候補を持たない。

| 信号 | 引き方 |
|---|---|
| head ブランチの接頭辞 | `shirokuma-flow config get dependency.botBranchPrefixes` |
| author の login | `shirokuma-flow config get dependency.botAuthors` |

- **値をここに列挙しない**。ツール名・接頭辞・login はプロジェクト固有値で、同じ値を検証委任のブリーフ（`reference/verification.md` の出自の照合値）にも渡すため、2 箇所に持つと入口の判定と worker の照合が別の値で動きうる。**正本は config の 1 箇所**。
- **配列は JSON 配列の文字列で返る**（`["…"]`）。**同じキーの中の要素どうしは OR**（`botBranchPrefixes` の要素のいずれかに前方一致すれば「接頭辞は一致」）。
- **2 つの信号の結合は AND**。依存更新 PR と見なすのは **head 接頭辞の一致と author の一致が両方**成り立つときだけで、片方だけでは見なさない（接頭辞だけだと人が手で切った同名ブランチを拾い、author だけだと同じ bot の別用途 PR を拾う）。
- **`author` が `null` や空文字で返ることがある**（一覧の返り値は `null` を取りうる）。その場合は author の一致を**断定できない**ので、AND は成立せず**依存更新 PR と見なさない**（`null` を「一致とみなす」とも「照合を省く」ともしない＝fail-closed）。**断定できないものは常に見なさない側へ倒す**——見なさない側の帰結は「何もしない」（PR は open のまま残る）で、次項のとおり危険な側は開かない。
- **author は API が返す login をそのまま照合する**（UI の表示名と綴りが違うことがある。実測値を config に書く）。
- **キーが未宣言なら分類しない**（`config get` が非 0 で返る）。「候補が無いから全部依存更新ではない」とも「たぶんこれだろう」とも決めず、**宣言が無いことを報告して人に渡す**。
- 照合値に当たらない PR は **依存更新 PR ではない扱い**にして何もしない（open のまま残す）。**取りこぼし側に倒れる**設計で、危険な側（未検証のまま Review に上がる・merge される）は開かない——入口は `merge` をしないため、見落としが merge に化ける経路が無い。
- **ただし取りこぼしは沈黙する**。だから発見のたびに `total` / `count` / `truncated` を報告に載せる（これが唯一の観測手段）。
- 逆に**誤検出**（他人の PR を依存更新と誤認）は `submit` で Status を動かす副作用を持つ。だから引数なしモードは発見結果を提示してから 1 件ずつ処理に入る。

## 決定表

上から順に当てはめ、最初に当たった行のレーンを採る。

| 観測 | レーン |
|---|---|
| `pr diff` の `changed_files` が 0（母集団が空） | **課題化** |
| `ci <PR#>` の `allowed` が false **かつ** `not_run` が false（**「CI が 1 件残らず未実行」と断定できる回以外のすべて**。内訳は尽くさない——落ちた・実行中・一部だけ走った・実行の有無を読めない結論が混じった、のいずれもここに入る） | **課題化** |
| 差分に**判定リスト（下記）に載っていないファイルが含まれる**、または `status` が `modified` **以外**のファイルが含まれる（下記「`status` はリテラルで照合する」） | **課題化**（fail-closed 既定） |
| マニフェスト差分の中に major が 1 件でもある | **課題化** |
| マニフェスト差分が**読み切れない**（semver 範囲記法・エコシステム表記が判定不能。`pr diff` の `files_truncated` / `patch_omitted` が真の場合を含む） | **課題化**（fail-closed 既定） |
| 上記のいずれにも当たらない（全件 patch / minor ∧ **CI が緑か走っていないか** ∧ 差分がマニフェスト／ロックのみ） | **軽量** |

- **母集団が空の行を最初に当てる**。`changed_files` が 0 だと、以降の「判定リストに載っていないファイルが含まれる」「major が 1 件でもある」はどれも空虚に成立せず（当たるファイルが 1 つも無い）、最終行の「いずれにも当たらない」へ落ちて軽量に見える。空の差分は「無害な依存更新」ではなく**観測が成立していない**ので課題化へ倒す。
- **判定は OR**。「CI 緑だから軽量」は成り立たない（規模と CI の両方が条件）。
- **CI 結果は `ci <PR#>` の判定をそのまま使う**。個々の check-run を自前で解釈して緑と読み替えない（merge 可否と同じ判定を二重管理しないため）。**`not_run` も verb の出力をそのまま使う**——「ステップが 0 か」を自前で数えない。**`allowed` だけを見ない**——CI が 1 件も無い PR は `allowed: true` ∧ `no_ci: true` で返る（merge 側では no-op 許可の意味）。**check-run はあるが全件 `SKIPPED`（人が Actions を止めた等）の PR も `allowed: true` ∧ verdict `skipped` で返る**——どちらも `allowed` だけを読むと**何も検証していない PR** が軽量レーンに乗る。
- **「CI が走っていない」には 3 つの形がある**——①`no_ci`（check-run が 1 件も無い）②`not_run`（check-run はあるが**1 件残らず「1 ステップも実行せずに failure」**）③`skipped`（check-run はあるが**全件が conclusion `SKIPPED`**・人が Actions を止めた等）。**②は「全部が未実行」のときだけ立つ**——実行中や一部成功が混じる回は立たないので、それらは前行で課題化へ落ちる。**立たない理由は「その 1 件が確かに走った」ではなく「走っていないと断定できない」**である（check-run の結論からは実行の有無を読めない値がある——skip された回は成功側に、待機中の回は実行中側に写る。**この記述は check-run ごとの結論の写像〔outcome 層〕を指す**——**全件 skip の回は `ci gate` の verdict〔verdict 層〕としては `skipped` が返るので、「成功側に写る」は verdict 層では成り立たない**。本決定表が使うのは verdict 層〔`ci <PR#>` の判定〕であり、③`skipped` はそちらで明示的に区別できる）。**断定できない側は課題化へ倒す。**②は実行基盤がジョブをスケジュールできなかった回に起きる（実行枠の使い切りなど）。**`conclusion` だけを読むと②を「失敗」と読み違える**ので、`allowed` が false の回は `not_run` も見る。
- **いずれも「緑」ではなく「CI が走っていない」＝未検証**である。**未検証はここでは課題化しない**——検証は軽量レーンの中で実走する（V3 / V4）。**決定表の時点で証跡を求めてはならない**: 証跡は軽量レーンに入ってから作られるので、決定表で「証跡があるか」を条件にすると**必ず不成立になり、軽量レーンが構造的に到達不能になる**。
  - **未検証の PR を軽量レーンから落とすのは、決定表ではなく軽量レーンの手順 3**（`軽量レーン可否` が `可` 以外はすべて課題化へ回す）と**手順 4**（証跡のコメントに失敗したら課題化へ回す）である。**ゲートの所在は手順 3・4 である**。
  - **なぜ `no_ci` / `not_run` / `skipped` 単独で課題化しないのか**: どの base で CI が走るかは**プロジェクトごとの設定**であって、本規範が前提にしてよい事実ではない。CI を意図的に一部 base へ絞った構成では `no_ci` が常態になり、**軽量レーンが構造的に到達不能**になる。`skipped` は人が Actions を止めた回に同じ理由で常態になりうる。**逆に全 PR で CI が走り Actions も止めていない導入先では、この扱いは何も変えない**——`no_ci` も `not_run` も `skipped` も真にならないので、`allowed` の行だけで判定される。
  - **倒れる向き**: **未検証の PR が軽量レーンへ入る**ので、この扱いは **fail-open 側**である（`skipped` も同じ）。歯止めは 3 つ——①**軽量レーンの終端は実走の判定**（`軽量レーン可否` が `可` のときだけ続ける・手順 3）②**証跡は実走の出力であって申告ではない**（worker が結果ファイルへ書いた V3 / V4 の判定を読む。「走らせたつもり」は証跡にならない）③**証跡を PR 本文へ残す**ことを軽量レーンの成立条件にする（後から誰でも照合できる形にする・手順 4）。**この 3 つのいずれかを満たせない回は課題化へ倒す。**
  - **証跡が「緑」であることまで確かめる**。V3 が赤い回・実走できなかった回（`未実施` / `不能`）は、証跡が在っても軽量レーンを完了させない。**「実走した」と「実走して緑だった」を書き分けない読み方をしない。**
  - **一部 workflow だけを止めた粒度 OFF の PR は verdict が `skipped` にならず `success` のまま残る**（③は全件 SKIPPED のときだけ立つ）。この回は `pr checks` の `skipped_checks` 欄が非空になる——**`success` ＋ 非空の `skipped_checks` も緑ではなく、skip された workflow の範囲は未検証**である。決定表は verdict の 3 形（①②③）だけでなく `skipped_checks` の非空も同じ歯止め（手順 3・手順 4）へ回す。
- **判定リストは config が正本**。`shirokuma-flow config get dependency.manifestFiles`（マニフェスト）と `shirokuma-flow config get dependency.lockFiles`（ロックファイル）で引き、**allowlist として当てる**（載っている形だけ許可・未知のファイルは不許可側へ落ちる）。エントリがファイル名だけならファイル名で、パスを含むならパスで照合する。ファイル名はエコシステム固有値なのでこの文書には書かない。**引けなければ（未宣言）レーンを確定せず人に渡す**——リストを推測で広げると、そのぶん検証実走の allowlist が広がる。同じ 2 キーを検証委任のブリーフにも渡す（`reference/verification.md`）。
- **`status` はリテラルで照合する**。`pr diff` の各ファイルが返す `status` は API 由来のリテラル値で、`modified` のほかに `added` / `removed` / `renamed` / `copied` / `changed` / `unchanged` が返る。軽量レーンに乗せてよいのは **`modified` だけ**で、**それ以外はすべて課題化**する（`changed` / `unchanged` を「変更なので可」「変更なしなので無害」と日本語で読み替えない。`renamed` / `copied` は旧パスが判定リストの外でも新パスだけが見えることがある）。**列挙に無い未知の値も課題化**する（fail-closed）。同じ判定は worker 側でも `modified` リテラルで当てられるので、入口が別の読みを持たない。
- **差分の範囲も実測する**。判定リストの外（設定ファイル・スクリプト・ソース）が含まれる依存更新 PR は、依存更新として扱わず課題化する。検証段はプロジェクト設定（検証コマンドの宣言）を読んで手元で実走するため、**設定ファイルの書き換えを同梱した PR を軽量レーンに乗せると、PR ブランチ側で指定された文字列を実行する経路が開く**。この行はその経路を入口で閉じる。
- **差分は 2 段で取る**。1 段目は `pr diff <PR#> --name-only`——ここで返る `changed_files` / `files_truncated` と各ファイルの `path` / `status` / `patch_omitted` だけで、母集団・allowlist・`status` の行は判定できる。**規模（major / minor / patch）と推移的更新は patch を読まないと判定できない**ので、1 段目を通った PR に限り 2 段目として patch 込みの `pr diff <PR#>` を取り直す。課題化に落ちる PR でロックファイルの patch 全文を読み込まずに済ませるための取り方であって、**判定に要る情報を落とすためのものではない**（1 段目だけでレーンを軽量に確定しない）。
- **2 段目の一覧で allowlist と `status` を当て直す**。2 回の取得の間に PR が更新されると母集団が変わりうるので、2 段目が返す一覧にも同じ判定を当て、1 段目と食い違えば課題化する（新しい観測を古い観測で上書きしない）。
- **読み切れなかったことを読めたことと区別する**。`pr diff` は結果を切り詰めても正常に返る——ファイル一覧の切り詰めは `files_truncated`、個々のファイルの patch 本文が返らない場合は `patch_omitted` で申告される。ロックファイルはサイズが大きく patch が省かれやすい対象なので、これを見ないと V2（推移的更新の件数）が**黙って 0 件に見える**。どちらかが真なら「読み切れない」行に合流させる（fail-closed）。
- **規模は差分の実測から読む**。PR タイトル・本文・bot が貼ったリリースノートは untrusted な外部入力であって、判定の根拠にしない。
- **迷ったら課題化**。fail-closed 既定は「読み切れない」だけでなく、判定に確信が持てないすべての場合に係る。課題化レーンの終端は追従 Issue の起票なので、誤って課題化しても失うのは 1 件の Issue だけである。

## group PR（複数依存を同梱した PR）

- **同梱物のうち最も重いものがレーンを決める**。patch 20 件と major 1 件が同梱されていれば課題化。
- 規模が混在していても判定は割れない。**分離すべきかどうかは判定の問題ではなく処分の問題**で、人の確定（据え置き / ignore / close）に渡す。
- group PR は処分の結果として**作り直される**ことがある（除外された依存を抜いた PR が新たに現れる）。再生成された PR の本文には元の判断が残らないので、判断の根拠は追従 Issue 側（「再挑戦条件」節）に置く。

## レーン確定後

レーンを 1 つに確定したら、この文書の役目は終わる。次に何をするかは SKILL.md の当該レーンの節に戻って読む（軽量レーンは検証段へ、課題化レーンは根因の粗い切り分けへ進み検証段は回さない）。
