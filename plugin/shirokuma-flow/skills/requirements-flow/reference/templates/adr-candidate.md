# ADR 候補 Issue 雛形

requirements-worker が **ADR 候補 Issue（IssueType `ADR`）** を起案する際の本文雛形。埋めれば候補 Issue 本文になる。

> ADR は **候補=Issue ／ 確定=正本ファイル（config `adr.dir`）** で扱う。候補 Issue 本文は決定の枠（Why payload）を担い、Why の審議・却下トレイルは**コメント**に積む（対話駆動）。
> 候補の状態は Issue の Status（状態機械: Backlog→Review→ToDo→Done）が正本。**本文に Status を書かない**（二重管理で drift する）。`approve`＝確定（副作用で ADR 正本ファイル `ADR-NNNN.md` を書き、索引に 1 行を足し、候補 Issue に確定コメントを書く）。**確定の形は宣言欄で決まり、打ち手は `shirokuma-flow next <候補番号>` の `runBy` に従う**——「緩めない」と宣言した候補は `approve` で確定し（既定は orchestrator が打つ）、「緩める（人が Accept）」と宣言した候補は `shirokuma-flow adr publish <候補番号> --accept-boundary-loosening` で確定する（素の `approve` / 素の `adr publish` は人が打っても CLI が拒否する。この形を打つのは既定では人で、緩める側の事前授権がある構成では AI も打つ。形と主体の正本は [[status-policy]] の `approve` 条項）。**`adr publish` verb の直打ちは既定では人専有**（config の事前授権がある構成で AI に開く条件は [[permission-boundary]]「verb 名では見分けられない副作用」節が正本。「緩めない」と宣言した候補の確定の正規経路は `approve` の副作用）。Status は正本ファイル（front matter）が持つ。状態遷移は orchestrator が flow verb で行う。worker は本文起案まで。
> 番号は **ADR ID（`ADR-NNNN`）が正本**（対応表 `adr-id-map.json` が `origin_issue` から確定・冪等に採番）。候補 Issue 段階では番号を断定しない（確定時に採番）。

## 構造

```markdown
{宣言欄（必須・BLUF 位置に 1 行）: 接頭辞と閉じた 2 値は `shirokuma-flow gate vocab --field adr-autonomy-boundary` が返す。
この決定の中身が `autonomous-flow` の `reference/criteria/irreversible-operations.md`
§1「例外」の判定基準 1・2 のどちらかに当たるか（一方でも当たれば例外に当たる。判定基準 2 の層の射程は flow の層に限らない）を、値域の 2 値から選んで書く}

**日付:** {YYYY-MM-DD}

## コンテキスト（Why）

{この決定の動機となっている問題。技術的・運用的・構造的要因と制約を記述する。
解決策ではなく問題を書く。「なぜ今この決定が必要か」を 1 段落で明確に}

## 決定（What）

{何を採用するのか。能動態で具体的に書く（「X を採用する」）。
スコープ（何に適用し・何に適用しないか）を含める}

## 検討した代替案

実在の検討のみを書く（比較のための捏造をしない）。「何もしない」も有効な代替案。

### {代替案 1}
- **利点:** {メリット}
- **欠点:** {デメリット}
- **却下理由:** {なぜ採らなかったか}

### {代替案 2}
- **利点:** {メリット}
- **欠点:** {デメリット}
- **却下理由:** {なぜ採らなかったか}

## 帰結（Consequences）

### ポジティブ
- {得られるもの}

### ネガティブ（トレードオフ）
- {失うもの・新たに生じる制約。正直に書く（空にしない——負の帰結の無い候補は approve の内容検査を満たさない）}

### 移行・互換性
- {既存への影響・段階移行の要否（ビッグバンを避ける）}

## 関連する決定
- {関連 ADR 番号と概要。先行 ADR の決定要素を**すべて**置き換える場合だけ **Supersedes: ADR-{NNN}** と書く。一部の要素だけを置き換える場合は Supersedes にせず、先行 ADR を Accepted のまま残し、どの要素を置き換えたかを本文に書く（Superseded にした ADR は語の取り込みの検査から外れるので、生きた要素を持つ ADR に使うと検査が黙って縮む）。Supersedes を書いた候補が確定したら、旧 ADR は人が `shirokuma-flow adr supersede <旧 ADR の ID> --by <この ADR の ID> --write` で Superseded にする（確定の `next` に出る）}

## 着地の見込み

{決定の What が、この候補を実装する変更の後も別の変更を縛るかを見て、縛る What ごとにカテゴリと置き場を書く。
縛らないなら「Issue だけ」と理由を書く。迷ったら着地させる側に倒す。
基準と迷ったときの判定規則は `docs-placement` 第 1 節、カテゴリ（名前・判定の問い）は `shirokuma-flow gate vocab --field adr-landing-category` で引く。
カテゴリは名前（語彙・モデル・構造・振る舞い・規範・設計思想・機械強制）で書く。確定後にこの見込みから `shirokuma-flow adr land` で記録する}

- {What}: {カテゴリ} → {置き場}（すぐ書ける / 実装と一緒に着地する）
- 既存の正本との突き合わせ: {決定が既存の置き場の What と食い違うか・食い違うならどれを改定するか。DDD 正本があるプロジェクトでは BC 帰属・集約境界・不変条件の 3 点を必ず書く（該当なしを含む）。手順は `ddd-enforcement-gradient`「着地した What の照合」節}

## 宣言欄の判定

- 例外の 1 項目め: {当たる / 当たらない}——{理由}
- 例外の 2 項目め: {当たる / 当たらない}——{理由}
- 迷った点: {どの項目で何に迷ったか。無ければ「なし」}
```

## 軽量版（小規模・容易に可逆な決定）

選択肢が単一で根拠が明白・影響範囲が小さい場合は軽量版で足りる。

```markdown
{宣言欄（軽量版でも必須・上と同じ 1 行）}

**日付:** {YYYY-MM-DD}

## コンテキスト（Why）
{問題・ニーズ — 1〜3 文}

## 決定（What）
{決定内容 — 1〜2 文}

## 検討した代替案
- {検討した代替と却下理由 — 「何もしない」も可}

## 帰結（Consequences）
- ポジティブ: {得られるもの}
- ネガティブ: {失うもの・新たに生じる制約（軽量版でも空にしない）}

## 着地の見込み
- {縛る What ごとに、カテゴリ（名前で書く）と置き場。縛らないなら「Issue だけ」と理由}
- 既存の正本との突き合わせ: {食い違う既存の What と改定の要否。DDD 正本があれば BC 帰属・集約境界・不変条件の 3 点（該当なしを含む）}

## 宣言欄の判定
- 例外の 1 項目め: {当たる / 当たらない}——{理由}
- 例外の 2 項目め: {当たる / 当たらない}——{理由}
- 迷った点: {どの項目で何に迷ったか。無ければ「なし」}
```

## 書き方の要点

- **決定文の要素を全部書く**: `approve`（＝確定）の内容検査は、候補本文に下のマーカー内の 4 要素が、対応する見出しの下に実際の内容として書かれていることを求める（判定の正本は `autonomous-flow` の `reference/criteria/irreversible-operations.md`「条件付き自動実行」§1）。
  <!-- gate-pin:adr-candidate-template/adr-decision-elements -->
  - ①決定 → `## 決定（What）`
  - ②背景 → `## コンテキスト（Why）`
  - ③trade-off → `## 検討した代替案`（検討した代替と却下理由。`## 帰結（Consequences）` の下のネガティブ小節は ③ ではない）
  - ④帰結 → `## 帰結（Consequences）`（**負の側を必ず含む**）
  - **要素 id**: `decision` / `context` / `trade-off` / `consequences`
  <!-- /gate-pin:adr-candidate-template/adr-decision-elements -->

  **軽量版でも 4 つとも、同じ見出しで要る**——軽量版が省けるのは粒度であって要素ではない。④は Nygard・MADR がともに必須とする Consequences に当たる。**遡及の射程は approve の時点で未確定の候補すべて**（確定済み ADR 正本ファイルには遡らない）。要素の集合の正本はコードのレジストリ（`shirokuma-flow gate vocab` の `adrDecisionElements`）で、上のマーカーに囲まれた範囲と上の雛形の見出し行はその写しである（正本との一致を照らす検査は配布物の外にしか無く、導入先では走らない）。
- 一般的な ADR の書き方（Why-first でコンテキストを決定より先に厚く・却下案は実在の検討から・1 候補 = 1 決定）に従う。審議の往復・却下トレイルは候補 Issue のコメントに積み、本文は確定形に近い「枠」を保つ。
- **宣言欄は必須**: 欄が無い候補は `approve` が**機械層に deny される**（欄なし・値域外・欄が複数・本文を取得できない回はすべて deny＝fail-closed）。**接頭辞も値も本雛形は逐語で持たない**——`shirokuma-flow gate vocab --field adr-autonomy-boundary` を 1 回引いて、**返った字形をそのまま 1 行で書く**（記憶で書くと値域外に落ちて deny される。とくにコロンは半角——`：`（全角）は接頭辞と一致せず `missing`＝deny になる）。**書き方は「空行で挟んだ単独の 1 行」**——本文中に**ちょうど 1 行**だけ、**直前行・直後行を空行にして**置く。**空行は半角空白・タブだけの行**（NBSP・全角空白のような見た目だけの空白は空行として扱われない）。**同一行に閉じる装飾**（例: 1 行に収まる打ち消し線）は行頭完全一致の条件で外れて `missing` になるが、**複数行にまたがる打ち消し線 `~~…~~` や `<del>…</del>` を空行で挟んで囲むと、単独段落の条件を満たしてしまい `missing` にならない**——**囲み系の装飾（打ち消し線・折りたたみ `<details>`・引用ブロック `<blockquote>` 等）で宣言を包まない**こと（塞げていない残存＝下記）。**コードフェンス / 字下げコードブロック / HTML コメント / `<script>`・`<style>`・`<textarea>`・`<pre>` の中や、他の HTML タグの中（属性値を含む）に入れない**——`<script>` 等の中身は GitHub が描画しないので値として採らず deny、フェンス・HTML コメントの中は値としては採らないが本数には入るので deny の原因になる。**行頭に見出し・箇条書き・番号付きリスト・引用・表の記号を付けない・欄名を強調（太字・斜体・打ち消し）で囲まない・HTML タグや打ち消し線・括弧・リンクで包まない**——**値として読み取られるのは単独段落の生の 1 行そのものだけ**で、装飾した宣言は権威ある値にならず「欄なし」として deny される（値採取は装飾を一切落とさない厳格な行頭一致＋単独段落＋HTML ブロック外）。**本数（deny の根拠になる「欄が複数」判定）は同一段落内で欄名の字がこの順で現れれば数える**（全称ではない——本文の他の場所（同じ段落の中）に欄名の字を並べて書くと、装飾や引用の体裁・HTML タグの中・HTML コメントの中でも「宣言に見える行」として数えられ、素の 1 行と併記すると「欄が複数」で deny される。**欄名を段落境界〔空行〕で分割した形・字を並べ替えた形は数えない**ので、引用や説明のためであっても欄名の字を分割せずに書かないこと）。**上の構造ブロックはフェンスの中にある雛形なので、フェンスごと写さない。** **欄の値は自己申告である**——「緩めない」と書けば機械層は通すので、緩めるかどうかの判定そのものは `autonomous-flow` の `reference/criteria/irreversible-operations.md`「条件付き自動実行」§1 の「例外」2 項を当てて行う。
- **「宣言欄の判定」節は軽量版でも書く**: 冒頭の宣言の値を選んだ根拠を残す節。例外の 2 項目の**両方**について、当たるか・当たらないかと理由を書き、迷った場合はどの項目で迷ったかを書く。2 項目の中身は本雛形に持たない——正本は `autonomous-flow` の `reference/criteria/irreversible-operations.md`「条件付き自動実行」§1 の「例外」。**flow の層に触れないことは、当たらない根拠にならない**（判定基準 2 の層の射程は製品側の層も含む）。**この節の中でも、冒頭の宣言の欄名の字を並べて書かない**（上の項のとおり「欄が複数」と数えられて確定が拒否される。「宣言欄」「冒頭の宣言」と書く）。
- **判定 JSON の `build` ブロック（`sourceMatch` / `dirty` / `degraded`・欠落した回の読み方を含む）の読み方は `shirokuma-flow gate limits --sub limits` の `H19` が正本**（ここに写さない）。`stale` を名乗った回・`build` ブロックそのものが無い回は、その判定を現ソースの値として読まない。`stale` と `build.dirty: true` が同時に立つ回は、その判定を根拠に使わない。`build.dirty: null`（焼いていない）は、再現性の担保が無い側として `build.dirty: true` と同じに読む。（本雛形が `shirokuma-flow gate vocab` の出力を読むすべての箇所に掛かる。）

**残存（fail-open のまま・網羅は主張しない）**: 空行で挟んだブロックレベルの HTML タグ（`<del>` / `<ins>` / `<details>` / `<blockquote>` 等）で宣言を囲むと、単独段落条件を満たし権威ある値として採られてしまう（`<details>` は折りたたまれ・`<del>` は打ち消し線として描画されるため、人には撤回・非表示に見えうる）。欄名 5 文字を段落境界（空行）で分割した形・並べ替えた形・見た目の似た別字への置換・文字の削除も計数から外れる。**この宣言欄の機械チェックは「宣言が 1 つに定まり雛形どおりに書けているか」を fail-closed に確かめる層であり、宣言を装飾で偽装することは想定していない**——**宣言は上の書き方どおりに素直に書く**こと。偽装が疑われる回は人が本文を読む（`approve` の人ゲートは `ambiguous` / `missing` のたびに残る）。
