# EPIC 親本文雛形

EPIC（親 Issue）を起案・整備する際の本文雛形。埋めれば EPIC 親本文になる。**Integration ブランチ節を必ず含める**（サブ Issue の PR ターゲット解決に使われる）。

> 階層モデル: 課題 → 設計（=1）→ 計画（複数可）→ PR。EPIC は `IssueType = EPIC`（継続型・auto-close しない。タイトル接頭辞 `EPIC:` は org に EPIC 型が無い環境向けの互換フォールバック）。親子は IssueType でなく**構造（sub-issue 関係）**で成立する。
> サブ Issue の参照は**実 Issue 番号で手書き**（再ペアレント確定後・プレースホルダを残さない）。状態遷移は orchestrator が flow verb で行う。

## 構造

```markdown
## 目的

{この EPIC で誰が・何を・なぜ達成するか。束ねる関心の共通軸を 1〜2 文で}

## 背景

{現状の問題・なぜ束ねるか。関連する決定（ADR）・制約}

## スコープ

- **含む**: {この EPIC が扱う範囲}
- **含まない**: {別 EPIC / フォローアップに送る範囲}

## Integration ブランチ

`epic/{親番号}-{slug}`

> サブ Issue の PR はこの Integration ブランチをターゲットにする（`branch-workflow`）。
> サブ Issue は Integration ブランチから分岐し、Integration ブランチへ PR を出す。
> 全サブ完了後、Integration ブランチから本流への最終 PR を出す。

## サブ Issue 構成

| # | Issue | 内容 | 依存 | サイズ |
|---|-------|------|------|--------|
| 1 | #{sub1} | {概要} | — | S |
| 2 | #{sub2} | {概要} | #{sub1} | M |

> サブはサイズ S/M に収める。XL なら着手前に分割する（[../criteria/sizing.md](../criteria/sizing.md)）。

## 実行順序

{依存関係に基づく推奨順序。一律「調査完了後」にしない（確定済み作業の並行着手を阻害しない）}

## 完了の定義

検証可能な形で書く。**継続型 EPIC は「子全 Done」では自動クローズしない**（人が閉じる）。

- [ ] {全サブ Issue が Done}
- [ ] {Integration ブランチ → 本流の最終 PR がマージ済み}
- [ ] {観測可能な完了条件（コマンド出力・成果物の存在）}

## リスク・懸念

| リスク | 影響範囲 | 軽減策 |
|--------|---------|--------|
| {サブ間の依存リスク・統合時の競合} | {範囲} | {軽減策} |
```

## 書き方の要点

- **Integration ブランチ節は必須**: ベースブランチの自動解決が `### Integration ブランチ` 見出し直後のバッククォート内ブランチ名を参照する。見出し名・記法を崩さない。
- **継続型と完了型の区別**: 継続型（EPIC / Research）は子が全 Done でも親は人が閉じる。完了型は子全 Done で親も Done（`status-policy`）。`cancel`（NOT_PLANNED）された子は「完了」に数えない。
- **サブの親は EPIC**: 束ねるサブは EPIC を親に持たせる（再ペアレント）。サブの IssueType は親から継承せず各タスクに適切な型を付ける。
- **数量の節間一致**: サブ Issue 構成・実行順序・完了の定義で参照するサブ数を一致させる。
