# 分割粒度の判定基準（sizing）

EPIC のサブ Issue・既存 Issue を「そのまま着手してよいか／分割すべきか」を判定する基準。**XL は着手前に必ず分割**する。

> 1 サブ Issue = 1 ブランチ = 1 PR が原則（`branch-workflow`）。レビュー可能な規模に保つことが分割の目的。
> 状態遷移・再ペアレントは orchestrator が flow verb で行う。

## サイズの目安

| サイズ | 目安 | 扱い |
|--------|------|------|
| XS | 1 ファイル・数行（タイポ修正等） | そのまま 1 サブ。背景節は省略可 |
| S | 数ファイル・数コミットで完結 | そのまま 1 サブ |
| M | 1 PR・1 レビューで差分全体を見渡せる | そのまま 1 サブ |
| L | 1 PR で見渡しにくい・関心が増えてきた | **分割を検討**（複数サブへ） |
| XL | 1 PR で見渡せない・複数の関心が混在 | **着手前に必ず分割**（S/M のサブ群へ） |

- 親が L/XL でも**サブは S/M が一般的**。サブのサイズは個々のタスクの工数で設定する（親から継承しない）。

## 分割が必要かの判定軸

以下のいずれかに該当したら分割する（特に L/XL）。

| 軸 | 分割する条件 |
|----|------------|
| レビュー可能性 | 差分が 1 レビューで読み切れない（diff が大きすぎる） |
| 関心の混在 | 1 つの Issue に独立した複数の関心（機能追加＋リファクタ＋設定変更）が同居 |
| 並行性 | 分ければ依存なく並行着手できる部分がある（直列に縛らない） |
| ロールバック単位 | 一部だけ戻したい場面が想定される（戻す単位＝PR 単位に分ける） |
| テスト境界 | テスト対象が複数の独立した振る舞いに分かれる |

## 分割の進め方

1. **関心ごとに割る**: 機能の縦の薄いスライス、または独立して検証できる単位で切る。
2. **依存を最小化**: 本当に順序が必要なものだけに依存を張る。一律「調査後」「基盤後」にしない。
3. **各サブを S/M に収める**: 割った結果が再び L 以上なら更に割る。
4. **EPIC の子として並べる**: 割ったサブは EPIC（親）の子にする。階層を深くぶら下げない。
5. **サブ構成表へ反映**: 分割結果を EPIC 親本文の「サブ Issue 構成」表に実番号で記す（[../templates/epic-issue.md](../templates/epic-issue.md)）。

## 過分割を避ける

- XS を機械的に分けない（オーバーヘッドが価値を上回る）。1 PR で安全に見切れるなら 1 サブで足りる。
- 分割は「レビュー可能性・並行性・ロールバック」のいずれかに実益があるときだけ行う。数を増やすこと自体は目的ではない。
