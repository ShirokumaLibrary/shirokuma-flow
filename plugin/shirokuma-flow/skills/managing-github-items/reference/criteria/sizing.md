# 分割の判定基準（sizing）

EPIC のサブ Issue・既存 Issue を「そのまま着手してよいか／分割すべきか」を判定する基準。**分割するのは、1 つの Issue を 2 本以上の PR に分ける必要があるときだけ**で、その条件（系統 1・系統 2）の正本は規範 `branch-workflow`「Plan ケース」節（ここには条件を写さない）。大きさだけでは分割しない。

> 1 サブ Issue = 1 ブランチ = 1 PR が原則（`branch-workflow`）。
> 状態遷移・再ペアレントは orchestrator が flow verb で行う。

## サイズの目安

サイズは工数の見積もりで、分割の判定軸ではない。

| サイズ | 目安 | 扱い |
|--------|------|------|
| XS | 1 ファイル・数行（タイポ修正等） | そのまま 1 サブ。背景節は省略可 |
| S | 数ファイル・数コミットで完結 | そのまま 1 サブ |
| M | 1 PR・1 レビューで差分全体を見渡せる | そのまま 1 サブ |
| L〜XL | 1 PR で見渡しにくい・複数の関心が混在 | 系統が真の部分ごとにサブへ分ける。系統が偽の部分は大きくても 1 サブ（PR 1 本）のまま、コミットで分ける |

- サブのサイズは個々のタスクの工数で設定する（親から継承しない）。

## 分割の進め方

1. **系統ごとに割る**: 規範 `branch-workflow`「Plan ケース」の系統が真になる部分ごとにサブを切る。
2. **依存を最小化**: 本当に順序が必要なものだけに依存を張る。一律「調査後」「基盤後」にしない。
3. **EPIC の子として並べる**: 割ったサブは EPIC（親）の子にする。階層を深くぶら下げない。
4. **サブ構成表へ反映**: 分割結果を EPIC 親本文の「サブ Issue 構成」表に実番号で記す（[../templates/epic-issue.md](../templates/epic-issue.md)）。

## 過分割を避ける

- 1 本の PR で閉じるものは分けない。関心ごとの切り分けはコミットで行う。
- 分割の数を増やすこと自体は目的ではない。
