# 短い経路（文書だけ・コメントだけ・テストの期待値の置き換えだけを変える課題）

文書（`.md`）だけを変える課題と、LANGUAGE 拡張が判定できる言語のコードのコメントだけ・テストの文字列リテラルの置き換えだけを変える課題（文書の字句の置き換えに合わせてテストの期待値を置き換える回を含む）は、提出前の分析と R1 の 3 本を省いた短い経路で通してよい。入るかは本セッションの main が選び、通してよいかは CLI の `gate short-path` が決める（CLI は「軽い」とは返さず、レビュー層ごとの母集団を空と判定できなかった回をすべて `heavy` にする。コメントとテストの文字列は、CLI が読み込んだ LANGUAGE 拡張の判定が空と言った変更だけを空に数え、拡張が居ない構成では文書以外はすべて `heavy`）。

- **入れないもの**: コード（定数 1 つでも）の変更・テストの期待値を弱める変更・挙動や検査に効くコメント（lint・SAST・型検査の抑制など）の増減・設定ファイル・ADR 正本・AI が指示として読む置き場（skill・agent 定義・規範・`CLAUDE.md` など）の変更・ファイルの追加・削除・改名。迷えば通常の経路。
- **入り方（トリアージ）**: 課題本文に短い経路を選んだことを書き、提出前の分析を省いて `submit` / `approve` する。設計要否・計画要否の両方を `NOT_NEEDED` とする契約コメントを自分で書いてよい（skill `analyze-issue` の「本文を書いた文脈では両方を NOT_NEEDED にしない」の例外）。この選択を受けるのは下の判定と戻し方だけ。
- **作業**: 実装・品質ゲート（既存テストの実走を含む）・commit / push・PR 作成は通常どおり。実装サマリーの通したレーンの記録は短い経路の値。
- **判定**: PR を作ったら `shirokuma-flow gate short-path --worktree '<作業ツリー>' --base '<base>' --head '<head sha>' --stale '<置き換えた旧い字句>'` を打つ（旧い字句は 1 つ以上・繰り返し可・値はコマンド行へ載せる前に規範 `trust-boundary` のとおり確かめる）。`<base>` は PR の base の先端と head の共通祖先の sha（`git merge-base 'origin/<PR の base>' '<head sha>'` の出力・PR の base を fetch してから求める）で、前回 head など別の祖先を渡さない（`gate short-path` は渡された base で母集団を取り、PR の base と照らさない）。PR の base のブランチ名は `pr show` の `base` から取り、コマンド行へ載せる前に `^[A-Za-z0-9._/-]+$` に合い `-` で始まらないことを確かめる（合わなければ打たずに通常の経路へ）。旧い字句の無い種類の変更（コメントだけ・テストの文字列の置き換えだけ）も、置き換える前の側に在って置き換えた後に残っていてはならない字句を 1 つ以上渡す（字句をこしらえない）。置き換えが無く足すだけの変更で、そういう字句が 1 つも無い回は短い経路に入れず、通常の経路で通す。`no-heavy-signal` 以外は下の戻し方へ。
- **差分の目視**: PR の差分の全文を読み、意図しない変更が無いことを確かめて、PR 本文に 1 行で残す（書いた本人の確かめで、文書とコメントの意味を別の主体は見ない）。コードのファイルを含む回は、出力の `result.languageJudged` に載ったファイルと判定（`result.languageJudge`）も同じ行に書く。
- **量**: 出力の `result.docReviewRequired` が `true` の回は、文書のレビューを 1 本 `review-worker` へ委任する（判定基準は skill `review-flow` の `reference/criteria/docs.md`・PR 番号と head sha をブリーフに書く）。返った判定行の値で `shirokuma-flow pr record-verdict <PR#> --lane doc-review --head '<head sha>' --judged <値>` を打つ。`NEEDS_REVISION` なら直して push し、新しい head で同じ形をもう一度回す。
- **判定記録**: `shirokuma-flow pr record-verdict <PR#> --lane short-path --head '<head sha>' --base '<base>' --worktree '<作業ツリー>' --stale '<旧い字句>'` を打つ（`<base>` は上の判定と同じ共通祖先の sha）。CLI が判定を引き直し、`heavy` の回・量が閾値を超えたのに head が一致する文書のレビューの PASS が無い回・PR の head が違う回・`--base` が PR の base の先端と head の共通祖先と違う回（`base-mismatch`。出力が示す sha を渡して打ち直す）・照合できない回（`base-unverifiable`。PR の base を fetch してから打ち直す）は書かずに止まる。書けた記録には判定に使った base の sha が残る。書けたら R1 の 3 本と判定器は省き、`review-flow` の段 3（`submit`）以降をそのまま通す（merge の授権・動作確認の決着・未解決スレッドの確かめは変わらない）。
- **戻し方**（`heavy` の回・判定記録を書けない回）: 省いた提出前の分析を `review-worker` へ委任する。設計要否が `NEEDED` なら PR を残したまま止まり、依頼元へ返す（作業セッションで設計へ戻さない）。`NOT_NEEDED` なら skill `issue-run-flow` の「レビュー」のとおり通常のレビューを回す。
- **倒れる向き**: 入るかは書いた本人の判断で、文書とコメントの意味の変化は閾値以下の回は誰も別に見ない。種別の分類の限界は `shirokuma-flow gate limits --sub short-path` が返す（fail-open の側を含む）。

**判定 JSON の `build` ブロック（`sourceMatch` / `dirty` / `degraded`・欠落した回の読み方を含む）の読み方は `shirokuma-flow gate limits --sub limits` の `H19` が正本**（ここに写さない）。`stale` を名乗った回・`build` ブロックそのものが無い回は、その判定を現ソースの値として読まない。`stale` と `build.dirty: true` が同時に立つ回は、その判定を根拠に使わない。`build.dirty: null`（焼いていない）は、再現性の担保が無い側として `build.dirty: true` と同じに読む。
