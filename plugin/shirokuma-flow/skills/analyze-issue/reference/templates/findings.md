# 所見レポート雛形

analyze-issue が返す所見レポートの構造。**先頭の判定行は機械分岐の契約**——orchestrator がこの文字列で次フローを分岐するため、一字一句この形式で必ず出力する（契約の正本は [../../SKILL.md](../../SKILL.md)）。

> 状態遷移は orchestrator が flow verb で行う。analyze-issue は所見の報告に専念し、**Issue を直さない**（修正は orchestrator が別 worker に委任する）。
> 所見は Issue コメントに投稿する（What/Why 分離: 本文は更新しない）。計画分析の所見は**計画 Issue（子）側**にコメントする。投稿は `shirokuma-flow issue comment {n} -`（stdin）等で行う。

## 構造

```markdown
**レビュー結果:** PASS | NEEDS_REVISION
**設計要否:** NEEDED | NOT_NEEDED   ← 要件分析時のみ。判定根拠を 1-2 文で添える
**計画要否:** NEEDED | NOT_NEEDED   ← 要件分析時のみ（設計要否と同じ回で必ず出す）。判定根拠を 1-2 文で添える

**適用基準**: {読んだ criteria ファイル名}
```

## 判定行の決め方

- `PASS`: 重大な問題なし（Medium 以下の改善提案があっても PASS）
- `NEEDS_REVISION`: 必須要素の欠落・重大な不整合・実装困難な要件・アンチパターン検出（High 以上の指摘あり）
- 対象別 criteria に個別の発動条件がある場合は**そちらを優先**（例: research の「取り込み提案あり = NEEDS_REVISION」・plan の「計画並存 = Critical」）

## 深刻度定義

| レベル | 影響 | アクション |
|--------|------|----------|
| **Critical** | 要件の欠落・実装不可能な要件・正本の二重化（計画並存等） | 次フロー進行をブロック |
| **High** | 重要な情報の不足・重大な不整合 | 次フローへ進む前に修正 |
| **Medium** | 改善余地・明確化の余地 | 修正推奨（PASS は可） |
| **Low** | スタイル・軽微な改善 | 後日対応 |
