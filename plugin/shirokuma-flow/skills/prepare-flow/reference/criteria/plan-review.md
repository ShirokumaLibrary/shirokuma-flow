# 計画レビュー観点（plan-review）

prepare-flow が所有する計画レビュー観点カタログ。prepare-flow の手順 2（計画レビュー委任）で発生する計画レビューの判定基準で、委任ブリーフに本ファイルのパスを明示して review-worker に渡す。基本チェックリストで構造を確認し、**本ファイルに実在する「観点 N」見出しの全件**で失敗パターンを検出する（実在する見出しの集合が正本）。観点に付く **観測 ID**（`plan_scope_drop_without_tradeoff` 等）は失敗パターンの識別子である。

> 計画 Issue は親 Issue の子（タイトルが「計画:」で始まる Issue）として作られる。`shirokuma-flow status {parent}` の `children` から計画 Issue を特定し、`shirokuma-flow issue context {plan-issue-number}` で本文を取得する。
> レポートの形式（先頭の判定行契約・深刻度定義）は委任ブリーフに明示されたレビューレポート雛形に従う。

**適用の流れ**: 基本チェックリストと**実在する「観点 N」見出しの全件**で検出 → 末尾の「判定」節で PASS / NEEDS_REVISION を決める。**検出段では指摘を深刻度に関わらず全件列挙し、絞り込みは判定節で行う**（検出段で絞ると低深刻度の所見が失われる）。

## 基本チェックリスト

### サブ Issue 本文の最低限確認（分解観点の一部）
- [ ] 各サブ Issue の受け入れ基準が**実行可能**か（実装者が完了条件を判別できる・観点 3 の二択禁止に抵触しない）
- [ ] 各サブの変更対象（ファイル / 範囲）が親計画のスコープに対して**妥当**か（漏れ・スコープ外の余分がない）

> **設計判断（Why）**: `approve` は承認継承でサブを一括 ToDo 昇格させるため、サブ本文の品質がここでしか裏取りされないと「分解観点のみで通る」ギャップが残る。一方でサブ本文の**深い個別精査**（受け入れ基準の網羅性・変更対象の実コード検証）まで approve 前に行うと、後段（implement-flow の `analyze-issue`・PR の `review-flow`）と**二重レビュー**になる。よって本観点は **分解観点の一部としての最低限確認**（実行可能性・スコープ妥当性）に留め、深い個別精査は後段に委ねる。実質レビューの正本は後段フローが担う。

### 目的・記述の十分性
- [ ] 「誰が・何を・なぜ」が揃い、目的とアプローチに一貫性がある
- [ ] 計画 Issue 本文だけで全体像を理解できる（外部の会話・別 Issue に依存しすぎない）
- [ ] アプローチの根拠（なぜこの方法か）・代替案の検討結果・前提条件が記載されている

### 要件カバレッジ
- [ ] 親 Issue の概要・検討事項・成果物の全項目に対応するタスクがある
- [ ] 暗黙の要件（テスト・ドキュメント更新等）が見落とされていない

### 変更ファイルの妥当性
- [ ] 変更対象ファイル一覧があり、漏れ・スコープ外の余分がない
- [ ] 新規作成と既存更新が区別されている
- [ ] ソースコード変更に対応するテストファイルが変更一覧に含まれている

### タスク粒度
- [ ] 各タスクが具体的で実行可能（「実装する」だけでなく、何をどう変更するか）
- [ ] 1 タスク ≈ 1 コミットの粒度・依存関係と順序が論理的

### リスク分析
- [ ] 破壊的変更の影響範囲・既存機能への影響・軽減策が記載されている（該当する場合）

## 観点 1: 親 Issue / 前提の検証

計画は親 Issue 本文の「背景」「現行仕様（確認済み）」を前提に組み立てられる。**親 Issue の前提が実装と乖離していると、計画全体が誤前提に引きずられる**。

- 定数マッピング・デフォルト値・列挙値の個数と内容を実コードで再確認した形跡があるか（grep / Read）
- 関連ファイルの行番号と関数シグネチャが実装と整合するか
- 実装済みガードの範囲を計画が独自検証したか
- ADR のトレードオフ記述を無批判に引き継いでいないか
- 前回レビュー指摘の転記で grep による一次確認を経たか

確認形跡がなく実装とのズレがあれば、`[計画]`（再確認タスク追加）と `[Issue記述]`（背景訂正）の 2 ラベルで分類して指摘する。

## 観点 2: 計画内のセクション間整合性

「N 箇所を置換する」のような数量記述は、変更対象節・タスク分解節・リスク節で**同じ根拠で数えられているか**をクロスチェックする。

- 計画内の数字（「8 箇所」等）が複数セクションで一致するか
- 「対象外」と明記される参照がある場合、「全 N 箇所」が対象外を含むか除外するか明示されているか
- 「N 箇所（列挙 M 行番号 他）」の「他」が何を指すか不明確なら、総数と個別列挙の内訳一致を要求

方針転換後は rationale コメント・判断根拠の同期更新も確認する（`plan_rationale_comment_drift_after_pivot`）。方針転換が親 Issue / ADR 本文の同期更新タスクとしてスコープに入っているかも要確認（`plan_phase_pivot_unsynced_to_epic`）。

オプション名のリネームが移行表に暗黙混入していないか、後方互換戦略が定義されているかも確認する（`plan_silent_option_rename_in_migration_table`）。

## 観点 3: 受け入れ基準の明確性

サブ Issue の受け入れ基準が「A を実施する、または A を実施しないと判断してクローズする」の**二択になっているケースは禁止**。実装者が完了条件を判別できない。

- 受け入れ基準が「A or B」形式なら、目的を「実装」「判断」「メタタスク」のいずれかに一本化するよう提案
- 同 EPIC で原則化を進める他のサブ Issue と矛盾しないか確認

## 観点 4: 「現状こうなっている」断定の実コード検証

計画の現状記述（「現状 X が抜けている」等）は、**ソース文字列を末尾まで読まず断定すると不要な修正タスクが混入する**。

- 説明文字列・JSDoc の特定トークン有無を主張する箇所は、文字列全体を Read で実地確認
- 不一致があれば Medium 以上で指摘し、「次回 plan-worker 委任時に『現状記述は実ソース末尾まで読んで検証する』フィードバックを渡す」旨をレポートに添える

## 観点 5: スコープ境界と除外項目の明示

計画が親 Issue の当初スコープから項目を**片側論点だけで除外**していないか、残存ユースケースと別 Issue 化計画が示されているかを確認する。

- `@deprecated` 残存呼び出しの扱いが計画スコープに明記されているか（`plan_deprecated_symbols_scope_ambiguity`）
- 重複解消 refactor で親 Issue 列挙の範囲だけ踏襲し、兄弟箇所の同一パターンが対象外で残っていないか（`plan_refactor_scope_omits_sibling_duplication`）
- スコープから除外する項目について、トレードオフの両側論点が記述されているか（`plan_scope_drop_without_tradeoff`）
- EPIC 計画でサブ Issue 依存が一律「調査完了後」になっていないか — 確定済み修正の並行着手を阻害する（`plan_subissue_dependency_vs_confirmed_fixes`）

## 観点 6: 環境変数 / データソース / guard 仕様の明示

新規導入する仕組みの**意味論を計画本文で確定**させる。

- 新規環境変数: 「何を上書きするのか」と既存ロジックの置換先が明記されているか
- 新規コマンド: データソースが「〜から取得する想定」止まりではなく検証済みか（`plan_new_command_with_unverified_data_source`）
- 検出ガード: 「warn ログのみ（処理継続）」か「書き込み拒否」かを計画本文で明示しているか（`plan_guard_behavior_ambiguity`）
- env 変数隔離機構: ガードを個別呼び出し側に置くと新規書き込みパス追加時に見落とすため、resolver 側に置く設計を要求（`plan_env_var_semantics_undefined` / `env_guard_resolver_vs_caller`）

## 観点 7: 計画 Issue の並存検出

計画やり直し時に旧計画を破棄せず放置すると、親の子一覧に計画が 2 件返り、実装者が誤って旧計画を読むリスクが生じる。

- 計画レビュー開始時に `shirokuma-flow status {parent}` を必ず実行し、`children` に計画 Issue が複数並存していないか確認
- 並存していれば **Critical** で指摘し、「採用しない方の `cancel`（orchestrator が verb で実行）、または『#X を破棄し #Y を採用』の明示宣言」を要求
- 「キャンセル済み」と前提を宣言された再レビュー依頼でも、`shirokuma-flow status {old-plan}` で実状態（Status・親子）を再取得して実機検証

## 観点 8: 抽出ヘルパーの呼び出し到達性（PR レビュー兼用）

共通ヘルパー抽出では、**ヘルパー単体の品質ではなく実ユーザー経路での到達可能性**を確認する。

1. 単体品質（JSDoc / 契約 / テスト）
2. 呼び出し側の到達性: 実ユーザー経路（CLI → スキル → サブコマンド）でヘルパーが実際に呼ばれるか、呼び出し分岐の条件を実データで検証
3. 分離関心の誤結合: 概念の違う 2 処理（「番号特定」と「本文注入」等）が同じ条件で gate されていないか

チェック方法: 呼び出し元のテンプレート（PR 本文雛形等）の実例を確認し、条件分岐のどちら側に落ちるかを追跡する。

## 観点 9: テストカバレッジの本番経路再現（PR レビュー兼用）

describe ブロックの全テストが同じ前提条件を共有していると、その前提が外れる本番経路の回帰テストが丸ごと欠落する。

- 同一 describe 内で beforeEach / 各 it が同じ前提（`undefined`・`null`・空文字列）を共有していないか
- 「回帰テスト追加」を主目的とする PR で、リグレッション再現の前提（呼び出し元が渡す実データ）をテストが再現しているか
- コード側の `if (X === null / empty)` 分岐の**非** null 経路が describe 前提の外に置かれていないか
- ヘルパー抽出 refactor で helper 自身の直接単体テストが追加されているか・呼び出し側の旧 mock 配線が dead で残っていないか（`helper_extraction_test_drift`）

チェック方法: 実呼び出し元のテンプレート出力を 1 件読み、その値がテストセットアップに現れるかを確認。現れなければ Critical パスの未カバーを疑う。

## 観点 10: PR 本文と実装の乖離（PR レビュー兼用）

PR 本文の「実装方針」と実装コードの挙動を照合する。4 バリアント（挙動の乖離 / 本文 > 実 diff / 本文 < 実 diff / 関数名の幻覚）を疑う:

| バリアント | 内容 |
|-----------|------|
| A: 挙動の乖離 | 本文「リトライロジック」、実装は verify-only 等 |
| B: 本文 > 実 diff | 本文は 5 項目を列挙、実 diff は 3 項目（残りは先行 PR 由来） |
| C: 本文 < 実 diff | 本文は単独修正だが、base の取り方により統合 PR 状態 |
| D: 関数名の幻覚 | 「`createXxx()` を追加」と書くが実 diff にその関数が存在しない |

チェック手順: PR 本文の箇条書きから動詞を抽出して diff で存在確認・`git log origin/{base}...HEAD` のコミット数確認・branch / base の整合確認。

## 観点 11: ルール文書のサンプルコード API 整合

新規ルール（`.shirokuma/rules/*.md` 等）のサンプルコードが実装 API と一致しているか確認する。

- 関数呼び出しの引数数・順序を実装と grep 照合
- 返り値型のフィールド名を実装と照合
- ADR 対応 PR では実装とルール文書が同時追加されるため、両者の整合チェックをレビュー観点に含める

## 観点 12: enum / 定数のドリフト

- 新たな enum 値を書き込み経路で使用するが validator の VALID 定数を更新し忘れ、次回整合性チェックで恒久 error を生むパターン（`enum_constant_drift_from_new_usage`）
- 「case mismatch 修正」タスクが、新表記 / LEGACY を意図的に分離した既存定数を破壊するパターン（`plan_case_mismatch_breaks_legacy_split`）

## 観点 13: エラー / 例外処理の意味論一致

- 既存 try/catch 流用を謳う計画で、catch メッセージの意味論が新規ロジックの失敗表現と乖離していないか（`plan_reuses_catch_block_with_mismatched_semantics`）
- 例外規定で「取得不可」と「概念的に存在しない」を同じ `undefined` で混同していないか（`exception_clause_new_addition`）
- 修復処理を「既存ファイル復元」から「registry 必須」に変える refactor でオフラインリカバリが喪失していないか（`script_hard_fail_removes_offline_recovery`）
- `stat -c | cut || stat -f` パターンが POSIX パイプライン exit code 仕様で非 GNU 環境で機能するか（`shell_stat_pipeline_fallback_broken`）

## 観点 14: 計画修正の親子同期

計画修正で**子計画だけ更新し親 Issue 本文が古いまま残る**と親子乖離が再発する（`plan_revision_recreates_parent_drift`）。

- NEEDS_REVISION 後の再レビューでは、High / Medium / Low の指摘が根本解消されたか + 新規副次問題の両面で判定（`plan_revision_addressing_high_medium_low`）
- 設計レビュー提案がサブ Issue だけに反映され、親本文の表が未更新で正本が二重化していないか（`plan_naming_drift_from_design_review_feedback`）

## 観点 15: 親 Issue の運用指示の取り込み

計画が親 Issue の運用指示（ファイル仕様・集約マーカー・ベースラインコミット等）を取り込み損ねるパターン（`plan_missing_parent_operational_directives`）。

- 親 Issue の「運用ルール」「実装ガイド」「制約」セクションが計画タスクに反映されているか
- 計画が親 Issue の事実誤認を引き継いでいないか（`plan_inherits_parent_factual_inaccuracy`）
- 親 Issue の「推定原因（〜の可能性）」を無検証で引き継ぎ、実装に当該処理が存在しないケースを誤認していないか（`plan_inherits_false_causal_claim`）

## 観点 16: 新規ドメイン語 / ADR 矛盾の持ち込み（条件付き・concept 整合）

計画が**新規ドメイン語を持ち込む**、または**既存 ADR と矛盾する方針を含む時のみ**発火する条件付き観点。設計を経ない課題（設計要否 NOT_NEEDED）では計画が最初のドメイン決定点になりうるため置くが、計画はタスク分解が主眼のため**無条件の必須項目にはしない**（該当しなければ何もしない）。

- 計画が glossary 未定義の新規ドメイン語を導入している、または Accepted ADR の決定と矛盾する方針を含む場合に**限り**、[[concept-gap-to-adr]] への橋渡しを促して差し戻す（`plan_introduces_new_domain_term_or_adr_conflict`）。**差し戻しが求めるのは Why の記録（ADR 候補 Issue の起票）までで、その ADR が Accept されるのを待たせるものではない**——候補が Review のままでも計画は再提出・承認・実装へ進んでよい
- ADR 絞り込み手順（adr list→get→突合）の複製はしない。矛盾・新規語の疑いを所見に挙げて concept-gap ルートへ渡すに留める

## 観点 17: BC 帰属 / 集約境界 / 不変条件（構造レベル・DDD 正本があるプロジェクト）

観点 16 が見るのは**語彙**（新語を入れたか）と**明示的な矛盾**（ADR と食い違うか）の 2 点だけで、「**正本から導出できているか**」は本観点が問う。DDD 正本（BC / 集約 / 不変条件）を持つプロジェクトでは、次を問う。

- 計画が触る範囲の **BC 帰属**が計画に書かれているか。複数 BC にまたがるなら、サブ分割が BC 境界と整合しているか
- **集約境界**をまたぐサブがあるなら、整合性をどちらに寄せるかが決まっているか
- 既存の**不変条件（INV）**を壊すサブが無いか。新 INV を導入するサブがあるなら、守る場所が決まっているか

「該当なし」も答えとして扱う——**問うたうえで該当なしと書かれていること**を確認する（問わなかったのか該当しなかったのかを区別できるようにする）。

**導出できない場合は差し戻さず橋渡しする**: 正本から導出できないと分かったら、それは計画の欠陥ではなく**正本の欠落**なので、[[concept-gap-to-adr]] へ渡す（**正本そのものが欠けている型**）。導出できないまま進める判断もありうるが、その場合は計画本文にその旨が明記されていることを求める。

強制度の正本は `.shirokuma/rules/ddd-enforcement-gradient.md`（計画フェーズの構造・INV は**ソフト観点だが必須で問う**＝機械強制ではない）。

## 観点 18: 委任・検査に触れる計画（正本は [[delegation-and-checks]]）

計画が **委任（このタスクは既存 worker / skill / 手順へ回す、という割り当て）または検査（ゲート・判定条件・決定表・lint ルール・レビュー観点・テストによる機械検証）に触れている可能性がある**なら、[[delegation-and-checks]] を読んで実際の発火条件を当て、該当したら同規範の D 節 / C 節で見て、同規範が定める深刻度（High / Medium）で指摘する。

観点・発火条件・深刻度の正本は同規範側にあり、**本ファイルは条件を写さない**（写した要約が本体より緩くなる形＝同規範 C5 を避ける）。この開閉条件は正本より広く取ってあり、当たりすぎることはあっても当たらなくなることはない。

- **計画フェーズ固有の当て方**: タスク分解の段では委任する差分の実物がまだ無いので、同規範 D2 に従い**差分の型**（そのタスクでどのファイル群が必ず変わり、どのファイル群が変わりうるか）を計画本文に書き出して当てる。
- **設計を経ない課題では、計画が委任先を決める最初の地点になりうる**（設計ノードを挟まない課題では設計レビュー側の同観点が一度も発火しない）。**設計の有無で本観点を振り分けない**。
- **同規範は機械検査を持たず fail-open**（気づかなければ黙って pass する）。レポートには**発火条件に当たったか否か**を書き、当たらなかったと判断した回はその理由を 1 行残す。

## 観点 19: 着地した What の照合（正本は [[ddd-enforcement-gradient]]「着地した What の照合」節）

この段では G1（置き場を書き換える）・G3（予定の着地を解消する）と、設計を経ない課題での構造・振る舞いの G2 を当てる（設計を経ない課題では計画が最初の決定点になりうるため）。モデルは観点 17 が見る。条件と深刻度は同節に従い、本ファイルには写さない。照合の申告行を書く。

## 判定（PASS / NEEDS_REVISION の決め方）

検出をすべて終えたあとに、列挙済みの指摘から判定する。

- **判定は High 以上の指摘があれば NEEDS_REVISION**（Critical を含む）。
- High が無く Medium 以下のみなら PASS（指摘はレポートに記載する。対応は著者の任意）。
