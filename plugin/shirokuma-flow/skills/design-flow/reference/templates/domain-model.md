# ドメインモデル雛形（domain-model）

design-worker が **DDD を採用する課題**（[../criteria/ddd-adoption.md](../criteria/ddd-adoption.md) の採用契機に該当）で、各 BC の集約・不変条件・ユースケースを記述するときに埋める雛形。プロジェクトの `domain/domain-model.md` の下敷きにする。[bounded-contexts.md](bounded-contexts.md) 雛形で BC を切ってから本雛形でモデルを厚くする。

書き方の規律:

- **コアを厚く・支援 / 基盤は要点のみ**: 差別化の中核 BC の集約・INV を丁寧に、支援 / 基盤 BC は箇条書きの要点で足りる（すべてを均等に厚くしない）。
- **集約は不変条件（INV）で括る**: 「一緒に守る整合性の単位」で集約境界を引く。独立に整合を保てるものは別集約にする（大きすぎる集約を作らない）。
- **値オブジェクトは識別子を持たない**（等価性は値で決まる・列挙・不変）。エンティティ（識別子＋ライフサイクルを持つ）と区別する。
- **決定の Why は ADR に置き、本書からは参照**する（ADR 番号を裸で参照・Why を本書に転記しない・二重管理しない）。ユビキタス言語の定義は glossary YAML が正本。
- **集約の見出しは `### 集約: {集約名}` で書く**（行頭が `###` ＋ 半角スペース ＋ `集約:` ＋ 半角スペース）。`auditing-docs` の **DDD レベル L2** 検査はこの形の行を数え、0 件なら `ddd-artifact-empty`(error) になる。
- **INV は行頭の `**INV**:` ブロックで書き、直後に箇条書きを 1 行以上続ける**。同じ L2 検査が「行頭形のブロックが 1 つ以上・かつ非空」を要求する（**識別子は要求しない**——散文のままでよい）。**箇条書きの一項として `- **INV**:` と書くと母集団から外れる**ので、行頭に置くこと。
- 上の 2 つとも下の雛形本文（`### 集約: {集約名…}` と `**INV**:` ＋ 箇条書き 2 行）がそのままこの形なので、**検査は雛形を追認するだけで新しい書式を課さない**。
- **貧血モデルを避ける**: 振る舞い（状態遷移・計算・検証）を集約に寄せ、データと処理を切り離さない（DDD 採用の主目的の一つ）。
- 状態遷移・Issue 提出は orchestrator が flow verb で行う（worker は本文を作るだけ）。

---

```markdown
# ドメインモデル

各 BC の主要な集約（Aggregate）・不変条件（INV）・ユースケース。コア BC を厚く、支援 / 基盤は要点のみ。glossary（ユビキタス言語）と整合させる。**決定の Why は ADR** に置く（本書からは参照）。

## {コア BC 名}

### 集約: {集約名（対応する概念）}

{この集約が何を 1 つにまとめるか。境界を引いた理由（一緒に守る不変条件）}

- **{構成要素 / 属性名}**: {説明。導出元があれば参照（[ADR-xxxx]）}
- **{値オブジェクト名}**: {識別子を持たない値。等価性は値で決まる}
- **親子 / 関連**: {集約内の関係か、別集約への参照か}

**INV**:
- {この集約で常に守るべき不変条件。破れない制約を宣言形で}
- {…（Why が横断的なら [ADR-xxxx] を参照）}

### 値オブジェクト: {名前}

{識別子・ライフサイクルを持たない列挙 / 不変値の説明}

### ユースケース（例）
- {この集約に対する主要な操作・シナリオ}

## {支援 / 基盤 BC 名（要点のみ）}

- **{BC 名}**: {主要な集約と INV の要点を 1〜2 文で。コアほど厚くしない}

## 集約一覧（まとめ）

**{中核集約} / {…}**。{値オブジェクトは集約でないことを明記}

## 次
ここから実装単位（skill / agent / rule / CLI / モジュール等）を導出する（各 BC の集約・ユースケースを実装に対応づける）。

---

[ADR-xxxx]: {決定の Why を置いた ADR（Discussion 等）への URL}
```
