# 設計ドキュメント雛形

design-worker が設計 Issue（IssueType=Design）の本文として埋める雛形。節構成はそのまま設計レビュー観点（[../criteria/design-review.md](../criteria/design-review.md)）と対になっている——Brief 品質 / 案比較の実績性 / 要件カバー / 実現可能性。

書き方の規律:

- **Why-first（AgDR）**: 採用案だけでなく**却下案と却下理由**を必ず書く。却下案は実在の検討に基づく（比較のための捏造をしない。検討の形跡＝参照した実コード・ADR・制約を示す）。
- 前提とする既存コード・API は**実コードで確認してから**書く（実在しない前提は設計レビューの自動指摘対象）。
- 大きな変更は段階移行（strangler-fig）で計画する。ビッグバン前提にしない。
- **計画要否を必ず宣言する**: 規範 `branch-workflow`「Plan ケース」のどちらかの系統（PR を 2 本以上に分ける理由）に当たれば `NEEDED`、当たらなければ `NOT_NEEDED`。作業の大きさでは決めない。`NOT_NEEDED` の設計は計画を飛ばして実装へ進むので、タスク分解を持たない（コミットの分け方は実装者が決める）。「受け入れ基準」と影響範囲の「リスク」は、計画が無いときに計画の代わりになる節として書く。
- 状態遷移・Issue 提出は orchestrator が flow verb で行う（worker は本文を作るだけ）。

---

```markdown
## Design Brief

| 項目 | 内容 |
|------|------|
| Purpose | {解決する問題。曖昧な「改善する」でなく検証可能な目標} |
| Context | {技術スタック制約・既存アーキテクチャ・既存パターンとの整合} |
| 対象ユーザー | {誰のための設計か（ロール / 呼び出し元）} |
| スコープ | {対象} |
| スコープ外 | {対象外（明記する）} |

## 案比較

### 案 A: {採用案の名前}（採用）

{構成・動作の要点。図・ディレクトリ構造・I/F 定義など}

- **採用理由（Why）**: {要件・制約に対する適合}

### 案 B: {却下案の名前}（却下）

- **却下理由（Why）**: {実在の検討に基づく理由。トレードオフの両側を書く——メリットも認めた上でなぜ採らないか}
- **検討の形跡**: {参照した実コード・ADR・制約}

（案 C 以降も同形式。比較軸が多い場合は決定マトリクス（案 × 評価軸）を併記する）

## 決定表

各行を [ADR 切り出し判定](../criteria/adr-extraction.md)の 6 軸で検分し、スコープを記録する。横断（ADR 級）の行は ADR 候補 Issue（IssueType=ADR）へ切り出し、本文からは ADR を裸番号で参照する（Why の本体は ADR 側・設計に転記しない）。

| 決定 | 選択 | スコープ | 根拠 |
|------|------|---------|------|
| {トピック} | {採った選択肢} | {この課題限り / 横断→ADR候補（参照する ADR）} | {理由（既存 ADR と矛盾しないこと。矛盾するなら ADR 改定をスコープに入れる）} |

## 影響範囲

| 観点 | 内容 |
|------|------|
| 変更対象 | {モジュール / ファイル / 公開 I/F。実在を確認済みのパスで} |
| 互換性 | {破壊的変更の有無・後方互換の扱い} |
| 移行パス | {段階移行の手順。新規設計なら省略} |
| テストへの影響 | {既存テストへの影響範囲} |
| 着地した What への影響 | {触れる置き場・縛る ADR・ADR の改定の要否・予定の着地（無ければ「該当なし」）} |
| リスク | {リスクと影響範囲・軽減策} |
| 未決事項 | {適用時までに解消する事項（あれば）} |

## 計画要否

**計画要否:** {NEEDED | NOT_NEEDED}

{規範 branch-workflow「Plan ケース」のどの系統に当たるか（どちらにも当たらないか）と、その理由}

## 受け入れ基準

- [ ] {検証できる基準。確かめるコマンドか手順を添え、対象が 0 件のときに真にならない形で書く}
```
