# 設計レビュー観点（design-review）

design-flow が所有する設計レビュー判定基準。design-flow の手順 4（設計レビュー）で発生する設計レビューの基準で、委任ブリーフに本ファイルのパスを明示して review-worker に渡す。観点は Design Brief 整合性・要件カバー・案比較の実績性・実現可能性の 4 群。

> フレームワーク固有の設計観点（route 階層・server/client 境界・AWS リソース選定等）は各拡張プラグインの designing-* / reviewing-* skill 側にあり、本ファイルには置かない。
> レポートの形式（先頭の判定行契約・深刻度定義）は委任ブリーフに明示されたレビューレポート雛形に従う。

**適用の流れ**: 観点 1〜4 とアンチパターンで検出 → 末尾の「判定」節で PASS / NEEDS_REVISION を決める。**検出段では指摘を深刻度に関わらず全件列挙し、絞り込みは判定節で行う**（検出段で絞ると低深刻度の所見が失われる）。

## 1. Design Brief の品質

| 基準 | 評価観点 |
|------|---------|
| Purpose | 解決する問題が具体的に記述されているか。曖昧な「改善する」ではなく、検証可能な目標があるか |
| Context | 技術スタック制約・既存アーキテクチャ・既存パターンとの整合が網羅されているか |
| 対象ユーザー | 誰のための設計か（ロール / ユーザー種別 / 呼び出し元）が明確か |
| スコープ | 設計の対象と対象外が明記されているか |

- [ ] Design Brief が存在する（見出しのみで内容が空でない）
- [ ] 課題 Issue の要件と Brief の目標が対応している

## 2. 案比較・決定の実績性（Why-first）

- [ ] 採用案だけでなく**却下案とその却下理由**が記載されている
- [ ] 却下案が実在の検討に基づいている（比較のための捏造でないか。検討の形跡＝参照した実コード・ADR・制約が示されているか）
- [ ] 主要決定が決定表（決定 / 選択 / スコープ / 根拠）にまとまっている
- [ ] 決定表の各行のスコープが判定されている（この課題限り / 横断→ADR候補）。**ADR 級（6 軸該当）の横断決定が ADR 候補へ切り出されず決定表に埋もれていないか**（可逆性 / 構造性 / 影響範囲 / 規約確立 / 既存決定変更 / トレードオフ）
- [ ] 決定が既存 ADR と矛盾しない。矛盾する場合は ADR の改定・新 ADR 起案がスコープに入っている
- [ ] トレードオフの**両側**の論点が書かれている（メリットのみの比較は指摘）

## 3. 要件カバーと整合性

- [ ] 課題 Issue の要件（概要・成果物・検討事項）が設計で全てカバーされている
- [ ] 設計が要件のスコープを超えていない（スコープクリープ・過剰設計）
- [ ] 設計内のセクション間で矛盾がない（構成図と本文の記述・命名の不一致等）
- [ ] 用語がプロジェクトの glossary / 既存ドメイン語彙と一貫している（**順方向**: 既存語との一貫）
- [ ] **逆方向 canon-gap**（必須）: この設計 / 変更は正本（concept / domain / glossary / Accepted ADR）に**無い新概念・新しい成果物クラス・新しい役割**を持ち込んでいないか。順方向（既存語との一貫）と対で常時発火させ、正本に照らして「これは何という語で、どの正本に定義があるか」を問う。定義の無い新語・新クラス・新役割が黙って設計に入っていたら High（NEEDS_REVISION）
  - **検出時運用（ADR-first）**: 末端の glossary へいきなり定義を足して辻褄を合わせない。[[concept-gap-to-adr]] に従い **Why を先に記録する**（ADR 候補 Issue の起票 → glossary 定義・不変則 → rules / criteria 配線）。**High（NEEDS_REVISION）に当たるのは「Why が記録されていない」場合だけ**——すなわち検出した新概念に対応する **ADR 候補 Issue が起票されておらず**、glossary / rules へ直書きして既成事実化しているケース。**候補 Issue が起票済みなら、それが Review のまま（未 Accept）でも順序違反ではない**——Accept 前に glossary / rules を触ること自体は High ではない（規範ファイルの変更は [[rule-evolution]] のとおり Issue → PR → 人の確定を通る＝**その規律は本観点の外**であって、本観点が見るのは Why が記録されているかだけ）
  - **自律の境界**: 概念ギャップの検知・ADR 候補 Issue での Why 記録・What ドラフトの提示（HTML 可視化）まで AI が能動。人ゲートは **`adr publish` の直打ち（verb 名では候補ごとの条件を表現できないので既定は人専有。config の事前授権がある構成で AI に開く条件は [[permission-boundary]]「verb 名では見分けられない副作用」節が正本）と、宣言欄が「自律の境界を緩める」と述べている候補の `approve`、および rule / glossary 変更の最終確定**（**緩めないと宣言された候補の `approve` は既定どおり orchestrator が打つ**）＝いずれも外向き・不可逆な操作の側であって、**実装・設計を進める前提ではない**（[[concept-gap-to-adr]] 手順 5）

## 4. 技術的実現可能性

- [ ] 前提とする既存コード・API・依存が実在する（設計が参照するファイル・関数を実コードで確認）
- [ ] 既存アーキテクチャの境界（モジュール責務・レイヤ分離）に沿っている
- [ ] 移行パスがある（大きな変更は段階移行＝strangler-fig で計画されているか、ビッグバン前提でないか）
- [ ] 実装コスト・リスク（破壊的変更・互換性）への言及がある
- [ ] **委任・検査に触れる設計**（必須・正本は [[delegation-and-checks]]）: 設計が **委任（既存または本設計で新設する worker / skill / 手順への作業の割り当て）または検査（ゲート・判定条件・決定表・lint ルール・レビュー観点）に触れている可能性がある**なら、[[delegation-and-checks]] を読んで実際の発火条件を当て、該当したら同規範の D 節 / C 節で見て、同規範が定める深刻度（High / Medium）で指摘する。観点・発火条件・深刻度の正本は同規範側にあり、**本ファイルは条件を写さない**（写した要約が本体より緩くなる形＝同規範 C5 を避ける）。この開閉条件は正本より広く取ってあり、当たりすぎることはあっても当たらなくなることはない
  - **設計フェーズ固有の当て方**: 設計時点では委任する差分の実物がまだ無いことが多い。その場合は同規範 D2 に従い**差分の型**（どのファイル群が必ず含まれ、どのファイル群が含まれうるか）を設計本文に書き出し、それを母集団に当てる
  - **同規範は機械検査を持たず fail-open**（気づかなければ黙って pass する）。レポートには**発火条件に当たったか否か**を書き、当たらなかったと判断した回はその理由を 1 行残す

## 検出すべきアンチパターン

| パターン | 問題 |
|---------|------|
| Brief 不在・空 Brief | 設計判断の前提が確認できない |
| 却下案なしの一本道 | 比較検討の形跡がなく、人が What を確定する材料がない |
| 実在しない前提 | 参照する既存コード・API が実装と乖離（行番号・シグネチャ含む） |
| スコープクリープ | 要件にない機能・将来要件の先回り設計 |
| ビッグバン移行 | 段階移行パスのない全面置換 |
| 既存 ADR との暗黙の矛盾 | Deprecated / Superseded とされた選択肢の再採用 |
| 横断決定が設計 Issue に埋没 | ADR 級（6 軸該当）の横断的・長寿命の決定が ADR 候補へ切り出されず決定表に埋もれ、複数課題から再解釈され齟齬の温床になる |
| 委任・検査の配線が発火しない | 委任した作業が全件 skip に倒れる／足した検査が母集団 0 件で緑に倒れる形（**判定条件は [[delegation-and-checks]] が正本。本行は条件を要約せず、当該規範を開く合図として置く**） |
| 逆方向 canon-gap の無音素通し | 正本（glossary / domain / ADR）に定義の無い新概念・成果物クラス・役割が黙って設計に入り、**Why がどこにも記録されないまま**（ADR 候補 Issue が起票されないまま）末端の辻褄合わせで既成事実化する（[[concept-gap-to-adr]]）。**候補 Issue が起票済みで未 Accept なだけの状態はこれに当たらない** |

## 判定（PASS / NEEDS_REVISION の決め方）

検出をすべて終えたあとに、列挙済みの指摘から判定する。

- **判定は High 以上の指摘があれば NEEDS_REVISION**。
- High が無く Medium 以下のみなら PASS（指摘はレポートに記載する。対応は著者の任意）。
