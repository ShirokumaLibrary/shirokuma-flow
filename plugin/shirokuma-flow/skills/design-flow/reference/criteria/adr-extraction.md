# ADR 切り出し判定基準（adr-extraction）

design-worker が設計案の**決定表の各行**を点検し、「この課題限りの What」か「横断的・長寿命の Why（ADR 級）」かを判定して、後者を ADR 候補 Issue に切り出して設計本文からは番号で参照するための基準。review-worker が設計レビュー時に「決定表に ADR 級が埋もれていないか」を見極める際にも使う。

> **本書の射程**: 決定表の**各行への適用**に特化する。ある決定そのものを ADR 候補として起票するか否かの**網羅的な要否判定**は requirements フェーズの責務であり、本書はそれを設計の決定表という具体に焼き直したもの。両者の判定軸は同源だが、design-flow が自己所有して単体で完結させる（別所への参照に依存しない）。
>
> **役割の原則（What / Why 分離）**: 設計ドキュメントは「**この課題の What**」を確定する場。横断的・長寿命の「**Why**」（なぜその構造・規約を選ぶか）は、設計本文に書き切るのではなく ADR に分離する。設計は ADR を**裸番号で参照**し、決定表には「スコープ=横断（ADR へ）」と記録する。これにより、複数の課題から参照される決定が個別設計に埋没せず、独立に問い直し・改定できる単位に保たれる。

## 6 軸の検分（決定表の各行に適用）

決定表の各行について、以下の**いずれか**に該当したら、その行は ADR 候補として切り出す。

| 軸 | ADR に切り出す条件 |
|----|-----------------|
| 可逆性 | **元に戻しにくい**選択（移行コストが高い・データ形式が変わる・公開 API / 契約が変わる） |
| 構造性 | アーキテクチャ・境界・依存方向・分割方針を**決める / 変える** |
| 影響範囲 | 複数コンポーネント / 複数の課題 / 長期にわたって参照される |
| 規約の確立 | 以後の判断を縛る**パターン・規約**を定める（「以後すべて X する」） |
| 既存決定の変更 | 既に確定した決定や Accepted な決定を**覆す / 置換する** |
| トレードオフ | 採否で**何かを失う**選択（両側にコストがある決定） |

- 1 つでも当てはまり、かつ「後から人が経緯を問い直す可能性がある」なら、その決定行は ADR へ切り出す。
- どれにも当たらない（容易に可逆・影響範囲が単一・根拠が明白）行は、設計本文にそのまま残す＝**この課題限りの What**。

## 切り出し手順

ADR 級と判定した決定表の行は、以下の導線で切り出す（経路自体は既存）。

1. **ADR 候補 Issue を最上位で起票**（IssueType = ADR・`--parent` を付けない）。その決定の Why（動機・制約・却下案・トレードオフの両側）を Issue 本文に残す。決定（What）は 1 ADR につき 1 つに保ち、複数の決定を混ぜない。
   - **配置**: **課題（normal）・設計（design）・計画（plan）の子にしない**。ADR 候補は最上位の独立決定として扱う。出典は 2 つに分かれる——**最上位 allowlist に `ADR` を含める線引きの正本が [[issuetype-hierarchy]]**、**子として置けない禁止そのものは rule ではなく kind 階層の実装（合法な子 kind の表）から導出**される（下記①）。継続型（EPIC / Research）の文脈で追跡したいときは、その直下に置くのは可。
   - **なぜ**: ① 階層モデル上、課題（normal）の合法な子は design / plan・設計（design）の合法な子は plan だけで、ADR 候補をそれらの子にすると kind が sub に倒れて `reconcile` が逸脱として報告する（code は配置で分かれ、親の直下に計画〔plan〕の兄弟がいれば `misplaced-sub`、いなければ `illegal-child-kind`）——**いずれも `ambiguous` 分類**なので `--fix` では直らず、人が毎回手で片付けることになる。**ただし計画（plan）の子だけは `plan > sub` が合法**なので階層違反としては報告されない——代わりに、計画が承認済み（ToDo 以上）で ADR 候補が Backlog のままだと承認継承の取りこぼし（`approval-inheritance-missed`・**`deterministic`**）が立ち、`reconcile --fix` が ADR 候補を実装サブとして ToDo へ昇格させる。② **課題・設計・計画のいずれの子でも、親の完了が ADR の確定（approve）に縛られる**——`done` / `cancel` の子未完ガードと親 Done カスケードはいずれも子の kind を区別せず全子 Done を要求するため、ADR が確定（approve）するまで**親を閉じられない**（縛られるのは**親の close だけ**で、設計 submit・計画・実装は ADR 候補の状態に関係なく進む。[[concept-gap-to-adr]] 手順 5）。**禁止の根拠は②**（3 ケースすべてに効く）で、①の検知信号の有無ではない。
   - **宣言欄の見込みを設計に書くときは、例外の 2 項目の両方を当てる**: ADR 候補の宣言欄が緩める側になるか緩めない側になるかの見込みを設計本文に書くなら、片方の項目だけで「緩めない」と見込まない（起草時に覆り、確定の打ち手が変わる）。2 項目の正本は `autonomous-flow` の `reference/criteria/irreversible-operations.md`「条件付き自動実行」§1 の「例外」（ここには写さない）。
   - **トレーサビリティは親子関係でなく番号参照で取る**（次の手順 2）。設計本文からの裸番号参照が ADR との紐付けを担う。
   - **`IssueType=ADR` を「子として置く」操作は機械強制されるが、止めるゲートと射程は経路ごとに違う（create / retype は継続型〔EPIC / Research〕以外のすべての親で block・reparent は計画〔plan〕親だけ素通り・親側の型変更と flow 外は無防備）**: ゲートを呼ぶのは `issue create --parent` / `issue retype` / `issue reparent --parent` の 3 経路。
     - **`issue create --parent` と `issue retype`**: `IssueType=ADR` を課題（normal）・設計（design）・計画（plan）の子にする操作は **ADR 配置ゲートが hard-block する**。親子 kind の予防ゲートは子 kind が `sub` に倒れるとき呼ばれない（EPIC / Research 直下に nature 型サブを置く既存運用を壊さないための設計）ので、`IssueType=ADR` はこの隙間を素通りする——その 1 型だけを IssueType 名で名指しして別ゲートで閉じた形で、`normal > sub` 一般（課題直下への Task / Docs 直付け）は通常どおり通る。block 文面は合法な配置（**最上位で起票** / **継続型 EPIC・Research 直下**）を併記する。
     - **`issue reparent --parent`**: ADR 配置ゲートは呼ばない（対象外）。付け替え後に導出される kind（ADR → sub）で親子 kind ゲートを評価するため、課題（normal）・設計（design）親は `normal > sub` / `design > sub` 違反として block されるが、文面は kind 階層違反であって ADR の合法配置は併記されない。**計画（plan）親は `plan > sub` が合法なので reparent では今も素通りする**（この素通りを確かめる検査は配布物の外にしか無く、導入先では走らない）。
     - **親側の型変更（`issue retype <親>`）は塞がっていない**: retype は対象の**親**しか見ず子を走査しないため、EPIC 直下に合法に作った ADR 候補は、**親を Feature 等へ retype した時点で事後に `課題 > ADR` へ変わる**。上の 2 経路が守るのは「ADR を子として置く」向きだけで、「親を継続型から外す」向きは誰も止めない。
     - **共通の限界**: いずれのゲートも `issueTypes` を設定しているプロジェクトでのみ有効で、`--force` でバイパスされ、`issue create --no-project`（bootstrap）では入口ゲート群ごとスキップされる。対象の IssueType 名は **`ADR` 固定**（config 化されていない）なので、決定を別名の型で運用するプロジェクトでは設定済みでも静かに無効になる。**「継続型直下は可」の判定は親の IssueType ではなく導出された kind で行う**ため、タイトルが `EPIC:` で始まる親は IssueType が Feature 等でも継続型として扱われる（互換フォールバック）——裏返せば、親を **nature 型（Feature 等）へ**変えても**タイトル接頭辞が残っている限り**継続型のままなので、上記「親側の型変更」の穴はその向きでは開かない。**ただしこの接頭辞フォールバックは、kind 導出が役割型（計画 / 設計）と認識する型への変更には効かない**——kind 導出は接頭辞を見るより先に役割型で kind を確定するため、接頭辞が残っていても継続型ではなくなる（役割型かどうかは IssueType 名の照合で決まるので、役割型を別名で運用するプロジェクトではそもそもこの限定が立たず接頭辞フォールバックが効く。**照合は名前の大小差・前後の空白を吸収する**ので、それらの違いは別名にあたらない）。その経路は入口ゲート群（最上位なら最上位 allowlist・子なら親子 kind ゲート）に当たりうる。ただし**先行して変則的な配置が要るのは子として成立させる場合だけ**で、**最上位の親ではそれも要らない**——親なしの型変更に効くのは最上位 allowlist だけなので、その allowlist に役割型を含むプロジェクトなら 1 手で成立しうる（allowlist の中身は対象リポの config が決めるので、成立するかはプロジェクト依存）。いずれにせよ**どこまで実際に成立するかはここでは網羅していない**。「接頭辞があるから開かない」を型変更の向きを問わず一般化しないこと。block 文面が示す「最上位で起票」は、`issueTypes.topLevel` に `ADR` を含まないプロジェクトでは最上位 allowlist ゲートで再び止まる。**さらに 3 経路はいずれも flow の verb**——GitHub Web UI の sub-issue 追加や `gh api` 直叩きはゲートを通らないので、この限定自体が flow を経由する操作に閉じている。素通りした逸脱は事後に `reconcile` が `ambiguous` として検知するのみ（`--fix` では直らない）——**ただし計画（plan）親では `reconcile` は「配置については」何も言わない**（`plan > sub` は合法なので階層違反が立たない＝入口だけが止める非対称）。**Status 軸は別で、上の「なぜ」①のとおり `approval-inheritance-missed`（`deterministic`）が立ち `--fix` が ADR 候補を実装サブとして ToDo へ昇格させうる**——「何も検知されない」ではないので取り違えない。
2. **設計本文から参照**: 設計ドキュメントには決定の結論と、ADR の**裸番号での参照**を書く。Why の本体は ADR 側に置き、設計本文に転記しない。
3. **決定表のスコープ列に記録**: 当該行のスコープを「横断（ADR へ）」とし、参照する ADR を示す。この課題限りの行は「この課題限り」と記録する。

> 起票・確定・公開の経路（IssueType=ADR → 承認 → 公開）は既存の仕組みに乗せる。本書は決定表からその経路へ流す導線を示すのみ。
>
> **切り出したあとは待たない（明示）**: ADR 候補を起票した時点で **Why は記録済み**なので、**候補が `Backlog` / `Review` のままでも設計本文の完成・`submit`・計画・実装へ進んでよい**。`approve` / `adr publish` は**公開（外向き・不可逆）のゲート**であって設計・実装の前提ではない（[[concept-gap-to-adr]] 手順 5）。CLI も ADR 候補の状態ではフェーズを止めない（根拠は `autonomous-flow` の `reference/criteria/phase-skill-map.md` の「注記」節）。

## 過剰 ADR 化の歯止め

- **迷ったら軽量に**: ADR にするほど重くないと感じたら、設計本文・Issue 本文・PR 説明に Why を残して通常進行する。
- 過剰な ADR 化は索引を汚し、**本当に重い決定を埋もれさせる**。「後から人が経緯を問い直す可能性」が薄い行まで切り出さない。
- 逆に、決定表が一見すると単純な選択ばかりでも、規約を確立する行や境界を動かす行が混ざっていないかは毎回検分する。**埋もれた横断決定**は、後から複数の課題で再解釈され齟齬の温床になる。

## Why-first の運用（切り出し時）

- **Why を先に残す**: 決定（What）を確定する前に、動機・制約・却下案を ADR 候補 Issue に残す。質問は記録済みの Why から答える。
- **却下案は実績から**: 検討した代替案は実在の検討から書く。捏造した弱い対抗案を並べない。
- **末端で確定しない**: 設計中に「これは末端で確定すべきでない」と気づいたら、その場で決めずに ADR 候補として起案する（言われる前に能動的に）。長寿命・横断の決定を個別設計に閉じ込めない。
