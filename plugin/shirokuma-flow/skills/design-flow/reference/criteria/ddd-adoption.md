# DDD 採用可否判定基準（ddd-adoption）

design-worker が設計案を作るとき、その課題に **DDD（ドメイン駆動設計）の道具立て**（集約 / 値オブジェクト / ドメインサービス / ユビキタス言語 / glossary YAML 正本 等）を採り入れるかを判定する基準。設計は複雑度に見合う道具を選ぶ場であり、DDD は「常に使う型」ではなく「複雑さがそれを正当化するとき借りる道具」として扱う。

> **方針**: DDD は**実用的に借りる**。採用は**各プロジェクト・各課題の裁量**であり、本フレームワークは DDD を**支援するが強制しない**。判定は下の採用契機（OR）と非採用下限で行い、迷ったら軽い方（非採用）から始めて必要になってから育てる。
>
> **役割の原則**: DDD は目的ではなく手段。複雑なドメインの誤解コストを下げ、モデルとコードの乖離を防ぐために借りる。複雑さが無い所に持ち込むと、間接層が増えるだけで理解コストがかえって上がる。

## 採用を検討する契機（OR・いずれか該当で検討）

以下の**いずれか**に該当したら、その課題では DDD の道具立てを採ることを検討する。全てを一度に導入する必要はなく、該当した契機に対応する道具（集約・値オブジェクト・ドメインサービス等）を部分的に借りてよい。

| 契機 | 該当する状況 |
|------|------------|
| 集約をまたぐ不変条件 | 複数のエンティティ / 集約にまたがって守るべき不変条件（整合性ルール）があり、単一レコードの制約では表現しきれない |
| ロジックの層またぎ重複 | 同じドメインロジックが UI / API / 永続化など**複数の技術層に重複して漏れうる**（ロジックの置き場所が定まらず散らばる兆候） |
| 誤解の高コスト | ドメインモデルの誤解・用語のブレが**高コストな手戻り / 障害**を招く（金額・在庫・権限・状態遷移など間違えると影響が大きい領域） |
| 豊かな振る舞い | データ構造だけでなく、状態遷移・計算・検証など**振る舞いが本質**で、貧血モデル（データと処理の分離）では表現が痩せる |
| 長寿命・多参照 | そのモデルが長期に使われ、複数の課題・チームから参照・拡張され続ける（ユビキタス言語を glossary YAML に正本化する価値がある） |
| 境界づけの必要 | サブドメイン / 文脈ごとに同じ語が別の意味を持ち、**境界づけられたコンテキスト**を明示しないと語彙が衝突する |

- 1 つでも当てはまり、かつ「モデルを丁寧に立てる投資が誤解・重複コストを上回る」と見込めるなら、対応する DDD 道具を採る。
- 該当契機に対応する道具だけを借りる（集約不変条件があるなら集約境界を、語彙衝突があるなら境界づけを）。**全部入りにしない**。

## 非採用の下限（ここまでなら DDD を持ち込まない）

以下に当てはまる課題は、DDD の道具を持ち込まず**素直な型 + アクセサ / 関数**で足りる。過剰なモデリングは避ける。

- **素直な型 + アクセサで足りる**: データの保持・受け渡し・単純な CRUD が主で、守るべき不変条件が単一レコード内の制約に収まる。
- **振る舞いが薄い**: 計算・状態遷移・検証がほぼ無く、データ構造そのものが関心の中心（設定値・DTO・ログ・表示用データ等）。
- **短命・局所**: その場限りのスクリプト・一時的な変換・単一箇所からしか参照されないもの。
- **ロジックが 1 箇所に自然に収まる**: 層をまたいで重複する兆候がなく、置き場所に迷わない。

> これらは「今は不要」であって「永久に禁止」ではない。後から採用契機（OR）に該当した時点で、必要な道具だけ段階的に導入する（strangler-fig・ビッグバンにしない）。

## 迷ったときの原則

判定の方針そのものは冒頭の「方針」ブロックが正本（DDD は支援するが強制しない・迷ったら軽い方から始める・採用可否は各プロジェクト / 各課題の裁量）。ここではその運用上の帰結だけを挙げる。

- **先回りで重い構造を敷かない**: まず素直な型で書き、複雑さが顕在化してから集約 / 値オブジェクトへ育てる。
- **他プロジェクトの慣習を持ち込んで一律 DDD 化しない**: フレームワークが提供するのは支援（雛形・glossary 正本・lint）だけ。
- **横断決定は ADR へ**: 「このプロジェクトは以後 DDD を採る / 採らない」「この境界づけを規約とする」等、以後の判断を縛る決定は横断的・長寿命なので [ADR 切り出し判定](adr-extraction.md) に従い ADR 候補へ切り出す（設計本文に閉じ込めない）。

## 構造レベルの観点（DDD 正本が既にあるプロジェクト向け・必須で問う）

上記は「DDD の道具を**新たに**持ち込むか」の判定。これとは別に、**正本（BC / 集約 / 不変条件 / glossary）が既にあるプロジェクト**では、設計案を出す前に次の 3 点を問う。強制度は `.shirokuma/rules/ddd-enforcement-gradient.md` が正本（設計フェーズの構造・INV は**ソフト観点だが必須で問う**）。

- **BC 帰属**: この変更はどの Bounded Context に属するか。既存の BC のどれにも収まらないなら、**それ自体が決定事項**（下記の橋渡しへ）。
- **集約境界**: 触る集約はどれか。1 つの操作が複数の集約をまたぐなら、整合性をどちらに寄せるか。
- **不変条件（INV）への影響**: 既存 INV を壊さないか。新しい INV を導入するなら、それを守る場所はどこか。

**答えを設計案の中に書く**。「該当なし」も答えなので、問うたうえで該当なしと書く（問わなかったのか該当しなかったのかを、次に読む人が区別できるようにする）。

### 導出できないときは決定へ回す

3 点のいずれかが**正本から導出できない**なら、設計者がその場で決めない。`concept-gap-to-adr` に従って ADR の候補として起票する。

- 「どの BC か分からない」は選択の問題ではなく**正本の欠落**である。BC 帰属が未定義のまま症状だけを潰しても、同じ形が再発しうる。
- 導出できないまま設計を進める判断もありうるが、その場合は**進めたことを設計案に明記する**（「BC 帰属は未確定のまま進めた」）。黙って進めると、次の人には導出できたように見える。
