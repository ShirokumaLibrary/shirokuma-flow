# レビューゲート（R1 / R2）の詳細手順

`review-flow` の **R1（並走レビュー）→ R2（差し戻し判定）** の実行手順と、`gate` verb を呼ぶすべての段に共通する機械契約を持つ。

**この 2 段の Why は、PR を唯一のレビュー面にして、同じ差分を PR 作成前と作成後の 2 回精読する形を作らないこと。**

**読むタイミング**: **R1 に入る前に必ず Read する**。SKILL.md 側は本ファイルを指すだけで、条件・値域・分岐の逐語は持たない。

**射程外**: 欄名・値域・限界の逐語は本ファイルにも持たない——正本はコード内のレジストリ 1 箇所で、実行時に `shirokuma-flow gate vocab` / `shirokuma-flow gate limits` が返す。

## 対象の確定（R1 の前提）

**本 2 段の対象は PR である**（Issue ではない）。次の 3 値を **R1 の委任前に確定**し、以後の段はこの値だけを使う（取り直さない）。

- **`<base>`**: `shirokuma-flow pr show <pr#>` が返す **base ブランチ**。**外部由来の値として扱う**（下記「コマンド行へ値を差し込む前に検査する」の対象）。
- **`<head sha>`**: **checkout 済みの head ブランチに対する `git -C '<作業ツリー絶対パス>' rev-parse HEAD`** から取る。再レビューの増分母集団（R2）と、レビュー worker への差分基準の裏取りに使う。**`pr show` / `pr checks` からは取らない**——`pr show` が返す `head` は**ブランチ名**であって sha ではない。`pr show` の `head_oid` は**リモートの PR head の完全 sha** を返すが、R1 の 3 本が母集団にするのは checkout 済みの作業ツリーなので、未 push のコミットがある回はローカルの HEAD と食い違う（出所をローカルに揃える）。`pr checks` は **`head_sha` を返さない**（実測: `pr checks` の JSON にキーが無い。`head_sha` を持つのは `pr logs` で、取得不能時は null ではなく throw する）。**値域 `^[0-9a-f]{7,40}$` を差し込み前に検査してから**（下記「コマンド行へ値を差し込む前に検査する」）**R1 の 3 本の委任ブリーフへ渡す**。**Why**: ブランチ名を sha として渡すと値域検査で必ず落ち、R2 の増分母集団は一度も成立しない（**倒れる向きは fail-closed**——全差分へ倒れるので安全側だが、節約の機構が死んだまま気づかれない）。
- **`<issue#>`**: `pr show` の **linked issues** から取る。結果ファイルの**標準命名**（`.shirokuma/tmp/security-review-<issue#>.md` / `code-review-<issue#>.md` / `asset-safety-review-<issue#>.md`）に使う。
- **linked issues が空の回は Issue 番号を解決できない**ので、結果ファイルのパスを組めない。**その回は R1 を委任せず停止して報告する**（**fail-closed**。適当な番号へ丸めない）。

## gate の呼び方（R1 / R2 に共通・機械契約）


**機械判定は読み取り専用 verb `shirokuma-flow gate <サブコマンド>` が行い、本手順は呼び出しと結果による分岐（routing）だけを定める。** 判定ロジック・欄名・値域・限界の逐語は本手順に持たない（正本はコード内のレジストリ 1 箇所で、実行時に `gate` が返す）。

- **判定は JSON ＋ exit code の二重で返る**。JSON の `complete: true` が「検査が最後まで到達した」証拠、`version` が判定を出した CLI 版、`scope` が何を母集団に見たかである。exit code は **0（完走・記録や分岐を要する所見なし）／ 2（完走・所見あり＝`pass: false`）／ 1（判定不能＝`ok: false`）** の 3 値。
- **判定不能を pass に読まない**。JSON に `complete` が無い回・`ok: false` の回・verb を解決できない回（`unknown command`・コマンド不在）は、いずれも **`判定不能` であって「指摘 0 件」ではない**。**非 0 を一律「検査が何か言った」と読まない**——`unknown command` も非 0 で返る。
- **判定不能の回の routing（fail-closed）**: その段の pass を前提にする分岐（3 本目の委任・再委任・書き直し・継続委任）へ進まない。記録行は分岐に依存しない必須出力なので**書く**が、**値域内の値へ丸めない**——丸めると「測って良性だった回」と「測れなかった回」が PR 本文上で同じ見た目になる（fail-open）。当該記録行の値域に判定不能を表す値があるならそれを使い、無いなら `判定不能（<理由>）` と書いて直下の字下げ行に理由を残す。**`<理由>` には「引けなかった verb 名」ではなく、その回に判定を出せなかった事由を書く。** **値域へ判定不能の値を足すかはレジストリ（コード）側の変更であり、本手順では決めない。**
- **欄名・値域は `shirokuma-flow gate vocab`（`--profile` / `--field`）、検査の限界は `shirokuma-flow gate limits --sub <サブコマンド>` で引く**（`--sub` は `gate` のサブコマンド名であって Issue 番号ではない）。値域の照合は `gate vocab` が返す `matching` の方式で行い、**部分一致で走査する消費者を作らない**（値域の語どうしに包含があるため過検出側へ倒れる）。
- **profile 名は段名と別である**（欄検査は `--profile implement-4a`・記録行検査は `--profile implement-4d-2`）。**正本はレジストリの id** であって段名ではないので、段名の変更に追随させると正本が 2 つになる。**この食い違い（段名 R1 / profile 名 `implement-4a`）は受容する**——読み手は profile 名を段名の宣言として読まないこと。
- **判定 JSON の `build` ブロック（`sourceMatch` / `dirty` / `degraded`・欠落した回の読み方を含む）の読み方は `shirokuma-flow gate limits --sub limits` の `H19` が正本**（ここに写さない）。**`stale` を名乗った回・`build` ブロックそのものが無い回は、その判定を現ソースの値として読まない。** **`stale` と `build.dirty: true` が同時に立つ回は、その判定を根拠に使わない。** **`build.dirty: null`（焼いていない）は、再現性の担保が無い側として `build.dirty: true` と同じに読む。**
- **検査の呼称（3 語・機械契約）**: 呼称は**検査した主体が判定対象を作った主体と別か**で決まり、使ったツールでは決まらない。
  - **機械検証**: 判定対象を作った主体とは**別の主体**が検査した段（`gate` が worker の結果ファイルの欄を検査する R1）。
  - **自己検査**: **同一主体が自分の出力を検査する**段（orchestrator が自分で書いた記録行に対し自分で `gate summary` を引く段）。
  - **自己申告**: **誰も検査しない**最下段（`gate` が出した判定を PR 本文へ書き写す転記・記録行の直下の字下げ行）。
  - **`gate` を呼べば機械検証になるのではない**——判定を出すプロセスが別でも、母集団を用意して結果を写すのが同じ主体なら、その段は自己検査であり転記は自己申告である。**倒れる向きは fail-open**（この呼び分けを検査する機械段は無い）。

### コマンド行へ値を差し込む前に検査する（`gate` を呼ぶ全段に共通・この経路の唯一の防御）

`gate` が持つ値域検査は**プロセス内**で走るので、**呼び出し側がコマンド行を組み立てる段には一切効かない**——注入はシェルの**構文解析時**に済み、`gate` が起動するのはその後だからである。したがって**外部由来の値をコマンド行へ置く前に、呼び出し側が値域を確かめる**。

- **対象と条件**: **`--base` に渡す base**（`pr show` が返す base ブランチ＝**GitHub 由来＝untrusted**）は、`gate vocab`（**`--field` では返らないので引数なしか `--profile` で引く**）が返す `baseRefAllowlist` の条件（許可文字 allowlist・`-` 始まり禁止・単一行）をすべて満たすこと。**`--file` / `--report` の絶対パスに埋め込む `<issue#>`** は `^[0-9]+$` に一致すること（**Issue 番号が数値であることをリポのどこも保証していない**——「絶対パスだから安全」ではなく、安全なのは**検査した値だけ**である）。**`--criteria` に渡す判定基準ファイルのパス**（`gate token` が返した値）は `'` を含まないこと。**`<head sha>`**（`git rev-parse HEAD` で取り、R1 の委任ブリーフへ載る）と **`<前回 head sha>`**（R2 の増分母集団で 3 本の worker が `git diff` のコマンド行へ載せる・出所は前回のコードレビュー結果ファイル＝**LLM が書いた untrusted な Markdown**）も同じ扱いで、`^[0-9a-f]{7,40}$` に一致すること。**`<前回 head sha>` を名指しするのは、出所が `pr show` 系ではなく結果ファイルだからである**——出所が違っても消費点（コマンド行へ載る）が同じなら同じ検査が掛かる。**この列挙は閉じていない**——`--worktree` に渡す作業ツリーの絶対パスのように**ここに挙げていない値も、コマンド行へ載せる以上は冒頭の一般文の対象**である。
- **満たさない回は verb を引かない**。base が満たさない回は R1 を委任せず停止して報告し、`<issue#>` が満たさない回は結果ファイルのパスを組めないので同じく R1 を委任せず停止して報告し、`--criteria` の値が満たさない回は 3 本目（`asset-safety-review-worker`）を委任しない。`<head sha>` / `<前回 head sha>` が満たさない回は増分を取らず**全差分へ倒す**（**fail-closed**）。いずれの回も、その段を判定不能として PR 本文の記録行に残す。
- **引用方式を選ぶだけでは足りない**——選んだ方式を破る 1 文字が必ずある（`'` は git の ref 名で禁じられていない）。差し込み前の検査を通したうえで、なお**単一引用符で囲んで渡す**（多層防御。`"` にすると `$(…)` / `` `…` `` が評価される）。
- **免除は経路単位で引く（値単位ではない）。分けるのは渡し方（チャネル）ではなく消費のされ方**: **受け手が Read するだけで終わる経路は本条の対象外**、**受け手がその値をコマンド行へ載せる経路は対象**である。**「委任ブリーフへ渡すだけ」は免除の根拠にならない**——`gate token` が返す判定基準ファイルのパスは 3 本目の worker が Read するだけなので免除に当たるが、**同じブリーフで渡す `<base>` は 3 本の review worker が `git -C <作業ツリー絶対パス> diff <base>` としてシェルへ載せるので免除にならない**（**3 本とも差し込み前検査の条項を現に持っているが、それを機械強制する層が無い**——散文の規律だけなので守らなかった回は静かに通る＝**fail-open**。この未解決点は `shirokuma-flow gate limits --sub asset-delay` が返す）。**「担い手が居ない」と読まない**——条項は在る。**`ok` は「差し込んで安全」を意味しない**（verb 自身が `guarantees.shellSafe: false` を返す）。**値域を絞ることで塞がない**——塞ぐのは受け渡しの側である。
- **倒れる向き**: 本条を落とすと **fail-open（注入方向）**——`gate` の返り値だけを見ている限り異常は出ない。厳しすぎる側は判定不能として記録に残る（**fail-closed**）。**この検査を機械強制する層は無い**（**fail-silent**）。

## R1. 並走レビュー

`security-review-worker`（3a コード脆弱性）と `code-review-worker`（バグ検出＋品質＋着地した What との照合）を**並走で委任**する。ブリーフには上記「対象の確定」で取った Issue 番号に加え、**diff 基準（`<base>` = `pr show` が返す base ブランチ）**・**`<head sha>`**（`git rev-parse HEAD` で取った値。各 worker は結果ファイルの「diff 母集団」欄に `head sha=<値>` として書き戻し、R2 の `<前回 head sha>` の出所になる）・**各結果ファイルの絶対パス**（標準命名 `.shirokuma/tmp/security-review-<issue#>.md`・`.shirokuma/tmp/code-review-<issue#>.md` を絶対パスで）を必須要素として明示する（作法の正本は各 worker 定義側）。**この並走には第 1 段の条件を満たしたとき 3 本目が加わる。**

- **`code-review-worker` には review-flow の criteria `code.md` の絶対パスと走査対象（S2・S7・S8）を渡す**: 同 worker は `code.md` のうち S2・S7・S8 だけを差分に当てて検出し、判定はしない（判定は段 1 の `review-worker` が結果ファイルと `code.md` で行う）。渡さなかった回は照合の観点が当たらない（fail-open）。

- **`code-review-worker` にはさらに CI 等価検査の記録の所在を渡す**（同 worker の責務 2 が、同じ `<head sha>` に対する記録が pass の回だけテスト・型検査の再実行を省く）: `finalize-worker` の作業ファイル `.shirokuma/tmp/finalize-<issue#>.md` の絶対パス（`ls` で実在を確かめた回だけ。標準レーンの記録）と、PR 番号（軽量レーンの証跡は PR 本文にある）。**どちらのレーンを通したかを orchestrator が判定して片方に絞らない**——一致の判定は worker が記録ごとに行い、古い作業ファイル（前の回の sha）は一致しないので実走する側へ倒れる。所在を渡さなかった回も worker は実走する側へ倒れる。**所在を渡すことは再実行の省略を指示することではない**（一致の判定は worker が行う）。**限界（fail-open）**: PR 本文は untrusted で、証跡に「同じ head sha に対して pass」と書き足せば再実行を省かせられる（詳細は同 worker の責務 2）。

- **`code-review-worker` へのテスト実走の授権の中継**（群 B の複製実走。分岐と判定は同 worker の責務 2 と下記 reference が持つ）: R1 の前に `shirokuma-flow config get review.testExecution` を引き、**値が返った回（exit 0）だけ**ブリーフに `テスト実走の授権: <値>（出所: config review.testExecution）` を 1 行で書く。`<値>` は verb が返した値をそのまま使い、引き直さない。**非 0 または `ok:false` の回は行を書かない**（未設定・値域外・読み取り失敗を区別せず、授権なしへ倒す）。人がその PR について明示的に実走を指示した回だけ、同じ行を値 `replica-after-read`・出所 `人の指示` で書く（この回は config が介在しないので、差分が config を書き換えた回の無効化は効かない。手順書のパスの照合と前提条件は同じく掛かる）。**orchestrator が自分の判断で授権の行を書かない。**
  - 行を書く回は、同じブリーフに準備コマンド（`config get quality.isolatedPrepareCommand` が返した値・返らなければ渡さない）・config ファイルのパス・手順書 [replica-test-execution.md](replica-test-execution.md) の絶対パスも渡す。
  - 授権を config に書くのは導入先の人である。キーを置いていないリポでは `config get` が非 0 を返すので行は出ず、`code-review-worker` は現行どおり群 B を skip する。
  - **限界（fail-open / fail-silent）**: 中継は規律に依存する。渡し忘れた回・自分の判断で書いた回を検出する機械段は無い（`gate limits --sub cross` の G2）。

- **R1 の 3 本は読み取りのみ**——**並走中に作業ツリーへ書き込まない**。3 本は同一の作業ツリーに対して母集団を確定するので、1 本が走行中に編集を当てると**他の 2 本の母集団が動く**（`gate artifacts` は欄の存在と値域しか見ないので緑のまま通る＝**fail-silent**）。**Nit の直接修正は R1 の外＝下記「R1b」で行う。**

- **worker 定義の作例に現れる裸の `-C <…絶対パス>`（例: `git -C <作業ツリー絶対パス> diff`）はプレースホルダであって値ではない**。**実値を置く形は、review worker 定義（code-review / security-review / asset-safety-review）の「`-C` の値は literal のプレーンパスで書き」の条項が正本**で、既定はプレーンパス・`-C` の値を空にしない（理由も同条項が持つ。本ファイルでは形を再定義しない）。**本項は orchestrator が読む文書にあり、worker には委任ブリーフを経由したときだけ届く。**

- **3a の適用範囲——どの差分種別を対象とするか——の正本は [[sast-operation]] の「検出層の分担」節にある第 3 層 LLM レビュー（3a）の項**。本手順は適用範囲を再宣言しない。**指し先を解決できない回は、確認できないことを理由に見送らず委任する側へ倒す**（fail-closed）。
- **「R1 を通った」が保証しないこと（射程の正本は `shirokuma-flow gate limits --sub cross` の該当項・ここに写さない）**: **R1 の 3 層はいずれもテストを実走しない回がある**ので、**テストに関する主張の根拠は実装 worker の自己検査であって R1 の機械検証ではない**。よって ①**「レビュー 3 本 pass」をテストの裏取りを含むものとして読まない**——実走の有無と理由はコードレビュー worker が 実走検証（`runtime-verification`） で必ず記録するので、**`gate verdict` の `fields[]` からその値を読んで判断する**（skip は pass ではない。**この値は判定を動かさない**ので、記録が欠けても `fields[]` に判定不能を表す値が載るだけで機械は止まらない＝**fail-open**） ②**実装 worker の実走記録を人ゲートを外す条件に使う回は、R1 の pass をその代替に数えない** ③**群 A とパス名の一次判定は緩めない。群 B の skip を外すのは、授権と `code-review-worker` 責務 2 の連言が揃った回だけ**（①は授権の無い回についてそのまま残る）。

**第 1 段（無条件に引く・3 本目の委任可否を決める）**: R1 の最初に `shirokuma-flow gate token --kind criteria-path` を引く。**判定基準ファイルを宣言する config キーを verb が自分で読む**ので、値は orchestrator のシェルを一切通らない。

- **`verdict` が `ok` の回だけ** `asset-safety-review-worker` を 3 本目として並走に加える。`unset`（キー未宣言＝この段を持たないプロジェクト）・`empty`（空値）・`violation`（値域違反）の回は委任しない。**`violation` は良性の劣化ではなく入力の異常として扱う**——良性の未委任と同じ並びに置かず、PR 本文に明示する。**違反した値そのものは記録行にも PR 本文にも書かない。**
- **委任ブリーフへ渡すのは verb が返した値（`valueRaw`）そのもの**とし、**`config get` を引き直さない**——2 回読むと「検査した値」と「委任へ渡した値」が同一である保証を誰も持たなくなる（fail-open）。**返った値を別のパスへ読み替えない。** **`ok` 以外では値が返らないので、その回はブリーフを組めず 3 本目を委任しない**（fail-closed）。
- **委任ブリーフの必須要素（6 つ）**: 対象 Issue 番号 ／ **diff 基準（`<base>`）**（他 2 worker と同一値） ／ **`<head sha>`**（他 2 worker と同一値） ／ **結果ファイルの絶対パス**（標準命名 `.shirokuma/tmp/asset-safety-review-<issue#>.md`） ／ **判定基準ファイルのパス**（`valueRaw`） ／ **作業ツリーの絶対パス**。加えて「**動作確認・テストで実 GitHub に書き込まない**」と**当該 worker scope の規範要旨**を同じ規約で明示する。
- **段名を渡すのは 3 本目だけ**。**どのフェーズでも「3a / コードレビュー」の 2 段名は渡さない**（review-flow は `gate verdict` で判定を導出するので、finalize へレビュー結果を転記させる経路そのものを持たない）。**渡さない理由は「finalize に転記段が無いこと」である**——finalize の雛形にこの段名の行が無いことを、渡してよいことと読み替えない。
- **記録行（0 / 非 0 の両分岐で書く必須出力）**: 第 1 段の結果を **PR 本文の最上部（BLUF）**へ **1 行**残す（`shirokuma-flow pr record <pr> --field asset-safety-review --value <v>`・状態は触らない）。**接頭辞と値域は `gate vocab --field asset-safety-review` が正本**で、**渡す値は verb が返す `recordLineValue` をそのまま使う**（手順側で値を選び直さない）。**行の有無を分岐に依存させない**——依存させると、行が無い状態が「記録を落とした」のか「書かない仕様」なのか区別できない。**書き落としを検知する機械段は無い**（PR 本文を母集団にする lint が無い＝**fail-silent**。値域外を渡した回だけは `pr record` が exit 1 で書き込みを止める）。**本欄は実装サマリー側（4d-2 の `gate summary` が検査する行）にも同じ id で存在する——正本は本行（PR 本文側）で、実装サマリー側は PR 作成前の記録にとどまる。両者が食い違ったら PR 本文側の値を採る。**
- **本段は 3 本目の判定値を差し戻し判定に使わない**（R2 の差し戻しは別の判定行だけを見る）。**この宣言の対象は 3 本目の判定行**（配布物 AI 安全性の判定値（`asset-safety-verdict`））であって、結果ファイルが持つ欄・所見すべてではない——**人への受け渡し経路は一般にこの宣言の対象外**である。**経路を列挙して切らない**（列挙で切ると、後から足した受け渡し経路だけが静かに無効化される）。
- **3 本目の第 2 軸欄（`weakening-diff`・値域は `gate vocab --field weakening-diff` が正本）による routing**: R1 の後に引く `gate verdict`（SKILL.md 段 1）の `fields[]` の `weakening-diff` の値を読んで渡し先を決める。**4 値のうち 2 値——該当かつ不当の疑いを表す値と、変更前の判定基準を取得できなかったことを表す値——と、`gate verdict` が出す委任したが結果なしを表す値の 3 つが出た回は人ゲートへ回す**（渡し先は R2 が既に持つエスカレーションで、**新しい停止点・新しい上限・新しい報告面は作らない**）。残る 2 値は `pass` のまま先へ進め、「結果ファイルが無い」を表す値（3 本目を委任しなかった回）は routing に入らない。判定行は動かさない。**欄名も値も本手順に逐語で持たない。** **判定不能を表す値も人ゲートへ入れる**——「緩める向きだったか」を機械にも worker にも決められない回なので、**値域のすべての値に消費者を持たせ、素通りする値を残さない**。
  - **値の読み出し**: 値は `gate verdict` の `fields[]`（role が `asset`・field が `weakening-diff` の要素の `value`）から取る。**結果ファイル（Markdown）から値を読み取らない**——判定値は asset worker が `detector record` で検出器記録へ書き、`gate verdict` が値域を照合して返す。
  - **倒れる向き（申告）**: 3b を委任した回（`--asset-expected`）に asset の記録が無い・head の entry が無い・値域外の回は、委任したが結果なしを表す値になって**人ゲートへ回る**（止まる側・可用性を落とす向き。SKILL.md 段 1 の再委任の枝と同じ選択）。**`--asset-expected` を付け忘れた回は非該当に倒れて人ゲートへ回らない**（**fail-open**・`gate limits --sub verdict` の N8 ③）。**記録値の真偽は見ない**（値域内の値なら、判定の結果かどうかは見ない＝**fail-open**）。
- **共有上限を消費した回はその事実も PR 本文に残す**（`shirokuma-flow pr record <pr> --field shared-limit-consumption --value <v>`・状態は触らない。**接頭辞と書き方は `gate vocab --field shared-limit-consumption` が正本**で、消費した回数と段を書く）。**この行は消費した回だけ書く**（他の記録行と違い分岐に依存する——「消費しなかった」ことは R1 を通れば常に真なので、行の不在が判定不能になる形にならない）。

**結果ファイルの実在検証と欄検査**: 委任した各 worker の報告受領後、`shirokuma-flow gate artifacts --profile implement-4a --file security=<絶対パス> --file code=<絶対パス>` を引く。**3 本目を委任した回は `--file asset=<絶対パス>` と `--asset-expected` を併せて渡す**——委任可否は第 1 段で確定しているので、**同じ入力から対象本数と記録行の値の両方が導かれ**、フラグと本数が独立に食い違う経路が消える。

- **読むのは 2 つ**: `files[].exists`（結果ファイルの実在。worker の報告を鵜呑みにせず verb が自分で確かめる）と `findings[]`（欄ごとの `missing` / `empty` / `out-of-range`）。**`exists: false` と「欄が無い」は別フィールドで返る**ので、不在と欠落を取り違えない。
- **この検査が見るのは欄の存在・値の非空・閉じた値域を持つ欄の値域適合だけ**であって、**母集団が実際に測られたことの検査ではない**。後続はこの pass を母集団の正しさ・版の同定の正しさの保証と読んではならない。**何を見ないかの全件は `shirokuma-flow gate limits --sub artifacts` が返す。**
- **欠落時の経路（新しい停止点を作らない）**: `exists: false`・`missing` / `empty` / `out-of-range` のいずれも同じ扱いで、**該当 worker への R1 再委任 1 回**で回復を試みる（ブリーフに `<base>`・作業ツリー絶対パス・欄名を明示し、欄名と値域は `gate vocab --profile implement-4a` から引いて渡す。**その値を「間接証拠として測って書く」旨も逐語で添える**——**実行時の worker 定義がリポジトリ現行版とは限らない**ため）。**値域違反も欠落と同じ経路に合流させ、専用の停止点も専用の上限も作らない。** **該当 worker は R1 で委任した全 worker が対象。** `code-review-worker` へ再委任する回は、R1 で渡したテスト実走の授権の行と付随する値も同じ形で渡す（R1 で行を書かなかった回は書かない）。 再委任は R2 と**同じループ上限 2 回**を共有する。**共有上限が既に尽きている場合は再委任せず、欠落したまま先へ進める**（欄欠落は人の判断を要する指摘ではないため人ゲートへは回さない）。その回は PR 本文へ「> 注記: diff 母集団欄が欠落しており、本レビューの対象母集団は未確定。」を付す（`pending` で止めない）。
  - **逐語転記フォールバック（再委任 1 回で回復しなかった回・結果ファイルそのものが無い回）**: **検出器記録には適用しない**（転記の対象は結果ファイル〔Markdown〕だけ。orchestrator が判定値を記録へ書くと検出器と記録者が分かれなくなる——記録の無い役割は SKILL.md 段 1 の再委任の枝で扱う）。**orchestrator が該当 worker 返答の全文を、R1 でブリーフに渡した絶対パスの結果ファイルへ逐語転記する**（**転記の対象は R1 で委任した全 worker の結果ファイル**。冒頭に固定注記「> 注記: worker が結果ファイルを生成しなかったため、orchestrator が worker の返答レポート全文を逐語転記した。」を付す）。転記後は既存の経路へ合流させ **`pending` で止めない**。**Why**: worker が Critical を検出しても結果ファイルの書き出しに失敗すれば所見は誰にも読まれず消え、判定行は `PASS` に落ちる——**倒れる向きは fail-open** なので、返答テキストという唯一残っている材料を下流が読める形へ落とす。**この転記は review-flow の責務である**（`implement-flow` 側の手順は持たない）。

## R1b. Nit の直接修正を当てる（R1 の並走の外・条件付き）

R1 の並走中は 3 本とも読み取りのみなので、`code-review-worker` が挙げた Nit はこの段で当てる。**新しい停止点も新しい上限も作らない。**

- **発火条件（3 つすべてを満たす回だけ）**: ① **R1 の 3 本すべての結果ファイルが実在し `gate artifacts` を通った後**であること ② `gate verdict` の `fields[]` の Nit 直接修正の欄（`nit-direct-fix`）が**候補ありを表す値**（値域の正本は [../templates/report.md](../templates/report.md)）であること ③ **同じ `fields[]` の修正推奨が「なし」であること**。**修正推奨「あり」 の回は R1b を単独で走らせず、候補は R2 の是正連鎖（coding-worker → finalize-worker → commit-worker）へ合流させて一緒に反映する**（R2 の「2 つの経路を独立に走らせない」条項と対）。**Why**: ③ が無いと Nit の反映が R2 の前に単独で push され、同じ回に R2 が「連鎖の中で一緒に push する」と定める条項と両立しない（読み手ごとに実行が割れ、finalize → commit の往復が 1 回増える）。
- **やり方**: orchestrator は **同じ `code-review-worker` の続き**として適用を指示する（**新規委任ではない**——列挙した Nit とその判断は当の worker の文脈にしか無く、別の主体に渡し直すと「何を当てるか」の判断がやり直しになる）。手順・当ててよい範囲・除外の正本は `code-review-worker` 定義の該当責務。
- **適用後（orchestrator が機械段を直接回して commit・push する・`finalize-worker` → `commit-worker` へ委任しない）**: 本段に入るのは 修正推奨「なし」 の回だけ（発火条件③）で、残る仕事は機械段と commit・push だけである——どちらも結果が終了コードと出力で機械的に検証でき、実行者が誰でも同じ結果になるので委任しない（`implement-flow` 軽量レーンと同じ形）。
  - **何を回すかの正本は `finalize-worker` 定義の全体**（報告表の全段・各段の手順・「CI 等価検査」節の `quality.localVerifyCommand` の同一性確認を含む）。**ここへ段を写さない**——写すと、定義に段が足された回にこの経路だけ古い段で回る。**orchestrator は同定義を Read して、その手順を自分で実行する**（定義が「本 worker」と書く主体を自分に読み替える）。この回の実行主体は orchestrator なので、**同一性の確認も orchestrator 自身が CI 等価検査の直前に行う**（下記 R2「入口はもう 1 つある（`quality.localVerifyCommand` の値そのもの）」の「確かめるのは実行主体」と同じ扱い。確かめられない・同一でない回はその段を実行せず、その事実を報告して同節の人ゲートへ回す）。
  - **commit・push**: 機械段がすべて `pass` / `skip(理由)` で終わった回だけ、作業ツリーの変更を commit し（書式は注入される rule `commit-style`）、head ブランチへ名前付きで push する（`git -C '<作業ツリー絶対パス>' push origin '<head ブランチ>'`・ブランチ名は「コマンド行へ値を差し込む前に検査する」を通す）。**`fail` が 1 つでもあれば commit・push せず、当てた Nit を戻して列挙側へ回す**（壊れを検出できるクラスに限るという R1b の前提が崩れたため・**fail-closed**）。
  - **証跡**: 回した段の実行コマンド・終了コード・出力の要点と、push 後の `検査対象 head sha:`（`finalize-worker` 定義の同名の行と同じ書き方）を、段 2 のレビュー結果コメントに残す。**回さなかった段は回さなかったと書く**（「検査が実行されなかったこと」を緑と読ませない）。**倒れる向き**: 証跡は orchestrator の自己申告で、回したかの裏取りは無い（**fail-open**・軽量レーンの証跡と同じ）。報告表（`finalize-worker` の作業ファイル）は作られないので、報告表に対する機械検証の母集団はこの経路では不在になる（**fail-silent**・軽量レーンと同じ）。
- **再レビューは起こさない。** **根拠**: 除外規則が外すのは**プラグインのソースだけ**で、R1b がそれ以外の 3b の allowlist 該当ファイル（`.shirokuma/rules/**` など）へ Nit 修正を当てた回は、**3b の判定を受けないまま**この経路に乗る（**倒れる向きは fail-open**・本節では塞がない）。3a / コードレビューの母集団に入るのは**レビュアー自身が挙げた Nit の修正だけ**で、壊れは finalize の機械段（テスト・lint・型）が検出する。
- **この根拠が成り立たない回——除外に当たる編集が混じった回——は R1 へ戻す**（**fail-closed**）。**倒れる向きは fail-open**: 混じったかどうかを判定する機械段は無く、当てた側の申告（Nit 直接修正の欄（`nit-direct-fix`）の対象ファイル列挙）に依る。
- **判定記録（SKILL.md 段 2）は push の後に書く**: `head-sha` には push 後のリモートの PR head、`reviewed-sha` には R1 の `<head sha>` を書く（欄名は `shirokuma-flow gate vocab --profile review-record`）。**書く前に**、`git -C '<作業ツリー絶対パス>' diff --name-only --end-of-options '<reviewed sha>' '<head sha>'` のファイル集合を、コードレビュー結果ファイルの Nit 直接修正の欄（`nit-direct-fix`）が列挙した対象ファイルと突き合わせる（2 つの sha は完全 sha の値域 `^(?:[0-9a-f]{40}|[0-9a-f]{64})$` を通してから置く——「コマンド行へ値を差し込む前に検査する」の `^[0-9a-f]{7,40}$` より狭い。判定記録を読む側〔`pr checks`〕が受けるのは完全 sha だけで、短縮 sha は形式外として `runBy:"human"` に倒れ、64 桁〔SHA-256 のリポジトリ〕は `{7,40}` では落ちるため。検査を通らない回は突き合わせをせず `head-sha` に `reviewed-sha` と同じ値を書く——それも完全 sha でなければ記録は形式外として `runBy:"human"` に倒れる）。**欄に無いファイルが 1 つでも差分にあれば、`head-sha` に push 後の sha を書かず `reviewed-sha` と同じ値を書く**——`pr checks` の `merge` は `runBy:"human"` になり、人ゲートか再レビューへ倒れる（**fail-closed**）。**R1b を通していないのに 2 つの sha が違う回**（R1 の後に別の push があった等）も同じ突き合わせに当て、欄が候補なしを表す値なら差分がある時点で同じ値を書く。**倒れる向きは fail-open**: 照合するのはファイルの集合だけで、同じファイルの中の Nit 以外の行が変わっても通る。欄はレビュアー自身の申告である。

## R2. 差し戻し判定

`gate verdict` の `fields[]` で修正推奨が「あり」（＝**Important** がある回。Nit だけの回は 修正推奨「なし」 になる＝写像の正本は [../templates/report.md](../templates/report.md)）がある場合、`coding-worker` に修正を委任する。**ループ上限は 2 回**——収束しなければ、そこで再レビューの巡回を打ち切る（(b) 地点の定義は [[confirmation-style]]「確認モードの解決と中継」節。**この打ち切りは確認モードの有無で振る舞いが変わる**——`guided` は現状の指摘と結果ファイル `.shirokuma/tmp/code-review-<issue#>.md` の絶対パス・収束の記録行（欄 id `fix-convergence-record`）の値を PR 本文に添えて止まり人に判断を委ねる〔確認後に打つ verb は、指摘を受け入れて進めるなら段 1 以降の判定器委任、修正を続けるなら `coding-worker` への再委任〕。自律の回はここで止まらず、判定行が `NEEDS_REVISION` のまま残るため merge 条件①が不成立になり PR は `In progress` に留まる——未収束・merge 不可であることを報告して当該進行を終端する）。**終端するのは段 1（判定器）が判定行 `NEEDS_REVISION` を出し段 2 で PR へ記録した後であって、その手前で終端しない**（判定行が無い回も merge 条件①は不成立だが、持ち越しの裏打ちは判定行の側に置く）。修正推奨が無い、または security-review のみの指摘なら段 1（判定器）へ進む。下記の各入口も同じ渡し先を使い、**新しい停止点も新しい上限も作らない**。

2 つ目の入口は、確認モードの停止（SKILL.md 段 3）で人が差し戻しを選んだ回である（人の選択と指摘として扱う範囲は同段 3 の箇条が正本）。判定が PASS でも、人の指摘を Important と同じ扱いで下記の連鎖へ渡す。人の指摘が状態遷移・BC の決定など `coding-worker` の制約に当たる部分は、`coding-worker` が実行せず返すので、orchestrator が人へ戻す。

**是正 → 再レビューの連鎖（3 worker・この順に前景で）**:

1. **`coding-worker`** へ是正を委任する（Important を渡す。**同じコードレビュー結果ファイルの
   `fields[]` の Nit 直接修正の欄（`nit-direct-fix`）が候補ありを表す値なら、その候補（改善提案表の運搬体）も同じ委任ブリーフへ
   渡す**——R1b 発火条件③がこの回を R1b 単独では走らせず本連鎖へ合流させると定めるので、
   合流先の受け手をここで明示する。**渡すのは列挙された Nit 候補と
   結果ファイルのパスであって、「何を当てるか」の再判断をさせるものではない**——判断は
   `code-review-worker` が既に済ませている（R1b が新規委任を禁じた Why と同じ）。この合流は
   共有ループ上限を**消費しない**——上限を消費するのは Important 起因の巡と
   欄欠落の再委任だけで、Nit の合流はその巡に相乗りするだけだからである。人が起点の巡
   （確認モードの停止で人が差し戻しを選んだ回）も上限を数えない——その巡の後は必ず人のところへ戻るからである。その後に
   AI の Important で回る巡は、同じ共有カウンタへ足す（引き継ぐ）。
2. **`finalize-worker`**（機械段）を通す。
3. **`commit-worker`** で commit・push する。
4. **再レビューは増分だけ**——**`<前回 head sha>` 以降の増分**を母集団にする。**出所は前回のコードレビュー結果ファイルの「diff 母集団」欄の `head sha=` 行**（3 本の review worker はこの行を必須で書く）。上の 3 worker の委任ブリーフに **`<前回 head sha>`** を渡し、**`git -C '<作業ツリー絶対パス>' diff --end-of-options '<前回 head sha>'`（作業ツリー対コミット）を母集団にする**よう指示する。**`git diff A..B` のコミット範囲指定は使わない**——コミット済み差分だけを比較して**未コミット分が漏れる**形で、3 本の worker 定義がいずれも禁じている（指示と定義を正面衝突させない）。**欄が無い回・値域検査（`^[0-9a-f]{7,40}$`）を通らない回は全差分へ倒す**（**fail-closed**。節約は効かないが安全側）。**検査は渡す側（本手順）と受け取る側（worker）の両方で掛かる**——3 本の worker 定義の差し込み前検査条項は「名指しした値で列挙は閉じていない・消費点（その値をシェルのコマンド行へ載せる箇所）で切る」と定めているので、**`<前回 head sha>` はその条項に既に含まれる**（受け側へ新しい条項を足さなくても掛かる）。**前巡の Important は次巡へ逐語で持ち越す**——3 本の委任ブリーフに前巡の Important（場所・要旨）を逐語で渡し、各 Important の**解決可否を結果ファイルに明記させる**。**当該指摘箇所は増分の外でも再確認する**（増分だけを母集団にすると、是正が指摘箇所を外した回に未修正のコードが 2 巡目の母集団へ入らず 修正推奨「なし」 → PASS へ通る＝**fail-open**。増分縮小とこの持ち越しは対で働く）。**解決可否を検査する機械段は無い**（欄はレジストリ外＝fail-silent）。人が起点の巡は、人の指摘も同じ形で逐語で持ち越す（是正が指摘箇所を外しても AI が PASS に通しうるが、その回も確認モードの停止で再び人へ戻る）。
   - **base を取り込んだ後の増分再レビュー**（PASS の記録が head の移動で失効し、`pr checks` が本 skill の起動を案内した回を含む）: 取り込みコミットの差分をそのまま母集団にすると **base 側から入った変更**まで入る。**母集団は次の 2 つの和集合に限る**——①`git -C '<作業ツリー絶対パス>' log --no-merges --format= --name-only '<前回 head sha>..<現在の head sha>'` のファイル集合（PR 自身の非 merge コミットが触ったファイル）②取り込みコミットの衝突解消で変わったファイル（`git -C '<作業ツリー絶対パス>' diff-tree --cc --name-only '<取り込みコミット>'`＝両親のどちらとも違うファイル）。取り込みコミットの第 1 親との差分（base 側から入った変更）は数えない。3 本の委任ブリーフへこのファイル集合を母集団として渡す（sha は上の値域検査を通してから置く）。**限界（fail-open）**: 衝突なしで自動 merge された base 側の行が PR の変更と意味的に干渉する回は、この母集団では見えない。
   - **再レビューは R1 の worker を再開して回す（新規委任しない）**: R1 で委任した各 worker の agent ID を控えておき、再レビューの巡では `SendMessage`（宛先はその agent ID）で**同じ worker を再開**し、上の増分（`<前回 head sha>`・持ち越す前巡の Important の逐語・結果ファイルの巡ごとの追記規則）だけを見させる。**Why**: 再開は前の実行の文脈を読めるので、同じ母集団を新規委任で読み直すより 1 巡の消費が小さい。
     - **再開できない回は新規委任へ倒す**: agent ID を控えていない・その worker が停止済み（終了した・`SendMessage` が届かない・再開が失敗した）回は、R1 と同じブリーフ（テスト実走の授権の行と付随する値を含む）で新規委任する（**fail-closed**——再開を諦めて再レビューを省く分岐は無い）。どちらで回したかを段 2 のコメントに 1 行残す。
     - **再開した worker は背景で走る**。完了の通知を受けてから、R1 と同じ `gate artifacts` の欄検査に通す（通知を待たずに結果ファイルを読まない）。
     - **前巡の Important の逐語の持ち越しは再開した回も省かない**——再開した worker は前巡の文脈を持つぶん、前巡の見落としも引き継ぎうる。持ち越しはその手当てであって、再開で置き換わるものではない。
5. R1 へ戻る（上限 2 回を共有）。

- **Nit のレビュアー直接修正が入った回**（R1b を通した回）は、**再レビューを起こさない**。反映は R1b が定めるとおり orchestrator が機械段を直接回して commit・**push だけ**する。**push ごとの無条件再レビューはしない**——再レビューを起こすのは Important の是正だけである。**同じ回に 修正推奨「あり」 もあるなら、上の連鎖が優先し、Nit 修正はその連鎖の中で一緒に push される**（2 つの経路を独立に走らせない）。
- **収束の記録行（欄 id `fix-convergence-record`・分岐に依存しない必須出力）**: 本段の収束状況を、`gate vocab --field fix-convergence-record` が返す接頭辞で始まる 1 行として確定し、**PR 本文の最上部（BLUF）へ置く**（`shirokuma-flow pr record <pr> --field fix-convergence-record --value <v>`・状態は触らない）。値は**閉じた 2 値**（収束した回と、ループ上限で未収束のまま修正推奨が「あり」で残る回。逐語は `gate vocab --field fix-convergence-record` が正本）。**収束した回も書く**（**書き落としを検知する機械段は無い**＝fail-silent。値域外を渡した回は `pr record` が exit 1 で書き込みを止める）。接頭辞は `gate vocab`（欄 id `fix-convergence-record`）の `name` で、**段名ではなく欄名（接頭辞）として読む**。
- **結果ファイルの持続形式**: 結果ファイルは**巡ごとに追記**する（消さない・別内容で全文上書きしない）。**先頭行 `head sha=<sha>` は巡ごとに最新の値へ更新**する（R2 の `<前回 head sha>` の出所）。**巡の見出しの字形は定めない**——判定値は結果ファイルから読まれず、`shirokuma-flow gate verdict` は検出器記録の entry を `--head` との完全一致で選ぶ。
- **検出器記録の置き場所**: 3 本の review worker は判定値を `detector record` で役割ごとの記録ファイルへ書く。標準命名は `.shirokuma/tmp/{code,security,asset-safety}-review-<issue#>.detector.json` で、R1 の委任ブリーフで絶対パスを渡す（`<issue#>` は上の差し込み前検査を通した値）。**`.shirokuma/tmp/` が ignore されているかは導入先リポの設定に依る**——除外されていない回は記録ファイルが untracked の母集団に入る（worker 定義の作業ファイル条項と同じ扱い）。記録は (役割, head, 欄) 単位で upsert されるので、巡ごとに同じファイルへ書いてよい。
- **上限で収束しない回の持ち越し（確認モードに依らず常に行う・`guided` はさらに人ゲートと併存する）**: 最後の R1 が書いたコードレビュー結果ファイルを**残す**（**R2 以降で消さない・別内容で上書きしない**）ことと、段 1 の判定器（code ∧ mainline の回は `gate verdict`、それ以外の回は `review-worker`）が最後の巡の検出器記録（`review-worker` には `gate verdict` の `fields[]` を委任ブリーフで渡す）を読み、修正推奨が「あり」で残る回の判定行を NEEDS_REVISION にすることは、**確認モードに依らず常に行う**——`NEEDS_REVISION` が**merge 条件①の入力になる**ことが、自律の回で判定行 `NEEDS_REVISION` を持ち越して merge 条件①で止まったまま報告して終端する（上記「R2. 差し戻し判定」の記述）ための唯一の裏打ちであり、これを人の判断を条件に発火させると自律の回には一度も発火しない（安全装置を条件節へ閉じ込める形になる）。**`guided` の回はこれに加えて人ゲートで止め**、人が「指摘を受け入れて先へ進める」と判断してから段 1 以降へ進む。**PR 本文の収束の記録行だけでは条件①の入力にならない。** **受け側の版で挙動を変える分岐は置かない**（観測できない条件は一度も評価されない空文になる）。**倒れる向き**: 中身の読解は review-worker に依る（**fail-open**）。
- **入口はもう 1 つある（3 本目の第 2 軸欄・R1 からの routing）**: 上記 3 値が出た回は、**修正推奨の有無・ループ回数・確認モードによらず人ゲートへエスカレーションする**（渡し先は R2 が既に持つエスカレーションで、**新しい停止点・新しい上限・新しい報告面は作らない**）。**(b) 地点は「トリアージ / 設計 / 計画の `approve`・確認用 HTML・差し戻しループ上限のエスカレーション・レビュー結果の確認（merge の前）」の 4 つで、この第 2 軸欄の routing は含まれない**——ここが検出しているのは「配布物の検査を緩める変更で、かつ不当の疑いがある」こと（自律の境界そのものを緩める疑いの族）であり、R2 の渡し先を共有しているからといって R2 と同じ (b) 分類・同じ確認モード依存の振る舞いを引き継がせない。**この routing 自体は再委任を起こさない**（LLM の再判定で値が変わることを期待する経路ではないので、`coding-worker` への修正委任も R1 への戻りも行わず、共有のループ上限も消費しない）。**同じ回に 修正推奨「あり」 がある場合は、上の入口が定める修正委任と R1 への戻りを通常どおり行う**——2 つの入口は独立に働き、一方が他方を打ち消さない。
- **入口はもう 1 つある（`quality.localVerifyCommand` の値そのもの・機械段の実行前に掛ける）**: この値は**その回の差分がレビュー対象として持ち込みうるコマンド**で、値の中身に対する値域検査はどこにも無いままシェルで実行される。**上の 2 つの入口はどちらもこの値では発火しない**ので、**この値だけを別扱いにする**。
  - **一次は機械条件（実行の直前に base 側と同値であることを確かめる）**: 実行しようとしている値が、**base 側の config が宣言する同じキーの値**と**同一**であることを確かめる。**この 2 値はコマンド行へ載せない**（読むだけのデータとして扱う）が、base 側を取り出すコマンドには `<base>` と作業ツリーの絶対パスが載るので上記「コマンド行へ値を差し込む前に検査する」の対象である。**確かめるのは実行の直前**——レビュー層の委任から実行までの間に値が動いた回を覆うため。
  - **確かめるのは実行主体であって、検査を別の主体へ分離しない**: 標準レーンでは **`finalize-worker` が CI 等価検査の段の直前に**、軽量レーンでは**実行者自身が**同じ位置で行う（**手順とコマンドの正本は `finalize-worker` 定義の「CI 等価検査」節**——手で組み直さない）。**orchestrator が代行しない**——検査者と実行者を分けると「検査した値」と「実行される値」が別々の 2 回の読みになり同一性の保証が消える。
  - **同一でない回・確かめられない回はその値を実行する段を実行しない**（**実行そのものを起こさせない**のが条項の目的で、他の段まで止めるのではない）。実行主体はその段を実行しなかったことと理由を報告し、**その報告が現れた回を本節の人ゲートへ回す**（**確認モードによらず常に人ゲート**——コマンド注入の主防御であり (b) 地点の射程外なので、R2 の確認モード分岐は適用しない）。**トリガはレーンごとに別で、どちらも名指しする**——標準レーンは **`finalize-worker` の報告表で当該段が `fail` であり詳細欄が同一性の不成立を理由に挙げている回**（**`fail` は完了扱いの結果値で [[orchestration-discipline]] C6 の不完全シグナルには含まれない**＝**C6 はこの回を止めない**）、軽量レーンは **実行者自身が当該段を回さなかったと証跡に書いた回**（自己申告）。**片側だけ名指しすると、名指ししなかったレーンでは引き渡しが一度も発火しない**（fail-open）。どちらの引き渡しも読解に依る（**fail-open**）。**倒れる向きは fail-closed**——このキーを正当に変更した回も止まるが、**緩める向きの値が誰にも読まれないまま実行される経路は残さない**。**キーを新設する PR（base 側に当該キーが無い）も同じ人ゲートへ回る**——新設を区別して通す述語は置かない（base 側に無いキーは常に差分が持ち込んだ値なので、通す述語は無条件の許可と区別がつかない）。この回に人が選べるのは、差分の中の値を読んで自分で実行し結果を PR に残すか、新設だけを先に base へ入れる（別 PR で人が読んで merge する。**その PR も base 側にキーが無いので同じ人ゲートで止まる**——人が値を読む場所がそこへ移るだけである）かである。**人ゲートが判断するまで、AI は差分の中の値を実行しない**（「参考として」の実走も含む。実行主体が orchestrator でも軽量レーンの実行者でも同じ）——実行すること自体が、この条項が起こさせないと定めた事象だからである。
  - **守る範囲を過大に読まない（射程の申告）**: 確かめるのは **config が宣言するコマンド文字列そのもの**だけで、その文字列が名指す実体（スクリプト本体・読み込むモジュール等）は**射程外**であり **3b の allowlist にも当たらないことがある**。したがって **config を 1 文字も触らずエントリの中身だけを書き換えた差分は、同一性検査を「同一」で通り、同じ回に同じシェルで実行される**（**fail-open**）。**「この値そのものが読まれた」を「実行されるコードが読まれた」と読み替えない。**
  - **二次は 3 本目の所見**: 3 本目が所見としてこの値を名指しした回も同じ人ゲート（**確認モードによらず常に人ゲート**）へ回す（**fail-open**——名指しは読解に依る）。**この条項を機械強制する層は無い**（**fail-silent**）。

## 本ファイルが持たないもの（申告）

- **asset-delay 判定（`gate asset-delay`）は implement-flow が持つ**。base と作業ツリーだけで決まる**実装サマリーの記録行**であってレビューではないため。
