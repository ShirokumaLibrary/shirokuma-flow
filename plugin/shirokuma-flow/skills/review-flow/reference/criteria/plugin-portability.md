# プラグイン自己完結観点（plugin-portability）

review-worker が **プラグインのソース（`.claude-plugin/plugin.json` を持つディレクトリの配下。manifest を持たないディレクトリは当たらず、この観点の外になる＝fail-open。以下同じ）の変更**を含む PR / docs をレビューする際のハード観点。プラグインは配布物であり、各 skill / agent は**単体で読み込まれる**ため、自己完結していなければ配布先で参照が壊れる。以下のいずれかに該当したら**自動 NG**（`**レビュー結果:** NEEDS_REVISION`）。

> **枠組み**: PP1〜PP3（下記ハード観点）は該当＝**自動 NG**。末尾の「配布物自己完結の観点」節は射程を配布物一般（rules 等）へ広げた**推奨観点（人判断・自動 NG 対象外）**であり、両者を混同しない。

> 適用範囲: 変更対象にプラグインのソースのファイル（SKILL.md / agent .md / reference/*）が含まれるとき。コア観点（code.md / docs.md）と合算する。

## ハード観点（該当 = 自動 NG）

### PP1. 他 skill / agent へのパス参照・名指し依存

- [ ] 別 skill / agent の `reference/` や `SKILL.md` への相対パスリンク（`../<他skill>/reference/...`・`../<他skill>/SKILL.md`）がない。**同一 skill 内の relative リンクは可**
- [ ] 「正本は別 skill 側」「別 skill のファイルを Read せよ」等の名指しクロス依存がない（必要な内容は自己所有するか、委任ブリーフで渡す設計にする）

### PP2. リポ内部資料への参照

- [ ] リポ内部の運用資料への参照がない: `.shirokuma/notes/*`・`docs/`（セットアップガイド等）・`handoff`・`domain/`・確認用 pages の URL
- [ ] 規範を名前で指す参照（「規範 `<名前>`」・中身を読ませるなら `shirokuma-flow rules show <名前>`）は可。規範をパスで指す参照は不可（配布物の置き場は導入先の状態で在ったり無かったりし、パスは 1 つの状態でしか当たらない）。それ以外の内部 notes/docs はパス・URL とも不可

### PP3. プロジェクト固有の識別子

- [ ] このリポ固有の Issue 番号 / リポ名（`owner/repo`）/ Project 番号への言及がない
- [ ] **ADR の番号参照（`ADR-NNNN`・`ADR #N` の形）も NG**。配布先では解決できないうえ、配布先の利用者は自分の ADR を同じ形で持つので、配布物に残る番号は利用者自身の ADR と読み違えられる。**是正は「規範内容を本文に書き、番号を落とす」**——決定の Why 全文は不要で、skill が従うべきルールが番号なしで読めれば足りる。出典行（「Why の正本: …」型）は行ごと落とす。**本条の条件はここ（PP3）が正本**で、コア観点（code.md / docs.md）は本節を適用せよと指示するだけで条件を写さない（写した要約は必ず条件を落とし、本体より緩い基準として先に読まれる）。
- [ ] **番号に続く名札（`R1`・`3a`・`4 巡目` など）は番号と一緒に落とす**。名札は番号の中の位置であって、番号が無くなれば指すものが無い。名札だけを残すと、限界レジストリの id など別のものを指す名札と衝突する。限界レジストリの項を指すときは、バッククォートで囲んだ実在の id で書く。
- [ ] **来歴としての裸の Issue 番号併記も NG**（例: 「`#<実 Issue 番号>` 差分ビューア」のように機能名へ実 Issue 番号を添える書き方）。番号は来歴であり配布先では意味を持たないため、**意味を保ったまま番号を落とす**（「差分ビューア」）。番号が要るように見える箇所も、規範内容を本文に書いて番号を落とす。本条は `lint docs` の `plugin-bare-issue-ref`（プロジェクトの `lint docs` の設定で有効にしたときだけ走る。既定の母集団は `plugin/**/*.md`・error）が機械で検出する。機械段は検出器であって条件の正本ではない（正本は本節）。除外: ADR 形（`ADR #N(・#N)*` の連鎖含む）・`Discussion #N`・16 進カラー・`owner/repo#N`・worked example の架空番号（101〜105）・frontmatter とフェンス内。規範のファイル等は母集団外。**3 桁の番号は 16 進カラーと形で区別できないため機械段の母集団外（人が読む・fail-open）**。
- [ ] 例外として可: 書式そのものを説明する例示（GitHub 参照の書式を示す番号など）。worked example は番号を使わない形（`{計画番号}` のようなプレースホルダ）で書く

## 配布物自己完結の観点（rules 等・人判断／自動 NG 対象外）

> **強度**: 本観点は人の判断で当て、自動 NG の対象にしない。Why は、配布物が配布先で参照解決なしに読めること（自己完結）である。

上記 PP1–PP3 はプラグインのソースを射程とするが、**配布物は plugin だけではない**。同梱規範（`rules install` で導入先の配布物の置き場へ書かれ、`rules inject` で scope 注入される規範）自身も配布物であり、それ単体で配布先へ渡る。本節は PP1–PP3 と別に配布物一般を射程にし、**人の判断**で運用して、PP1–PP3 のような自動 NG にはしない。

- **観点**: **配布物（同梱規範 等 `rules install` で配布されるもの）に触れる変更は、規範内容が配布先で参照解決なしに読めるか（自己完結）を確認する**。ADR/Issue 番号を解決できなくても、従うべき規範内容が本文だけで読み取れる形になっているか。
- **突き合わせ対象**: **自己完結性**（規範内容を番号なしで自己完結させ、配布先で解決不能な内部参照に規範内容を依存させない）。
- **判断主体と強度**: 判断主体は**人レビュー**。lint（workflow 領域）が rules 内の `#n` / `ADR #n` 参照を warning で可視化するのは**補助**にすぎない（番号の存在を surface するのみで、「番号なしで規範内容が読めるか」は機械判定不能）。字面マッチの禁則にはせず、自動 NG にもしない。
- **PP2 との関係**: PP2 の「プラグインのソースから規範を名前で指す参照は可」は plugin 側から見た依存の可否であり、そのまま維持する。本観点はそれと別に、**rules 自身が配布物である**ことを見て、rules に触れる変更でその自己完結性を確認する（rules を安全側「可」で無条件に素通ししない）。

## 機械検査コマンド

```sh
# 他 skill / agent へのパス参照
grep -rn '\.\./[a-z-]*/\(reference\|SKILL\)' <プラグインのソースのディレクトリ>/ --include="*.md"
# リポ内部資料への参照
grep -rn 'notes/\|handoff\|docs/setup\|domain/' <プラグインのソースのディレクトリ>/ --include="*.md"
# ADR 番号参照（ヒットは PP3 で NG。書式の例示と検査定義の自己言及は除く）
grep -rnE 'ADR[- ]?#?[0-9]+' <プラグインのソースのディレクトリ>/ --include="*.md"
```

ヒットしたら同一 skill 内 relative・規範を名前で指す参照・架空例を除外した上で、残った箇所を NG として指摘する。**ADR 番号の grep のヒットも、書式の例示と検査定義の自己言及を除いて NG として指摘する**（PP3）。ただしこの grep は `ADR` に番号が続く字形しか拾わないので、番号の別の書き方は拾わない（倒れる向きは fail-open）。**検査定義・観点記述としての自己言及は除外する**——本ファイルの grep 定義行が `ADR[0-9]` や `notes/`・`handoff` を含むのも、他 skill のレビュー観点が「`.shirokuma/notes` への参照が無いこと」のように検査対象を字面で記述するのも、依存ではなく検査の定義なので正当。
