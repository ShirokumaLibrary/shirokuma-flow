# 調査レビュー観点（research）

review-worker が調査結果（research-worker の成果物・Research Issue）をレビューする際の判定基準。調査がプロジェクトの要件・アーキテクチャに合致しているかを検証し、不合致のベストプラクティスは取り込み提案に落とす。

> レポート雛形は [../templates/report.md](../templates/report.md)。

**適用の流れ**: 要件合致性・調査品質・実装可能性・不合致判定で検出 → 末尾の「判定」節で PASS / NEEDS_REVISION を決める。**検出段では指摘を深刻度に関わらず全件列挙し、絞り込みは判定節で行う**（検出段で絞ると低深刻度の所見が失われる）。

## 要件合致性

| 基準 | 評価観点 |
|------|---------|
| 技術スタック互換性 | 推奨パターンがプロジェクトの技術スタック（CLAUDE.md・`package.json`）と互換か |
| 既存パターン整合性 | 推奨事項がプロジェクト内の既存実装パターンと矛盾しないか |
| 依存関係互換性 | 推奨ライブラリ / バージョンが既存依存関係と競合しないか |
| アーキテクチャ適合性 | 推奨アプローチがプロジェクトのアーキテクチャ方針・既存 ADR に沿っているか |

## 調査品質

| 基準 | 評価観点 |
|------|---------|
| ソースの多様性 | 複数の独立したソースから裏付けがあるか（最低 1 つの公式ドキュメント） |
| バージョン整合性 | 参照ドキュメントのバージョンがプロジェクトの使用バージョンと一致するか |
| ソース帰属（provenance） | すべての推奨事項にソース URL が付与されているか |
| 最新性 | 古い API やパターンを参照していないか |

## 実装可能性

| 基準 | 評価観点 |
|------|---------|
| 具体性 | 推奨事項がコード例付きで具体的か（抽象的な助言ではないか） |
| 段階的導入 | 大きな変更の場合、段階的な導入パスが示されているか |
| リスク識別 | 潜在的なリスクや注意事項が明示されているか |

## 不合致判定（4 値）

| 合致度 | 条件 | アクション |
|--------|------|----------|
| 完全合致 | 推奨事項が既存パターンと整合 | そのまま採用 |
| 部分合致 | 一部の推奨事項のみ適用可能 | 適用可能な部分を抽出し、不適用部分の理由を記載 |
| 不合致だが有用 | ベストプラクティスだが現行アーキテクチャと競合 | 取り込み提案を作成（下記） |
| 不合致かつ不適用 | 技術スタックや要件と根本的に合わない | 不採用理由を記載、代替案を探索 |

## 取り込み提案の形式（不合致だが有用な場合）

レポートに以下の形式で記載し NEEDS_REVISION で返す。取り込みの可否は orchestrator 経由で人が確定する。

```markdown
### 取り込み提案: {パターン名}

**推奨パターン:** {ベストプラクティスの概要}
**現行パターン:** {プロジェクトの現状}
**不合致の理由:** {なぜ直接適用できないか}
**取り込み方法:** {段階的な導入パス}
**影響範囲:** {変更が必要なファイル数 / コンポーネント数}
**リスク:** {潜在的なリスク}
```

## 委任・検査に触れる変更（対象種別によらず適用・正本は [[delegation-and-checks]]）

調査結果が **委任（worker / skill / 手順への割り当て）または検査（ゲート・判定条件・決定表・lint ルール・レビュー観点・テストによる機械検証）に触れている可能性がある**なら、[[delegation-and-checks]] を読んで実際の発火条件を当て、該当したら同規範の D 節 / C 節で見て同規範が定める深刻度で指摘する。

観点・発火条件・深刻度の正本は同規範側にあり、**本ファイルは条件を写さない**（写した要約が本体より緩くなる形＝同規範 C5 を避ける）。上の開閉条件は正本より広く取ってあり、当たりすぎることはあっても当たらなくなることはない。**対象種別が調査でも適用する**——観点を 1 経路の判定基準にだけ置くと、その経路を通らない対象では発火頻度が 0 のまま緑になる。

## 判定（PASS / NEEDS_REVISION の決め方）

検出をすべて終えたあとに、列挙済みの所見から判定する。

- **重大な問題がなく要件と合致すれば PASS**（所見はレポートに記載する）。
- **ソース不足・バージョン不整合・要件との重大な不合致・取り込み提案がある場合は NEEDS_REVISION**（取り込み提案は人の確認が要るため）。
