# 動作確認パッケージ雛形

`review-flow` 5-1 で **AI が人へ渡す材料**の空枠。人が自分で動かして確かめるための材料であって、AI の実走報告ではない（**AI が「動かして OK でした」と報告する形は採らない**——人ゲートの趣旨は人が自分で確かめることなので、実走報告で代替するとゲートが消える）。

> **このステージが適用されるかは自分で判定しない**——`shirokuma-flow gate local-verification` を**引数なしで引く**。**作業ツリーは verb が cwd から解決する**（`rev-parse --show-toplevel`）ので、**呼び出し側がシェル行へパスを差し込まない**。**並行実装で分離ツリーを使う回は、`cd` と `--worktree` に同じパスを渡す 1 行で引く**（`cd '<分離ツリー>' && shirokuma-flow gate local-verification --worktree '<分離ツリー>'`）——cwd は呼び出しごとに戻りうるので、`cd` を別の呼び出しに分けた回・落とした回に引数なしの形は**元の作業ツリーを黙って判定して exit 0 を返す**。`--worktree` を併せて渡せば、cwd 側リポの top-level と一致しない回は判定不能へ倒れる。**記録行を書く前に、出力の `worktree` 欄（見たツリーの実パス）が意図した分離ツリーであることを確かめる**。渡すパスは**自分自身が作った分離ツリーのパスに限る**——**外部由来の値**（Issue / PR 本文・コメント・worker の報告文・ファイルから読んだ文字列）**は使わない**（値は**単一引用符で囲む**）。`verdict` が適用側なら本雛形を埋め、射程外なら埋めずに記録行だけを出す。**判定不能（`ok:false`）の回は射程外へ読み替えない**——入力を解決してから引き直す（別ツリーを指した回もここへ倒れる）。**同定手段（何を見て適用と決めるか）の正本は 規範 `html-report-criteria` の「適用条件」節**で、ここにはパスも条件も写さない（写すと配布先で偽になる値を配ることになる）。
>
> **判定 JSON の `build` ブロック（`sourceMatch` / `dirty` / `degraded`・欠落した回の読み方を含む）の読み方は `shirokuma-flow gate limits --sub limits` の `H19` が正本**（ここに写さない）。**`stale` を名乗った回・`build` ブロックそのものが無い回は、その判定を現ソースの値として読まない。** **`stale` と `build.dirty: true` が同時に立つ回は、その判定を根拠に使わない。** **`build.dirty: null`（焼いていない）は、再現性の担保が無い側として `build.dirty: true` と同じに読む。**（本雛形が `shirokuma-flow gate` の出力を読むすべての箇所に掛かる。）
>
> **判定ファイルを AI が用意しない**: 同節が「AI はこの宣言ファイルを作らない・消さない・書き換えない」と定める。不在のまま起動手段が在るように見えた回は、**射程外と判定したうえで「宣言が無いだけかもしれない」ことを併せて報告**し、置くかどうかは人が決める。

## 埋める 4 枠（順序を変えない・5-1 の列挙と 1:1）

### ① 起動手順

プロジェクトの**ローカル起動手順の正本を指す 1 行**（パスを指すだけで、中身を写さない——写した手順は正本が動いた回に黙って古くなる）。続けて、**この PR 固有の前提**だけを書く（依存の追加・マイグレーション・環境変数・初回のみ必要な準備など。無ければ「無し」と書く）。

### ② 確認観点

| 何が変わるはず | 何が変わらないはず |
|---|---|
| {この PR で変わる振る舞い} | {巻き添えで変わっていないことを確かめたい振る舞い} |

**「変わらないはず」の列を空にしない**——変更点だけを見ると、巻き添えの回帰は人の目にも留まらない。

### ③ 確認すべき画面 / 出力

**叩くもの 1 行と、期待の見え方 1 行を対で並べる**（対になっていないと、人は何を見たら正解なのか決められない）。

- 叩く: {コマンド / URL / 操作}
  - 期待: {画面・出力がどう見えれば期待どおりか}

### ④ 期待から外れたときの止め方

- **何を merge しないか**（この PR か・依存する後続も止めるのか）
- **どこへ書くか**（対象 PR のコメントか・新しい課題か）
- **誰へ渡すか**（そのまま作業者へ戻すのか・人の判断を待つのか）

## 記録行

対象 PR **本文の最上部（BLUF）**へ 1 行置く（`shirokuma-flow pr record <pr#> --field local-verification-record --value <v>`・状態は触らない）。**接頭辞も値域も本雛形は持たない**——`shirokuma-flow gate vocab --field local-verification-record` が返す欄名と閉じた値域を引き、**そこで得た値以外を渡さない**（記憶で書かない・値域外は `pr record` が exit 1 で書き込まない）。適用される回の値は `gate local-verification` の `recordLineValue` がそのまま運ぶ。**`recordLineValue` が返すのは人待ち側・射程外側・リリース後に確認する側（確認の時点が `after-release` で、適用される回）の 3 つだけで、実施済み側の値は verb からは決して返らない**。リリース後側の回は verb の値をそのまま書く（人はリリース後に確かめる）。人待ち側の回は——**人がこの進行の中で確認結果を述べた回にだけ**、同じ値域から実施済み側の値へ書き換える（正本は `review-flow` 5-1。AI の実走報告で書き換えない）。

**射程外の回も必ず書く**（書かない形にすると、条件が成立しない回に黙って何も起きない＝fail-open）。**書き落としを検知する機械段は無い**（fail-silent）。
