# TDD ワークフロー詳細

coding-worker が実装時に回す TDD（red → green → refactor）の刻み方とテスト粒度。worker 本文の原則「失敗するテストを先に書く → 実装で green」の詳細。委任ブリーフにこのパスが明示されたら Read する。

## サイクルと刻み方

```text
テスト設計 → red（失敗するテストを書く）→ green（最小実装で通す）→ refactor → 次の振る舞いへ
```

- **1 サイクル 1 振る舞い**: 「この入力でこの出力」を 1 つずつ。複数の振る舞いをまとめて red にしない（どこで壊れたか追えなくなる）。
- **red を確認してから実装する**: テストが「正しい理由で」失敗すること（コンパイルエラーでなく assertion 失敗）を確認するゲートを通過せずに実装へ進まない。
- **green は最小実装**: テストを通す最小の変更に留め、一般化・整理は refactor で行う（テストが緑のまま刻む）。
- 計画タスクが大きい場合は、受け入れ基準を振る舞い単位に分解してサイクルを並べる。

## テスト粒度（何をどこまでテストするか）

| 対象 | 必須テストケース |
|------|----------------|
| 公開関数・モジュール I/F | 正常系・異常系（エラーパス）・エッジケース（空・境界値） |
| CLI コマンド / エントリポイント | 正常実行・引数バリデーションエラー |
| 状態を持つ処理（状態機械・遷移） | 許可遷移・禁止遷移の両側 |
| ユーティリティ | 正常系・エッジケース・エラーケース |

- フレームワーク固有の最低カバレッジ（page / server action / API ルート等）は拡張 skill（coding-nextjs 等）側の基準に従う（併用判定は [../criteria/delegation.md](../criteria/delegation.md)）。
- 内部実装の詳細（private 関数）はテストしない——公開 I/F 経由で振る舞いを検証する（refactor でテストが壊れない粒度に保つ）。

## @testdoc コメント（必須）

各テストに説明付き JSDoc コメントを付ける（`shirokuma-flow lint areas tests` の検査対象）:

```typescript
/**
 * @testdoc ユーザーを新規作成できる
 */
it("should create a new user", async () => {
  // テスト実装
});
```

`.skip` するテストには `@skip-reason` を必ず付ける。

## テスト失敗時の規律

1. **テストではなく実装を修正する**（テストを直してよいのは要件・仕様の側が変わったときだけ）。
2. すべて緑になるまで再実行し、緑になってから次のサイクル・次のステップへ進む。

## 完了前の検証

実装完了時に以下を通してからサマリーを返す:

```bash
pnpm test          # （プロジェクトのテストコマンド）
shirokuma-flow lint areas tests   # @testdoc / skip-reason 検査
```

lint・型チェックのコマンドはプロジェクトの CLAUDE.md / package.json scripts に従う。

> テストの省略は不可（例外なし）。テストなしで実装サマリーを返さない。コミット・状態遷移は worker の責務外（commit-worker / orchestrator が行う）。
