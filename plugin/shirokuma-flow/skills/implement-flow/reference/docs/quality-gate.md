# 品質ゲート（段 4）の詳細手順

`implement-flow` の段 4（4c → 4d）の実行手順と、`gate` verb を呼ぶすべての段に共通する機械契約を持つ。

> **レビュー層 3 本と差し戻し判定は `review-flow`（`reference/docs/review-gate.md` の R1 / R2）が持つ。** 本ファイルはそれらの手順を持たない——**深いレビューの置き場は PR 作成後**であり、実装フェーズの終端は「finalize 緑＋PR 作成」である。

**読むタイミング**: **段 4 に入る前に必ず Read する**（軽量レーンで実行者が直接回す回も同じ）。SKILL.md 側は本ファイルを指すだけで、条件・値域・分岐の逐語は持たない。

**射程外**: 欄名・値域・限界の逐語は本ファイルにも持たない——正本はコード内のレジストリ 1 箇所で、実行時に `shirokuma-flow gate vocab` / `shirokuma-flow gate limits` が返す。

## gate の呼び方（4c / 4d に共通・機械契約）


**機械判定は読み取り専用 verb `shirokuma-flow gate <サブコマンド>` が行い、本手順は呼び出しと結果による分岐（routing）だけを定める。** 判定ロジック・欄名・値域・限界の逐語は本手順に持たない（正本はコード内のレジストリ 1 箇所で、実行時に `gate` が返す）。

- **判定は JSON ＋ exit code の二重で返る**。JSON の `complete: true` が「検査が最後まで到達した」証拠、`version` が判定を出した CLI 版、`scope` が何を母集団に見たかである。exit code は **0（完走・記録や分岐を要する所見なし）／ 2（完走・所見あり＝`pass: false`）／ 1（判定不能＝`ok: false`）** の 3 値。
- **判定不能を pass に読まない**。JSON に `complete` が無い回・`ok: false` の回・verb を解決できない回（`unknown command`・コマンド不在）は、いずれも **`判定不能` であって「指摘 0 件」ではない**。**非 0 を一律「検査が何か言った」と読まない**——`unknown command` も非 0 で返る。
- **判定不能の回の routing（fail-closed）**: その段の pass を前提にする分岐（3 本目の委任・再委任・書き直し・継続委任）へ進まない。記録行は分岐に依存しない必須出力なので**書く**が、**値域内の値へ丸めない**——丸めると「測って良性だった回」と「測れなかった回」が実装サマリー上で同じ見た目になる（fail-open）。当該記録行の値域に判定不能を表す値があるならそれを使い、無いなら `判定不能（<理由>）` と書いて直下の字下げ行に理由を残す。**`<理由>` には「引けなかった verb 名」ではなく、その回に判定を出せなかった事由を書く。** **値域へ判定不能の値を足すかはレジストリ（コード）側の変更であり、本手順では決めない。**
- **欄名・値域は `shirokuma-flow gate vocab`（`--profile` / `--field`）、検査の限界は `shirokuma-flow gate limits --sub <サブコマンド>` で引く**（`--sub` は `gate` のサブコマンド名であって Issue 番号ではない）。値域の照合は `gate vocab` が返す `matching` の方式で行い、**部分一致で走査する消費者を作らない**（値域の語どうしに包含があるため過検出側へ倒れる）。
- **判定 JSON の `build` ブロック（`sourceMatch` / `dirty` / `degraded`・欠落した回の読み方を含む）の読み方は `shirokuma-flow gate limits --sub limits` の `H19` が正本**（ここに写さない）。**`stale` を名乗った回・`build` ブロックそのものが無い回は、その判定を現ソースの値として読まない。** **`stale` と `build.dirty: true` が同時に立つ回は、その判定を根拠に使わない。** **`build.dirty: null`（焼いていない）は、再現性の担保が無い側として `build.dirty: true` と同じに読む。**
- **検査の呼称（3 語・機械契約）**: 呼称は**検査した主体が判定対象を作った主体と別か**で決まり、使ったツールでは決まらない。
  - **機械検証**: 判定対象を作った主体とは**別の主体**が検査した段（orchestrator が finalize-worker の報告表を走査する 4c。`gate` が worker の結果ファイルの欄を検査する段は review-flow の R1 が持つ）。
  - **自己検査**: **同一主体が自分の出力を検査する**段（orchestrator が自分で書いた記録行に対し自分で `gate summary` を引く 4d-2 など）。
  - **自己申告**: **誰も検査しない**最下段（`gate` が出した判定を実装サマリーへ書き写す転記・記録行の直下の字下げ行）。
  - **`gate` を呼べば機械検証になるのではない**——判定を出すプロセスが別でも、母集団を用意して結果を写すのが同じ主体なら、その段は自己検査であり転記は自己申告である。**倒れる向きは fail-open**（この呼び分けを検査する機械段は無い）。

### コマンド行へ値を差し込む前に検査する（`gate` を呼ぶ全段に共通・この経路の唯一の防御）

一般則（プロセス内の値域検査がコマンド行に効かない理由・単一引用符・免除の引き方・倒れる向き）は注入される rule `trust-boundary`「コマンド行へ値を差し込む前に検査する」が正本。ここは本フェーズの対象と分岐だけを持つ。

- **対象と条件**: **`--base` に渡す base**（親 Issue 本文の節や `origin/*/{親番号}-*` 探索から来る＝**untrusted**）は、`gate vocab`（**`--field` では返らないので引数なしか `--profile` で引く**）が返す `baseRefAllowlist` の条件（許可文字 allowlist・`-` 始まり禁止・単一行）をすべて満たすこと。**`--file` / `--report` の絶対パスに埋め込む `<issue#>`** は `^[0-9]+$` に一致すること（**Issue 番号が数値であることをリポのどこも保証していない**——「絶対パスだから安全」ではなく、安全なのは**検査した値だけ**である）。**`--criteria` に渡す判定基準ファイルのパス**（`gate token` が返した値）は `'` を含まないこと。**この 3 項目の列挙は閉じていない**——`--worktree` に渡す作業ツリーの絶対パスのように**ここに挙げていない値も、コマンド行へ載せる以上は上の rule `trust-boundary` の項の対象**である。
- **満たさない回は verb を引かない**。base が満たさない回は 4d-1 の記録行に判定不能を表す値を書き、`<issue#>` が満たさない回は 4d-2 を実行せず作業ファイルのパスが不正であることを表す値を書き、`--criteria` の値が満たさない回は 4c の `gate finalize` を **`--criteria` を渡さずに**引き（同引数は任意で、省略した回も**入力異常検知は走る**）、その段を判定不能として記録行に残す。

## 4c. finalize

**本段は機械段だけである**——レビュー層 3 本は本フェーズで委任しないので、**レビュー結果ファイルは存在しない**。**finalize への委任ブリーフにレビュー結果ファイルのパスを要求しない**（渡すものが無い）。finalize 定義のレビュー転記段は**結果ファイル未提供の既存の劣化動作** `skip(理由: 結果ファイル未提供)` で通る。**結果ファイルが在るのは review-flow の R1 以降**で、そこで欠落した回の逐語転記も review-flow の責務である（本手順は持たない）。**指し先は `review-flow` の `reference/docs/review-gate.md` の R1「欠落時の経路」の逐語転記フォールバック**——「review-flow の責務」とだけ書くと、どちらも持たない状態（両側が相手へ責務を渡す形）と区別が付かない。

`finalize-worker`（品質ゲート各段——段の列挙は finalize-worker 定義が正本）を通す。**ブリーフに `<base>` を明示する。** **finalize が何をコミットするか（射程）の正本は `finalize-worker` 定義**で、orchestrator 側が前提にするのは 2 点だけである: ① **返る SHA は finalize 自身の自動修正だけを指すとは限らない** ② **コミットしない回がある**ので、SHA 行が「なし」の報告はその回の理由の記載とあわせて読む。**`<base>` の解決順・挿入前の値域検査・出所の記録の作法は `finalize-worker` 定義が正本。** **本フェーズでは 3 本目（`asset-safety-review-worker`）を委任しないので、段名も結果ファイルパスも渡さない**（委任は review-flow の R1 が行う）。finalize-worker の報告を受けたら**各段の結果表＋コミット SHA の有無を機械検証**する（`skip(理由)` は完了扱い。不完全のシグナルは `pending` 残り・SHA 欠落・**ブリーフで段名を渡した段の行が表に無いこと**——**定義の正本は `orchestration-discipline` C6** で、ここに写した以上の条件を独自に足さない）。

- **記録行の存在検査と入力異常検知**: `shirokuma-flow gate finalize` を `--report <finalize 報告の絶対パス>` で引く（**この値は上記「コマンド行へ値を差し込む前に検査する」の対象**）。**本フェーズでは `--criteria` を渡さない**——3 本目の委任は review-flow の R1 が行うので、渡す値を持たないからである。同引数は任意で、渡らない回は**記録行の存在検査だけが `not-run`（`reason: criteria-unset`）になり、入力異常検知は走る**（パスを持たないことは入力異常検知を落とす理由にならない）。**検査に使う段名は verb が判定基準ファイルから読む**——worker が返す `**報告段名:**` は**照合用の副本であって検査の入力ではない**。**副本が欠落していても食い違っていても、検査は verb が読んだ段名で実施し、その事実〔一致 / 不一致 / 欠落〕を記録行の直下の字下げ行へ残す。**
  - **`anomaly`（入力の異常を示す行の検知）**: `anomaly.count` が 1 以上なら、良性の劣化と区別して `gate vocab --field finalize-input-anomaly` が返す接頭辞で始まる 1 行を実装サマリーへ残す（件数と拾ったトークンを書き、**段名の値そのものは書かない**）。**記録して先へ進み `pending` で止めない。**
  - **`row`（3 本目を委任した回に読む＝**本フェーズでは発火しない**）**: 3 本目の委任は review-flow の R1 が行うので、本フェーズの `row.verdict` は常に `not-run`（`criteria-unset`）であり、記録行には**未委任を表す値**を書く。以下の分岐は review-flow の R1 が finalize の報告表を読む回のための読み方である。`row.verdict` と継続委任の結果から記録行の値が一意に決まる。**値そのものは `gate vocab --field asset-safety-record-line` の `values` から選ぶ**（本手順は値域の逐語を持たない）。`row-ok` は pass、`row-absent` / `row-blank` は回復したか否かで分かれ、`row-pending` は既存の不完全経路へ、`row-badname` と `not-run`（`stage-name-unset` / `criteria-unreadable`）は検査未実施を表す値、`not-run`（`criteria-unset`）で**3 本目を委任しなかった回**は未委任を表す値を選ぶ。
    - **`criteria-unset` の 2 行は verb 出力では選び分けられない**（限界レジストリの `C10`＝`gate limits --sub finalize`）。**選ぶのは呼び出し側が自分の状況で行う**: 3 本目の委任をそもそも行わなかったのか、委任はしたが `--criteria` の値が差し込み前検査に落ちたのか。**verb 出力だけを見て前者の値（未委任）へ丸めない**——丸めると実際に委任した段が「未委任」として記録され、値域内なので **4d-2 の値域検査を素通りして緑になる**（fail-open）。**後者と `stage-name-ambiguous`・`ok: false`・verb 未解決は値域に対応する値が無い**ので、上記「判定不能の回の routing」に従う。
  - **`row-absent` / `row-blank` のときの復旧**: **段名で特定した当該段のみの継続委任**を finalize へ **1 回**行う（ブリーフに段名と結果ファイルの絶対パスを明示する）。**結果カラムが空の行も同じ経路へ回す**（空セルには `pending` が無いので `pending` 行起点では特定できない）。**再委任後もなお不在・空のままなら、記録行にその旨を残して先へ進む**（`pending` で止めない・人ゲートへも回さない）。**継続委任で渡す段名も verb が読んだ段名**とする——**副本と食い違っていた回は表に 2 行並ぶ**が、この重複は**不一致を可視化した結果であって解消ではない**ので、照合結果は記録行の直下の字下げ行へ残す。
- **記録行（委任の有無によらず毎回・分岐に依存しない必須出力）**: `gate vocab --field asset-safety-record-line` が返す接頭辞で始まる 1 行を実装サマリーへ残す。**3 本目を委任しなかった回も書く。** **結果カラムが空だった回を `pending` 残りとして記録しない**（起きていない事象の名前で記録すると復旧経路を取り違えさせる）。**副本の照合結果は同じ行へ併記せず、直下の字下げ行（`  - 副本照合: 一致 / 不一致 / 欠落`）へ書く**（**fail-silent**——字下げ行は走査母集団の外）。
- 欠落（不完全）なら作業ファイル（標準命名 `.shirokuma/tmp/finalize-<issue#>.md`・**絶対パス**）の `pending` 行から**残工程のみの継続委任**を行い、人手判断なしでチェーンを断絶させず完了まで運ぶ（`orchestration-discipline` C6）。**起点にすべき `pending` 行が無い欠落は段名起点の経路が扱う**（同じ欠落を 2 経路で二重に回さない）。

## 4d. 実装サマリーの確定と HTML 化判定

**4d-1（作業ファイル確定）→ 4d-2（記録行の検査）→ 4d-3（HTML 化判定）**の順で通す。

- **4d-1**: 実装サマリーの正本は **`.shirokuma/tmp/impl-summary-<issue#>.md`**（**絶対パス**・orchestrator が確定する）。本手順が定める記録行はすべてこの 1 本へ書き、4d-3 の HTML 化も段 5 の PR 本文要約も**この 1 本から派生させる**。**4c の結果ファイルと同じ規律を掛ける**——① orchestrator が絶対パスを確定し、worktree へ委任する回も**その作業ツリー配下の絶対パス**を使う ② 返ってきたパスを別のパスへ読み替えない。
  - **`.shirokuma/tmp/` は作業ツリーごとに別物**: `.gitignore` の対象で追跡されていないため、`git worktree add` で作った作業ツリーには**ディレクトリ自体が存在しない**。並行実装の回は**作業ファイルも作業ツリーごとに別ファイル**になる。**書き出す前にディレクトリの存在を確かめ、無ければ作る**（`mkdir -p`）。
  - **記録行レジストリ**: 本手順が定める記録行の全件と、その**必須性 / 値域の開閉 / 検査有無 / 検査しない理由 / 接頭辞 / 値域 / 雛形のプレースホルダ**は **`gate vocab --profile implement-4d-2` が正本**（本手順は表を持たない）。**区分は必須性 × 値域の開閉の 2 軸**で、各行の検査有無と検査しない理由はレジストリの `checked` / `whyNotChecked` が持つ。
  - **雛形**: `gate vocab --profile implement-4d-2` が返す `name`（接頭辞）と `placeholder` を並べて組み立てる（本手順は雛形を逐語で持たない）。**作業ファイルへは行頭〔字下げなし〕から書く。**
  - **行形式（全記録行に共通）**: ① **接頭辞は装飾込みで逐語固定**（`gate vocab` が返す `name` をそのまま使う）——装飾なしの接頭辞で行頭一致を取ると `completion-report-style` の KV 書式で書かれた行を**拾わない**。② **走査は行頭一致のみ**（**fail-closed**）。③ **値の後に併記しない**——同じ 1 行で「閉じた値域の一致検査」と「自由記述の併記」は両立しない。詳細は**直下の字下げ行**へ書く（**fail-silent**——字下げ行は走査母集団の外）。④ **雛形の値は値域外のプレースホルダにする**。ただし**値域内の正しい値を貼っただけの回は依然区別できない**。
  - **通したレーンの記録（両レーン共通・分岐に依存しない必須出力）**: `gate vocab --field lane` が返す接頭辞で始まる 1 行を残し、値は同 `values` から選ぶ（標準レーン／軽量レーン／途中で標準へ倒した回／通した段構成を確定できない回）。**行の有無をレーンに依存させない。** 書かなかった回は 4d-2 の `gate summary` が `no-row`（空値なら `blank`・値域外なら `out-of-range`）を返して pass が false になり、回復は書き直して 1 回だけ引き直す（人ゲートへは回さない・ループ上限も消費しない）。**限界**: 値を書くのは実行者自身なので**値域内の誤った値は素通りする**（**fail-silent**）。全件は `gate limits --sub summary` が正本。
  - **配布物変更の反映遅延を機械判定する**: **配布物（`plugin/**` の worker / skill 定義）の検査を変更した PR は、その変更が実行時に反映されないまま自分自身の品質ゲートを通りうる**（`gate asset-delay` の母集団は `plugin/**` で、プラグインのソースを別の置き場に持つ導入先では「変更なし」に倒れる）。**判定は base と作業ツリーだけで決まる**ので段 5 に依存せず、ここで確定させる。`shirokuma-flow gate asset-delay --worktree <作業ツリーの絶対パス> --base <base>`（base は段 3 の委任・4c の finalize と同一値）を引く。**base の差し込み前検査を verb 側の検査で代替しない**（**唯一の防御がこちら側にある**）。`verdict` が `bad-base` / `base-unresolved` を返した回は**判定不能側の値**を使い、`unchanged` へ読み替えない。記録行は `gate vocab --field asset-change-delay` が正本で、**行の有無を分岐に依存させない**。**この行が段 5 への受け渡し点**——段 5 は判定を取り直さずこの値だけを入力にする。**限界**: **PR 本文へ入れる 1 行を検査する機械段は無い**（転記で落ちても誰も検知しない＝fail-silent）。母集団と誤検出・見逃しの範囲は `gate limits --sub asset-delay` が返すので、**判定を主観で上書きしない**。
- **4d-2. 記録行の検査**: `shirokuma-flow gate summary --file <4d-1 が確定した作業ファイルの絶対パス>` を引く（**パスに埋め込む `<issue#>` は差し込み前に `^[0-9]+$` へ一致することを確かめる**）。**母集団はレジストリの全記録行**で、検査するのはそのうち検査有無が「有」の行の**存在と値域**、および**全記録行の接頭辞どうしの包含**（`clash`）である。
  - **読むのは 3 つ**: `fileMissing`（**不在は独立の判定値で返る**ので行を落とした回と区別が付く）／ `clash`（**あれば検査未実施**で pass に読み替えない）／ `rows[].verdict`（`ok` / `no-row` / `blank` / `out-of-range`）。
  - **欠落時の経路（新しい停止点を作らない）**: `no-row` / `blank` / `out-of-range` はいずれも**当該記録行を書き直して verb を 1 回だけ引き直す**。**なお欠落なら記録行に残して先へ進む**（`pending` で止めない・人ゲートへ回さない・共有のループ上限も消費しない）。`clash` と `fileMissing` は書き直しでは回復しないので**引き直さず**、それぞれを表す値を書く。
  - **記録行**: `gate vocab --field record-line-check` が返す接頭辞で始まる 1 行を残す。**この行自身は検査母集団に入らない**（値が検査の結果に依存するので循環する）。**拾った接頭辞・値そのものは書かない。**
  - **限界（全件の正本は `shirokuma-flow gate limits --sub summary` と `--sub finalize`・ここに列挙を写さない）**: 本検査が塞ぐのは「書く手順は通したが記録行を落とした／値域外を書いた」回だけである。**4d ごと飛ばした回は検知されない**（相関失敗＝**fail-silent**）。**判定結果を実装サマリーへ書き写す段は自己申告のまま**なので、**「機械検証（済み）」と呼べるのは別主体（`gate`）が出した判定そのものまで**である。**値域内の正しい値を貼っただけの回・転記や HTML 化で落ちた回は見ない**（**fail-open**）。
