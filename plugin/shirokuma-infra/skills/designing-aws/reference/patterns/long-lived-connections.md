# 長時間接続（SSE / ストリーミング / WebSocket）を通す

**接続の寿命**を設計時に決めるための節。**接続の寿命の判断は本ファイルにまとめてある。**

> **コンピュート選定とは別軸**: どのコンピュートを選ぶかでは決まらない。経路上の構成要素を選んだ後に、「その接続が何秒生きるか」を別途決める。ここを決めずに実装へ進むと、**後から効いて構成変更になる**（heartbeat 間隔とアイドルタイムアウトの関係はアプリとインフラの両側に跨るため、片方だけでは直せない）。

> **本ファイルの射程（ALB 経路のみ・他経路は未確認）**: 本ファイルは**接続の寿命という軸**を扱うが、**本ファイルが具体的に書いているのは ALB を通す経路だけ**である（コンテナフレーバー `Nextjs*Containers`・汎用コンテナ経路の ECS + ALB 等）。
>
> - **ALB を持たない経路の記述は本ファイルに無い。** `nextjs-deploy.md` の選定マトリクスには **ALB を構成に持たない construct**（既定の `NextjsGlobalFunctions` を含む）があり、**その経路で接続の寿命を何が決めるかは、この配布物の記述からは読めない（未確認**——確定させるには当該サービスの実測が要る）。どの construct が ALB を持つかは、同マトリクスの「構成要素」列を見る。
> - **この不明を「制限が無い」と読まない。** ALB を持たない経路でも §4 の 4 行は同じように書く。値が引けないなら「**引けなかった**」と書く（空欄にしない）。
> - **倒れる向き**: 未確認のまま長時間接続を出すと **fail-silent**——デプロイもヘルスチェックも緑のまま、接続だけが黙って切れる。本ファイルに ALB 以外の記述が**無いこと**は「制約が無いことを確認した」の意味を持たない（未調査と区別が付かない）。
>
> - **読めない範囲は `未確認` と明示し、確認手順は経路に依らず同じように行う。**

## 1. ALB の性質（設計の前提）

| 性質 | 帰結 |
|---|---|
| **ALB は応答をバッファしない**（ストリーミングをそのまま流す）——**中継値・未追試**（下記「出典」。この行を根拠に決めない） | ストリーミングが届かないときに **ALB を疑うのは最後**。先に前段（§3）とアプリ側の書き出し（フラッシュしているか）を見る |
| **アイドルタイムアウトがある**（無通信が続くと ALB が接続を切る）——**実効値は構成で動く**ので本ファイルは秒数を持たない（§2） | 何も流れない時間が続く接続は**切られる前提**で設計する（§2） |

- **「バッファしない」は不在の性質**なので、書かれていないと毎回調べ直しになる。**それでも、この行を根拠に決めない**——下の出典は第三者報告の中継で、この配布物の作成側では追試していない。**中継値は調べ直しの代わりにならない。** ストリーミングの可否が設計判断を左右する場面では、使う構成で自分で確かめ、確かめた／確かめていないを §4 に書く（値の書き方と読み方は `static-asset-delivery.md` §4「追試状況の書き方」）。
- **上の表から使ってよいのは「関係」だけ**——「ALB を疑う前に前段とアプリ側を見る」という**見る順序**（これは中継元に依存しない）と、「無通信が続けば切られうる」という**設計上の前提**（§2 の関係だけを使い、秒数は設計へ持ち込まない）。
- **出典**: AWS が Application Load Balancer をストリーミング / リアルタイム / WebSocket 向けに *"in streaming fashion instead of buffering requests and responses"* と説明している（`https://aws.amazon.com/blogs/aws/new-aws-application-load-balancer/`）。**第三者報告の中継で、この配布物の作成側では出典ページを追試していない。**

## 2. アイドルタイムアウトと heartbeat（**数値ではなく関係で決める**）

**タイムアウトの秒数を設計へ写さない。** 既定値も可変範囲も構成（設定値・リージョン・版）で動くので、**写した数字は静かに古くなる**。決めるのは次の関係だけ。

- **アプリからの送信間隔（heartbeat）< アイドルタイムアウト。**
- **安全側の目安は「タイムアウトの半分未満」**。1 回取りこぼしても次が間に合う余裕を持たせる（半分ぴったりでは、送信の揺らぎがそのまま切断になる）。

### どう決めるか

1. **その環境の実効タイムアウト値を引く**（既定のままか、明示的に設定したか）。**設計成果物にその値と、既定か明示かを書く。** 書かないと、後でタイムアウトを縮めた変更が heartbeat を壊しても、壊した側が気づけない。
2. **heartbeat 間隔をその半分未満に置く。** アプリ側の実装事項なので、設計成果物からアプリ側のタスクへ渡す。
3. **タイムアウトを上限近くへ上げて解決しない。** 切れない接続は、**切れたことに気づけない接続**の裏返しで、再接続の経路が一度も通らないまま本番へ出る。上げるとしても、§4 の再接続を先に設計する。
4. **接続の途中に「何も流れない時間」がどれだけできるかを見積もる。** 見積もれないなら heartbeat を置く（置かない判断をしてよいのは、無通信の上限を見積もれたときだけ）。

> **倒れる向き**: heartbeat が間に合わない構成は、**接続が黙って切れる**だけで、アプリのログにもデプロイの成否にも「失敗」として出ないことがある（fail-silent）。クライアント側に「切れた後どうなるか」が書かれていなければ、症状は「たまにデータが来ない」になり、原因へ辿り着かない。

## 3. 前段のバッファリング（**条件付き**——前段が無ければ何も足さない）

応答をバッファするリバースプロキシ（nginx 等）が経路に入ると、§1 の「ALB はバッファしない」があってもストリーミングは届かない。**この対処は前段がある構成でだけ要る。**

### 判定手順（この順で見る）

1. **クライアント ↔ ALB ↔ アプリの経路に、リバースプロキシが挟まっているか**を構成図で確認する（CDN・共有の入口・サイドカー・アプリ内蔵の前段を含む）。
2. **挟まっていない** → **何も足さない。ここで終わり。**
3. **挟まっている** → **その前段自身の設定で**応答バッファリングを切るのが第一手（設定に手が届く＝自分たちが管理している場合）。**CDN も「前段の設定」に含む**——CDN が経路にあるなら、まず CDN 側の配信設定でストリーミングをそのまま流せるかを見る。
4. **前段の設定に手が届かない**（マネージド・他チーム管理）ときの手は、**前段の種別で変わる**。手順 1 の母集団には CDN も入っているので、種別を先に確定する:
   - **nginx 系**（自前 nginx・nginx ベースの ingress / サイドカー）→ **アプリの応答ヘッダで前段へ指示する形**を使う（`X-Accel-Buffering: no`）。**このとき、どのプロキシに向けたヘッダなのかをコード側にコメントで残す。**
   - **CDN**（CloudFront 等）→ **このヘッダを対処とみなさない。** `X-Accel-Buffering` は**nginx 系が解釈するヘッダ**であって、CDN が解釈するとは限らない（**この配布物の作成側では CDN での挙動を追試していない**——効く／効かないのどちらも断定しない）。したがって残る手は **①CDN 側の設定で決める（手順 3 へ戻し、設定に手が届く経路を作る）②ストリーミングを CDN 経由で出さない（別ホスト名で CDN を迂回する）③CDN 経由で成立するかを自分で測ってから決める** のいずれかで、**選んだものを設計成果物に書く**。
   - **どちらでもない前段**（共有の入口・アプリ内蔵の前段）→ その前段が解釈する設定／ヘッダを確認する。**解釈するものが見つからなければ、CDN と同じ扱い**（①〜③から選ぶ）。
   - **共通**: **効かないヘッダを「対処した」として残さない。** 下の「無条件に付けない」がそのまま当てはまる——付けたヘッダは何も変えないのに、後から読む人には効いている設定に見える（fail-silent）。

> **無条件に付けない。** 前段が無い構成に付けたヘッダは何も変えないが、**動いているので誰も消さない**——後から読む人には「効いている設定」に見え、経路を変えるときの判断材料を汚す（fail-silent）。手順 1 の確認結果を設計成果物に書けば、後から「なぜ付いているか / 付いていないか」が読める。

- **中継の申告**: 「`X-Accel-Buffering: no` は ALB 背後で SSE を出すときの推奨」「バッファリングを有効にした nginx の経路でもこのヘッダで届いた」「このヘッダは nginx 系が解釈する」はいずれも**第三者報告の中継で、この配布物の作成側では追試していない**。**この行を根拠に「効く／効かない」を決めない。**
  - **手順 1〜3 は中継元に依存しない**（前段の有無で分岐せよ、という構造だけを使っている）。
  - **手順 4 の分岐だけは中継値に触れている**——「nginx 系が解釈するヘッダである」が中継なので、**nginx 系の枝で実際に届くかは自分で測る**。測っていないなら「測っていない」と §4 に書く。CDN の枝はこの中継値を**使わない**側（対処とみなさない）へ倒してあるので、中継が偽でも安全側に落ちる。

## 4. 設計成果物に書くこと（これが検知層になる）

本節の判断はいずれも**デプロイでは赤くならない**ので、書かれたものが唯一の照合材料になる。長時間接続を持つ設計では、次の 4 行を必ず含める。

- [ ] **実効アイドルタイムアウト値**と、それが既定か明示設定か。**ALB を持たない経路（既定 construct `NextjsGlobalFunctions` 等）で値の出所が引けなかったなら「引けなかった」と書く**（冒頭「本ファイルの射程」）。空欄にしない。
- [ ] **heartbeat 間隔**と、それがタイムアウトの半分未満であること。
- [ ] **前段のリバースプロキシの有無**（§3 手順 1 の結果）と、**有る場合はその種別**（nginx 系 / CDN / それ以外）と**取った手**（手順 3 か、手順 4 のどの枝か）。
- [ ] **接続が切れたときの挙動**——クライアントが再接続するか、取りこぼしたデータをどう埋めるか（再送・シーケンス番号・再取得のいずれか）。「切れない前提」と書かない。

> WebSocket も同じアイドルタイムアウト軸に乗る（無通信で切られる）。ping/pong を持つプロトコルでは §2 の heartbeat をその機構へ写せばよく、関係（間隔 < タイムアウトの半分）は変わらない。
