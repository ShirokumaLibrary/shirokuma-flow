# 静的資産の配信（配信経路の選定・配信属性）

CDN（CloudFront）から静的資産を配るときに設計時点で決める 2 つを扱う。**静的資産配信の判断は本ファイルにまとめてある。**

1. **配信経路** — CDN のオリジンをアプリにするか、オブジェクトストレージ（S3）にするか。
2. **配信属性** — 資産ごとの Content-Type・圧縮・キャッシュ。

> **コンピュート選定とは別軸**: どの construct / どのコンピュートを選んだかで本節の判断は決まらない。`aws-resource-patterns.md` の選定マトリクスと `nextjs-deploy.md` の construct 選定を終えた後に、そのどれを選んでいても本節を通る。

---

## 1. 配信経路の選定（A / B の 2 通り）

**どちらも選択肢として持つ。** 一方を構成の前提に埋め込まない。

| 軸 | **A: CDN → アプリのオリジン**（ALB / 関数 → アプリ） | **B: CDN → オブジェクトストレージ**（S3） |
|---|---|---|
| デプロイ段数 | **1 段**（アプリのイメージ / バンドルだけ） | **2 段**（イメージ / バンドル ＋ 資産の同期） |
| 新旧の版整合 | **構造的に揃う**（HTML と資産が同じ成果物に入る） | **揃わない窓ができる**。同期と切替の順序を設計で決めないと、新 HTML が未同期の資産を指す／旧 HTML が消えた資産を指す |
| オリジン負荷 | 資産のリクエストがオリジンへ届く（CDN のキャッシュに乗った後は減る） | オリジンへ届かない |
| CORS | 同一オリジンなら不要 | **別オリジンになる**。フォント・WebAssembly・ES モジュール等、取得経路が CORS を要求する資産では必要 |
| アプリ側の前置 | 不要（既定のまま） | **必要**（下記「2. プレフィックスの受け口」） |
| Content-Type を決める場所 | アプリのサーバ | 同期ツールとストレージ側のオブジェクトメタデータ |

### どう決めるか

上から順に見て、最初に当たったところで決める。

1. **資産のリクエストがオリジンの容量計画を動かすか？** 動かす（資産の総量・同時リクエストでオリジンをスケールさせたくない・オリジンをアイドルへ落としたい）なら **B**。ただし下記「B を選んだときに追加で決めること」を**全部決めてから**採る。
2. **CDN が使えない環境か？** 使えないなら A しか成立しない（B は CDN を前提にした経路）。
3. **どちらでも成立する** → **A へ寄せる。** 1 段で済み、版整合の窓が構造的に生じない。B へ移す必要が出たときは、受け口（次節）を持っていれば設定値 1 本と同期ステップ 1 本の追加で移せる（**逆向き A ← B も同じコスト**）。

> **これは「B を選ぶな」ではない。** 3 は同点のときの寄せ先を決めているだけで、1 に当たったなら B が正しい。**「決めなかった」を残さない**ことが本節の要求である。

### B を選んだときに追加で決めること

決めずに B へ進むと、下の 4 つはいずれも**本番で初めて現れる**（デプロイは成功する）。

| 決めること | 決めないとどうなるか |
|---|---|
| **同期と切替の順序**（新資産を先に置き、HTML を配る成果物の切替を後にする） | 切替が先だと、新 HTML が未同期の資産を指す窓ができる |
| **旧版資産の保持期間**（切替と同時に消さない） | キャッシュ済みの旧 HTML と、切り戻した先が、消えた資産を指す |
| **CORS の許可元** | 上表のとおり別オリジンになる。フォント・WebAssembly 等がブラウザ側でだけ失敗する |
| **Content-Type をどこで決めるか**（同期ツールの推測に任せるのか、明示するのか） | 下記「3. 配信属性」の軸 1 と同じ壊れ方をする |

> **倒れる向き（経路 B 全体）**: 上の 4 つはどれも**配信は 200 で返る**まま壊れる（fail-silent）。デプロイの成否・CDN のメトリクスには出ない。**設計成果物に上表 4 行の決定を書く**こと自体が唯一の検知層になる。

## 2. プレフィックスの受け口（A / B のどちらでも要る）

**配信元のベース URL を外から受け取る口をアプリ側に 1 つ作る。** これがあると A / B の違いが**設定値の差**に収まり、実装差にならない。

- **1 つの値**（資産のベース URL）を受け取り、**①フレームワークの資産プレフィックス設定**と、**②アプリが「フレームワークがプレフィックスを掛けない静的ファイル」を参照している箇所**の両方へ同じ値を通す。
- **未設定なら空文字＝同一オリジン（A）**になるようにする。既定が A、値を入れると B。
- **設計成果物に「受け口の有無」を必ず書く。** 書かないと実装側は既定（同一オリジン直書き）で組み、後から B へ移すときに参照箇所の全数修正になる。

### なぜ受け口が 1 つでは足りない形になりやすいか（Next.js の具体）

- Next.js の `assetPrefix` が掛かるのは**ビルド生成物（`_next/static`）だけ**で、`public/` 配下には掛からない。Next.js の同梱ドキュメントが「プレフィックスは利用者側で前置する」と案内している（**第三者報告の中継・この配布物の作成側では追試していない**）。
- 片側だけ設定すると「**チャンクは CDN・`public/` の資産はオリジン**」という半端な状態になる。**両方 200 で返るので赤くならない**（fail-silent）。気づくのは、オリジンをアイドルへ落としたときか、`public/` だけキャッシュが効かないと分かったとき。
- したがって受け口は「フレームワークの設定へ渡す」だけでは閉じない。**②の参照箇所を通す関数（またはコンポーネント）を 1 つ用意し、`public/` の参照をそれ経由に限る**——これが「受け口 1 つ」の実体。

### 受け口の値をどこから渡すか（切替コストが決まる）

- **ブラウザへ露出する変数（Next.js の `NEXT_PUBLIC_*` 等）はビルド時に静的置換される。** この受け口をそこに置くと、**配信元を切り替えるたびにイメージ / バンドルの作り直しが要る**。
- 決め方: **切替を運用手順（再ビルドを伴わない）で行いたいなら、サーバ側で読んで描画時に渡す形にする。** 再ビルドを許容するなら、ビルド時変数のままでよい——ただし**切替手順書に「イメージの作り直し」を明示的に含める**。どちらかを選んで書く（放置は前者を意図しないまま選ぶことになる）。
- 変数の区分そのもの（何がブラウザへ露出するか）は `env-mapping.md`（同一 patterns ディレクトリ）の「Next.js の変数区分」を見る。

## 3. 配信属性（Content-Type・圧縮・キャッシュ）

**A / B のどちらを選んでも要る。** 3 つとも「既定で何かが決まってしまう」ため、決めなかったことが**決定として残る**。

| 属性 | 何もしないと何が決めるか | 明示が要るのはどこか | 誤ったときの現れ方 |
|---|---|---|---|
| **Content-Type** | 同期ツール / サーバが**拡張子から推測**する | 推測表に無い・推測が誤る拡張子。ブラウザが型を見て経路を変える資産（例: WebAssembly のストリーミングインスタンス化は `application/wasm` を要求し、違う型なら失敗する） | **本番のブラウザで初めて失敗する**（fail-silent）。配信自体は 200 で返る |
| **圧縮**（gzip / Brotli） | CDN の自動圧縮は**対象 Content-Type の一覧**で決まる。一覧に無い型は非圧縮で出る | 一覧に無い型。事前圧縮したファイル（`.gz` / `.br`）を置く場合は `Content-Encoding` と、非対応クライアントへのネゴシエーション | **赤くならない**（fail-silent）。転送量とレイテンシだけが増える |
| **キャッシュ** | CDN / ブラウザの既定 | ファイル名に内容ハッシュが入るか否かの分岐 | 短すぎればコストと初回レイテンシ。長すぎれば**古い資産が消えず、切り戻しても戻らない** |

### どう決めるか

資産を 2 群に分けてから、3 つを順に決める。

**群分け**: ファイル名に**内容ハッシュが入るか**（ビルドが生成する資産は通常入る／`public/` に手で置くファイルは通常入らない）。

1. **キャッシュ** — ハッシュ入り → **長期 ＋ `immutable`**。ハッシュ無し → **短期 ＋ 再検証**。**迷ったらハッシュ無し側（短期）へ倒す**——長すぎる側の誤りは切り戻しでも直らないため。
2. **Content-Type** — **配信側で 1 回、実際にヘッダを確認する**（応答ヘッダを見るだけでよい）。**「拡張子から推測されるはず」で済ませない**——外れても 200 で返るので、確認しない限り気づく契機が無い。推測が外れる型は、同期時のメタデータ指定 / サーバ側の MIME 設定で**明示する**。
3. **圧縮** — その Content-Type が CDN の自動圧縮の対象一覧に入っているかを確認する。入っていなければ **①一覧を広げる ②事前圧縮を置いて `Content-Encoding` を付ける ③非圧縮を受け入れる** のどれかを**選んで設計成果物に書く**（何もしないのは ③ を黙って選ぶこと）。

> **倒れる向き（本節全体）**: 3 属性はどれも誤っていても**デプロイもヘルスチェックも緑**である（fail-silent）。手順 2 の「1 回ヘッダを見る」以外に検知層は無い。**確認したことを設計成果物に書く**（確認していない資産があるなら、そう書く）。

### マネージドな構成を選んだとき

`nextjs-deploy.md` の cdk-nextjs 経路のように、静的資産の配置を construct が自動構成する構成では、上の 3 属性のうち**どこまでを construct が決め、どこからが利用者に残るのかが、この配布物の記述からは読めない**（**未確認**——確定させるには上流ライブラリ側の実測が要る）。

- **この不明を「決まっている」と読まない。** 自動構成の経路でも、手順 2（応答ヘッダを 1 回見る）は**同じように行う**。推測が外れる型を配るなら、上書きの口が construct にあるかをピン版の型定義で照合する（版照合は `nextjs-deploy.md` の規律に従う）。
- 汎用コンテナ経路・経路 B は自前で決めるので、本節がそのまま効く。

## 4. 追試の状況（どこまでが誰の実測か）

本節の判断軸は、下記の報告を**中継**して組み立てている。**関係と手順は中継元に依存しないが、個別の事実は下表のとおり追試していない。**

### 追試状況の書き方（infra skill 群の reference で共通・値の意味と読み手が次にすること）

「追試」の列や備考に出る値は次の 3 つで、値の後ろに補足が付くことがある（例: `要確認（未追試）。本物の S3 / CDN では追試が要る`）。

| 値 | 意味 | 読み手が次にすること |
|---|---|---|
| `要確認（未追試）` | **中継元がある**主張で、この配布物の作成側が追試していない | 使う版と実サービスで自分で追試する |
| `未確認` | **出所そのものが無い**（誰も測っていない／中継元も測っていないと申告している） | 一次調査から始める |
| `実測（YYYY-MM-DD）` | この配布物の作成側が、その日に実際に測った | 自分の版・対象がその日の測定と同じかを確かめる |

- **追試状況を書くときは、この 3 値だけを使う。** 空欄も `—` も使わない。値の後ろに補足を書いてよいが、**値そのものは言い換えない**。自分の設計記録で同じ形の表（中継値を並べ、追試状況を添える表）を作るときも、この 3 値を使う。
- 自分の設計記録の表で追試したら `要確認（未追試）` / `未確認` を `実測（YYYY-MM-DD）` へ置き換える。版・対象が変われば `実測（…）` を `要確認（未追試）` へ戻す。
- **`要確認（未追試）` と `未確認` を混ぜない。次にやることが違う**: 前者は「誰かは測ったらしい」ので追試、後者は「誰も測っていない」ので一次調査。
- **倒れる向き**: 表に**行が無いこと**は「確認済み」の意味を持たない（未調査と区別できない）＝ **fail-silent**。

| 主張 | 出所 | この配布物の作成側での追試 |
|---|---|---|
| 資産プレフィックスの設定はビルド生成物にだけ掛かり、`public/` 配下には掛からない（利用者側で前置が要る） | フレームワークの同梱ドキュメント。第三者報告の中継 | **要確認（未追試）** |
| `.wasm` の取得で CORS が要る／同期ツールが拡張子から `application/wasm` を推測する／同一オリジンのフォールバックが 200 で残る | 第三者報告の中継。**測定環境は LocalStack Community の S3** で、**CDN（CloudFront）は当該環境に無く未測定** | **要確認（未追試）**。本物の S3 / CDN では追試が要る |
| ブラウザへ露出する変数がビルド時に静的置換される | 同上（第三者報告の中継） | **要確認（未追試）** |
| マネージド construct が Content-Type / 圧縮 / キャッシュのどこまでを決めるか | 出所なし（上流ライブラリの実測が要る。§3「マネージドな構成を選んだとき」） | **未確認** |
| CDN のキャッシュ挙動／ブラウザでの WebAssembly ストリーミングインスタンス化の成否／本番 CDN での `Cache-Control` 戦略 | 中継元が明示的に「測っていない」と申告した範囲＝出所なし | **未確認** |

> **上表を根拠に「動く／動かない」を断定しない**——使う版と実サービスで自分で確かめる。
