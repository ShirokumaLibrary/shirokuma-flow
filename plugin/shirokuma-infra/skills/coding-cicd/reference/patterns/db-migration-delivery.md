# DB マイグレーション適用パターン

デプロイ前チェックリストの「マイグレーション計画 | DB スキーマ変更がある場合は前後互換性を確認」と「ロールバック可否 | 不可逆な変更（DB マイグレーション）の有無を確認」が**何を確認するか**を言うのに対し、本ファイルは**どう打つか**を決める。デプロイ戦略の選択（[deploy-strategies.md](deploy-strategies.md) 冒頭の戦略比較マトリクス）が済んだ後に読む。

> **配布物としての射程**: ここに置くのは**選択肢と判断軸**であって、どれを選ぶかではない。**選択そのものはプロジェクト側の決定**として記録する（ADR・設計ドキュメント・`CLAUDE.md` のいずれか、そのプロジェクトの決定記録の置き場所に従う）。決めた結果を書き残さないと、次のスキーマ変更で同じ判断がやり直される。
>
> **数値を持たない理由**: 実行媒体の制限（実行時間の上限・同時実行・VPC 接続の設定項目名）は AWS 側の仕様で**版によって動く**。本ファイルは**関係**（何が何に効くか）だけを書き、具体値は持たない。選定時に公式ドキュメントと**実アカウント**で確認すること。

## 決め方（この順に決める）

前の決定が次の選択肢を絞るので、順序を入れ替えない。

1. **デプロイ戦略**（決定済みの前提）→ 新旧バージョンが**同時に走る窓があるか**が決まる。
2. **打つ位置**（軸 2）→ 戦略が要求する互換性（前方 / 後方）が決まる。
3. **失敗時の扱い**（軸 3）→ 位置が決まって初めて「デプロイを止める」が選べるようになる。
4. **ネットワーク**（軸 4）→ 実行媒体の候補が絞られる。
5. **実行媒体**（軸 1）→ 3 と 4 を満たす媒体を選ぶ。

## 軸 1: 実行媒体

| 媒体 | VPC 内に置けるか | 実行順序をパイプラインで制御できるか | 選ぶときに見るもの | 倒れる向き |
|------|----------------|--------------------------------|-----------------|-----------|
| ECS one-off task（`RunTask`） | 置ける（タスクのネットワーク設定でサブネットとセキュリティグループを指定する） | できる（起動して**終了を待ち、終了コードを読む**なら） | アプリと同じイメージ・同じ実行環境でマイグレーションを打てるか。タスク定義を CD 側で管理できるか | **起動しただけで待たない実装は fail-open**（失敗しても後続のデプロイが進む）。終了待ちと終了コード判定を必ず書く |
| CodeBuild ステップ | 置ける（プロジェクトに VPC 接続を設定する） | できる（パイプラインのステップそのもの） | ビルド定義に DB 接続情報を渡す経路があるか。ビルド環境のイメージにマイグレーションツールが入るか | ステップの失敗がそのままパイプラインの失敗になる＝**fail-closed**。ただし失敗を無視する記述（終了コードを捨てる形）を入れると fail-silent へ反転する |
| Lambda | 置ける（関数に VPC 接続を設定する） | できる（同期呼び出しで結果を読むなら） | **実行時間の上限**（マイグレーションが上限を超えないか）。上限値は版で動くので実測する。デプロイ済み関数の版とマイグレーション本体の版がずれないか | 上限で切れた場合は**部分適用が残る**。切れたことが「失敗」として返るかは呼び出し方次第で、非同期呼び出しなら fail-silent |
| init container（アプリタスク内でアプリ本体より前に実行） | 置ける（アプリタスクと同じ配置） | **できない**（デプロイの一部として暗黙に走る） | タスクが**同時に何個起動するか**。複数同時起動なら同じマイグレーションが並行実行される。ツール側に排他（アドバイザリロック等）があるか | 排他が無いと**並行実行が黙って走る＝fail-open**。またマイグレーション失敗＝コンテナ起動失敗になるので、戦略によっては旧版へ自動で戻らずタスクが再起動を繰り返す |
| 踏み台からの手動実行 | 置ける（踏み台を VPC 内に置く） | できない（人の操作） | **実行の記録がどこに残るか**。誰がいつどの版を打ったかを後から照合できるか | **fail-silent**。打ち忘れ・二重実行・打った版の取り違えが、どの機械段にも引っかからない。恒久の手段として選ばない（緊急時の退避手段としてだけ残す） |

**どう決めるか**: 上表を上から見て、**軸 4 のネットワーク要件を満たし、軸 3 で選んだ失敗時の扱いを実装できる最初の媒体**を採る。同点なら「アプリと同じイメージで打てる媒体」を優先する（マイグレーション本体とアプリコードの版ずれが構造的に起きないため）。**「踏み台からの手動」だけは恒久の選択肢に含めない**——上表の倒れる向きが fail-silent で、他の軸をどう決めても検知層が付かない。

## 軸 2: 打つ位置（順序）

**チェックリストの「前後互換性を確認」は、この順序に従属する**——どちらの互換性が必要かは、打つ位置と戦略で決まる。順序を決めずに「互換性を確認」だけを実施しても、何と何の互換を見るのかが定まらない。

スキーマ変更は 3 段に分けて、**別々のデプロイ**で打つ。

```
段 1（拡張）: 旧コードでも新コードでも動くスキーマ変更を、コードのデプロイより前に打つ
                 例: 列の追加（NULL 可・既定値あり）・新テーブル・インデックス追加
                 ↓
段 2（切替）: 新コードをデプロイする（スキーマは触らない）
                 ↓
段 3（縮約）: 旧コードが完全に退いた後で、後始末を打つ
                 例: 列の削除・NOT NULL 化・リネームの完了・旧テーブルの削除
```

| 位置 | 必要な互換性 | 成立条件 |
|------|------------|---------|
| 段 1（デプロイ前） | **前方互換**（**旧**コードが**新**スキーマで動く） | 変更が追加のみであること。旧コードが知らない列・テーブルが増えても壊れないこと |
| 段 2（デプロイと同時） | 新旧コードが同時に走る窓では**双方向**の互換が要る | 戦略が同時実行の窓を持つ（Rolling / Blue/Green / Canary）なら、その窓の間ずっと両方が動くこと |
| 段 3（デプロイ後） | **後方互換は不要**（旧コードはもう居ない） | **旧コードが 1 インスタンスも残っていないこと**を確認してから打つ。ロールバックの可能性が残っている間は打たない |

- **段 1 と段 3 を同じデプロイに混ぜない**。混ぜると、そのデプロイは**ロールバック不能**になる（コードは戻せてもスキーマは戻らない）。チェックリストの「ロールバック可否 | 不可逆な変更（DB マイグレーション）の有無を確認」はここを見ている。
- **リネームは「リネーム」として打たない**——追加（段 1）→ 両書き（段 2）→ 削除（段 3）に分解する。単一の `RENAME` は旧コードを即座に壊すので、同時実行の窓を持つ戦略と両立しない。
- **段 3 を打つ前に、旧コードが退いたことを実測する**。「デプロイが成功した」は「旧タスクが全部入れ替わった」を意味しない。サービス側の実行中リビジョンを確認してから打つ。
- **倒れる向き**: 段の分割を守らなかったことは**デプロイ時には赤くならない**（新コードだけを見れば整合しているため）。壊れるのは切替の窓の中を通ったリクエストと、切り戻したときで、いずれも**後から fail-silent に現れる**。

## 軸 3: 失敗時の扱い（デプロイ戦略ごと）

「デプロイを止める」を選べるのは、**マイグレーションがデプロイジョブより前段にあるとき**だけ（軸 2 の段 1）。段 2 の位置に置いた時点で、この選択肢は消える。

| 戦略 | 既定の打つ位置 | マイグレーション失敗時の既定 | アプリの状態 | 倒れる向き |
|------|--------------|--------------------------|-----------|-----------|
| Rolling | 段 1（デプロイ前） | デプロイジョブを**開始しない**（後続ジョブを止める） | 旧版のまま稼働継続 | fail-closed。新機能は出ないが可用性は落ちない |
| Blue/Green | 段 1（Green の起動前） | トラフィックの**切替を行わない**。Green は起動しない | Blue（旧版）が処理し続ける | fail-closed。ただし Blue と Green が**同じ DB を共有する**ので、段 1 の変更は Blue でも動く形に限る（前方互換） |
| Canary | 段 1（重み付けの開始前） | 重み付けを**動かさない**（全トラフィックが旧版） | 旧版のまま稼働継続 | fail-closed。段階リリース中は新旧同居の窓が最も長いので、互換の要求が最も厳しい |
| Recreate | 停止中（旧版停止後・新版起動前） | 新版を**起動しない**。停止のまま人の判断を待つ | **停止（ダウンタイム継続）** | fail-closed。不整合は出ないがダウンタイムが伸びる。伸びる上限を事前に決めて承認ゲートに紐づける |

- **どの戦略でも既定は fail-closed（デプロイを止める）**。「アプリを新版のまま進める」は選ばない——スキーマが揃っていない状態で新コードが動くのが最も高くつく壊れ方だから。
- **部分適用が残るかを事前に確認する**。マイグレーションが途中で失敗したとき、適用済みの分が残るか全部戻るかは**マイグレーションツールと DB エンジンの組み合わせで決まる**（DDL がトランザクションに入るかどうかが効く）。**ここでは断定しない**——使うツールとエンジンで実際に途中失敗させて確かめること。部分適用が残る構成なら、**再実行が安全（冪等）であること**が追加の要件になる。
- **失敗の検知は終了コードで行う**。ログの文字列一致で判定しない。パイプの先に別コマンドを繋ぐと終了コードが落ちる形があるので、**マイグレーションの実行行は終了コードがそのままジョブへ伝わる形で書く**。
- **倒れる向き（この節自体の）**: 「止める」を実装したつもりで終了コードを見ていない形は、**緑のまま通る（fail-silent）**。実装したら 1 度**わざと失敗するマイグレーションで実走**し、後続ジョブが実際に止まることを確認する。

## 軸 4: ネットワーク

DB をプライベートサブネットに置く構成（`designing-aws` のアンチパターン表が要求する形）では、**実行媒体が VPC 内に居ないと DB に到達できない**。

| 選択肢 | 成立するか | 見るもの |
|-------|----------|---------|
| 実行媒体を VPC 内（プライベートサブネット）に置く | **既定**。軸 1 の全媒体が VPC 接続を設定できる | 媒体の**セキュリティグループ**からの inbound だけを DB 側で許可しているか。イメージ取得・シークレット取得の egress 経路（NAT / VPC エンドポイント）があるか |
| セルフホストランナーを VPC 内に置く | 成立する | ランナーの権限がマイグレーション実行に必要な範囲へ絞られているか。ランナー自体の管理コストを引き受けられるか |
| 踏み台を経由してポートフォワードする | 成立する（**緊急時のみ**） | 軸 1 の「踏み台からの手動実行」と同じ倒れる向き（fail-silent）を引き継ぐ |
| DB をパブリックに開いて外部のランナーから接続する | **選ばない** | — |

- **最後の選択肢を「疎通しないときの是正」として採らない**。接続できない状態は**接続タイムアウトで赤くなる＝fail-closed で気づける**が、DB を公開して通した場合は**通ってしまい、赤くならないまま残る＝fail-open**。**赤を消す最短手が、検知できない状態への移行になっている**——ここが本軸で最も踏みやすい。
- **どう決めるか**: 軸 1 で選んだ媒体を VPC 内に置く設定を入れる。それが設定できない媒体なら**媒体のほうを変える**（DB の公開範囲は変えない）。
- **シークレットの経路も VPC の内側で閉じる**。接続情報を CD のログ・環境変数に平文で置かず、シークレット管理サービスから実行時に取得する。取得先へ到達するための VPC エンドポイントが要ることがある（構成依存・実測する）。

## 実装後の確認

- [ ] 打つ位置（段 1 / 段 2 / 段 3）が、そのデプロイの変更内容と一致している
- [ ] 段 1 と段 3 が同じデプロイに混ざっていない（混ざっていたらロールバック不能として扱う）
- [ ] マイグレーションの失敗が**終了コードで**後続ジョブへ伝わる（わざと失敗させて実走確認済み）
- [ ] 実行媒体が VPC 内に居る。DB 側の inbound が実行媒体のセキュリティグループに限定されている
- [ ] 実行媒体・打つ位置・失敗時の扱いの 3 点が、プロジェクト側の決定記録に書かれている
