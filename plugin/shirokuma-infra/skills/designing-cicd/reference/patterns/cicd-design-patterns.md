# CI/CD 設計パターン

CI/CD パイプライン設計の決定フレームワーク詳細。パイプライン構成・デプロイ戦略・環境分離・OIDC 認証のパターン集。SKILL.md 本文の判断骨格を補う設計リファレンス。

## パイプライン構成設計

### ワークフロー分類

| ワークフロー | トリガー | 目的 |
|-----------|---------|------|
| CI（テスト） | PR、push | lint → test → build の品質チェック |
| CD（デプロイ） | main/develop マージ | 環境別デプロイ |
| 手動実行 | workflow_dispatch | ホットフィックス、ロールバック |
| スケジュール | cron | 定期的なセキュリティスキャン等 |

### CI パイプライン設計

| ジョブ | 実行条件 | 並列化可否 |
|-------|---------|----------|
| lint | 全 PR | 可（test と並列） |
| typecheck | 全 PR | 可 |
| test | 全 PR | 可（lint と並列） |
| build | lint + test 通過後 | 不可（依存） |
| security-scan | cron / PR | 可 |

### CD パイプライン設計

| 環境 | トリガー | 承認フロー |
|-----|---------|----------|
| dev | develop ブランチマージ | 不要（自動） |
| staging | develop マージ or 手動 | 任意 |
| prod | main ブランチマージ | 必須（manual approval） |

## デプロイ戦略選択

### 戦略比較

| 戦略 | 概要 | ダウンタイム | ロールバック速度 | 適用場面 |
|-----|------|------------|----------------|---------|
| Rolling | 旧バージョンを順次置き換え | なし | 遅い | 通常のアプリ更新 |
| Blue/Green | 並列環境を切り替え | なし | 高速 | 本番ゼロダウンタイム要件 |
| Canary | 一部トラフィックから段階的に切り替え | なし | 高速 | 高リスク変更、A/B テスト |
| Recreate | 全停止してから起動 | あり | 不要 | DB マイグレーション等 |

### 選択基準

```
高可用性要件あり → Blue/Green または Canary
段階的なリリース要件あり → Canary
コスト重視・シンプル → Rolling
DB スキーマ変更を伴う → Recreate（メンテナンスウィンドウ設定）
```

> **「DB スキーマ変更 → Recreate」は最も単純な既定であって、唯一の解ではない。** ダウンタイムを許容できない場合、スキーマ変更を**拡張 → コード切替 → 縮約**の 3 段に分けて別々のデプロイで打てば、Rolling / Blue/Green / Canary とも両立する。**Recreate を選ばない場合は、設計段階で下の「DB マイグレーション適用設計」の 4 軸を決める**（決めずに実装へ渡すと、実装側が毎回ゼロから決めて散る）。

## DB マイグレーション適用設計

DB を持つプロジェクトでは、デプロイ戦略の選択に加えて次の 4 軸を**設計段階で決めて成果物に残す**。選択肢・判断軸・戦略別の失敗時の扱い・倒れる向きの詳細は、**`coding-cicd` スキルの `reference/patterns/db-migration-delivery.md`**（設計時にも読んでよい）を正本とする。ここでは決める項目だけを挙げる。

| 軸 | 決めること | 設計成果物への残し方 |
|----|-----------|------------------|
| 実行媒体 | ECS one-off task / CodeBuild ステップ / Lambda / init container のどれで打つか（手動実行は恒久の選択肢にしない） | 「主要決定事項」に選択と根拠 |
| 打つ位置 | 拡張（デプロイ前）／切替／縮約（デプロイ後）の 3 段をどう分けるか | 「CD 環境別デプロイ設計」に段の割り当て |
| 失敗時の扱い | 失敗時にデプロイを止める（既定・fail-closed）ことを、選んだ戦略でどう実現するか | 「主要決定事項」に戦略との対応 |
| ネットワーク | 実行媒体を VPC 内のどこに置くか。DB 側の inbound をどのセキュリティグループに限定するか | 「主要決定事項」に配置と許可元 |

**倒れる向き**: 4 軸のどれかを決めずに実装へ渡しても、**設計レビューでは赤くならない**（設計成果物の他の欄は埋まるため）。実装側で fail-silent な形（失敗が後続ジョブへ伝わらない・手動実行が既定になる）へ落ちて初めて現れる。下のレビューチェックリストで機械的に拾う。

## 環境分離設計

### GitHub Environments 設計

| 環境名 | 保護ルール | シークレット |
|-------|----------|-----------|
| `dev` | なし | `DEV_ROLE_ARN` |
| `staging` | 任意（レビュワー承認） | `STAGING_ROLE_ARN` |
| `production` | 必須（レビュワー承認） | `PROD_ROLE_ARN` |

GitHub Environments の `environment:` 名は GitHub Settings の環境名と完全一致が必要。

### OIDC 認証設計

IAM アクセスキーを使わず、OIDC フェデレーションで一時クレデンシャルを取得する。

```
GitHub Actions → OIDC トークン発行 → AWS STS（AssumeRoleWithWebIdentity）→ 一時クレデンシャル
```

IAM ロール信頼ポリシーに `token.actions.githubusercontent.com` を追加する。

## レビューチェックリスト

- [ ] OIDC 認証を使用し、IAM 長期クレデンシャルをシークレットに持たない
- [ ] `permissions` が最小権限（`id-token: write`, `contents: read`）
- [ ] prod 環境に manual approval が設定されている
- [ ] ジョブ並列化で CI 時間が最適化されている
- [ ] ロックファイルでキャッシュが有効化されている
- [ ] `needs:` による依存関係が正しい
- [ ] ブランチ戦略と CD トリガーが一致している
- [ ] DB スキーマ変更を伴う場合、「DB マイグレーション適用設計」の 4 軸（実行媒体・打つ位置・失敗時の扱い・ネットワーク）が**すべて**決まって成果物に残っている（DB を持たないプロジェクトなら「該当なし」と明記する。**空欄は「決めた」と読めない**）
