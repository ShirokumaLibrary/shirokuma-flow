# SSE（Server-Sent Events）でサーバー → ブラウザへ流す

Next.js（App Router）の route handler から SSE を出すときに**外せない関係**だけを書く。本ファイルは**実装側の節**で、どの通知機構を選ぶか（経路選定）と、接続がどれだけ生きるか（接続寿命）はここでは決めない——それぞれ別ファイルで扱う（末尾「参照」）。

> **ここでは `SSE` は Server-Sent Events を指す。** 同じ略語が S3 の暗号化方式（Server-Side Encryption）にも使われるので、設計文書で並べて書くときは略さない。

> **数値は載せていない。** 到達時間・購読者数などの実測値は構成で動く。ここに書くのは**関係**だけで、値が要る判断は自分の構成で測る。

---

## 1. 外すと成立しない関係

| 事項 | 関係 |
|---|---|
| ランタイム | route handler に `export const runtime = "nodejs"` を**明示する**。DB ドライバのように Node の API に依る購読機構は Edge ランタイムでは動かず、**経路ごと成立しない**（部分的に遅くなるのではなく、動かない） |
| 購読の持ち方 | 購読はプロセスにつき 1 つだけ持ち、**プロセス内で fan-out** する。接続に紐づく購読状態（RDB の `LISTEN` 等）は、借りて返すプール接続とは両立しない |
| 取りこぼしの埋め方 | サーバーが `id:` を付ければ、ブラウザは再接続時に `Last-Event-ID` を自動で送る。**クライアント側の追加実装が要らないのはこの形のときだけ**で、`id:` を付けないなら再送機構を自分で作ることになる |
| セッション固定 | 購読が DB / pub/sub 側で起きるなら、リクエストがどのタスクへ振られても同じイベントが届く＝**ロードバランサの sticky session を前提にしない**（前提にすると、要らない制約が構成へ固定される） |
| 誰へ流すかの絞り込み | **プロセス内 fan-out は、絞らなければ全接続へ全イベントが届く。**接続ごとに、その要求者が受け取ってよいイベントかを判定してから書き出す。**購読を 1 つへ寄せる判断と、認可を接続ごとに行う判断は独立**で、前者だけを採ると後者が消える（購読が 1 つなので絞り込みも 1 箇所で済む、と読めてしまう）。テナントが分かれる構成では、**この判定がテナント分離そのもの**になる |
| `Last-Event-ID` の扱い | **`Last-Event-ID` はクライアントが送るヘッダ＝要求者が自由に決められる入力である。**catch-up の起点に使う前に、**その値が要求者の見てよい範囲に収まるか**を検証し、**要求者の権限で絞った範囲からだけ**再送する。絞らないと、値を差し替えるだけで他の要求者・他テナントの過去イベントを引ける（id 列は単調増加＝推測できる）。検証を挟まず DB クエリへ渡す形は注入面にもなる |

- **`Last-Event-ID` を使うには catch-up の基準になる単調増加の id 列が要る。** 追記テーブルなど、それを持たないプロジェクトでは基準を別に用意するところから設計する（`id:` を付けるだけでは埋まらない）。

---

## 2. 順序: **購読を張ってから catch-up を流す**

1. **先に購読を張る**（通知を受け取れる状態にする）。
2. **そのあとで** `Last-Event-ID` を起点に catch-up を流す（起点の値は §1 のとおり**検証してから**使い、再送の範囲は要求者の権限で絞る）。
3. 購読から来たものと catch-up から来たものを、**id で冪等に**処理する。

**逆順にすると漏れる。** catch-up のクエリを投げてから購読を張ると、その隙間に発生したイベントは catch-up の結果にも購読にも入らない。この順なら最悪でも同じイベントが二重に届くだけで、手順 3 の冪等処理が吸収する。

> **倒れる向きは fail-silent**——順序を逆にしても接続は張れ、ヘルスチェックは通り、テストも緑のまま通る。症状は「たまにイベントが来ない」で、再現しないので原因へ辿り着かない。**この順序は通知機構の選択に依らない**（RDB の `LISTEN`/`NOTIFY` でも Redis / Valkey の pub/sub でも同じ）ので、機構を差し替えても同じ順序を守る。

> **認可を落としたときも同じく fail-silent**——絞り込みを書き忘れても接続は張れ、自分のイベントは届き、開発者が自分の口座で試す限り正しく見える。**症状は「余分に届く」ことなので、受け取った側が黙って捨てれば表に出ない。**自分以外の要求者のイベントが届かないことを、**別の要求者として**確かめる。

---

## 3. 接続の寿命はここで決めない

アイドルタイムアウトと heartbeat の関係・前段のリバースプロキシによる応答バッファリング・切れたときの再接続は、**インフラ側のファイル**が扱う: shirokuma-infra プラグインの `designing-aws` skill の `reference/patterns/long-lived-connections.md`。

- **指した先を読まずに実装しない。** heartbeat を置かない SSE は、無通信が続く構成で黙って切れる（アプリのログにも失敗として出ない）。

## 4. 中継の申告

本ファイルの関係は**別プロジェクトの実装検証の第三者報告を中継したもの**で、この配布物の作成側では追試していない。追試状況の値の意味は shirokuma-infra プラグインの `designing-aws` skill の `reference/patterns/static-asset-delivery.md` の「追試状況の書き方」節にある。

| 主張 | 出所 | この配布物の作成側での追試 |
|---|---|---|
| 購読をプロセスにつき 1 つへ寄せても購読者を増やせる（DB 接続の総数が増えない） | 第三者報告の中継 | **要確認（未追試）** |
| `id:` を付けるとブラウザが再接続時に `Last-Event-ID` を送り、取りこぼしが埋まる | 第三者報告の中継（SSE 仕様に基づく報告） | **要確認（未追試）** |
| 購読と catch-up の順序を逆にすると隙間から漏れる | 第三者報告の中継 | **要確認（未追試）** |
| 通知がタスク（コンテナ）を跨いで届き、sticky session が要らない | 第三者報告の中継 | **要確認（未追試）** |
| Node の API に依る購読機構は Edge ランタイムでは動かない（§1 のランタイム行） | 第三者報告の中継 | **要確認（未追試）** |

> **上表を根拠に「動く／動かない」を断定しない。** 使う版と構成で自分で確かめる。**表に行が無いことは「確認済み」の意味を持たない**（未調査と区別が付かない＝fail-silent）。
