# route 設計パターン

Next.js（App Router）の route 階層・レイアウト境界・ミドルウェアの設計判断のためのパターン比較テーブル。SKILL.md 本文「設計観点 1（route 階層）」の詳細展開。

## ルート構成

| パターン | 使用場面 | トレードオフ |
|---------|---------|------------|
| フラットルート（`app/page/page.tsx`） | シンプルなアプリ、少数ページ | 簡単だがスケールしない |
| ルートグループ（`app/(group)/page/`） | 共有レイアウト、認証境界 | ディレクトリ増だが明確な境界（URL に出さない整理） |
| パラレルルート（`@slot`） | ダッシュボードパネル、モーダル | 複雑だが独立したローディングが可能 |
| インターセプティングルート（`(.)path`） | 共有可能 URL 付きモーダルオーバーレイ | 強力だがデバッグ困難 |
| 動的ルート（`[id]`） | エンティティ詳細ページ | パラメータ検証が必須 |

### 判定: ルートグループ vs フラット

| 基準 | ルートグループ | フラット |
|------|-------------|--------|
| 共有レイアウトが必要 | 推奨 | レイアウト重複 |
| 認証境界 | 推奨 | ミドルウェアのみ |
| 関連ページ 5+ | 推奨 | 許容可 |
| 独立ページ 1-3 | オーバーヘッド | 推奨 |

## レイアウト境界

| パターン | 使用場面 | 例 |
|---------|---------|-----|
| ルートレイアウト | グローバルシェル（ナビ、フッター） | `app/layout.tsx` |
| ルートグループレイアウト | 認証ゲート付きセクション | `app/(dashboard)/layout.tsx` |
| ネストレイアウト | セクション固有の装飾 | `app/(dashboard)/settings/layout.tsx` |
| レイアウトなし（ページのみ） | 独立ページ（ログイン、エラー） | `app/login/page.tsx` |

## ミドルウェア

### ミドルウェアの責務

| 責務 | 適切か | 理由 |
|------|--------|------|
| 認証リダイレクト（未認証 → ログイン） | はい | ページレンダリング前に実行 |
| i18n ロケール検出 | はい | 全ルートで実行が必要 |
| セキュリティヘッダー | はい | グローバルな関心事 |
| フィーチャーフラグ（ヘッダーベース） | はい | 低オーバーヘッド |
| 重いデータ取得 | いいえ | 全ルートをブロック |
| ページ単位の認可 | いいえ | レイアウト/ページレベルのチェックを使用 |
| 複雑なビジネスロジック | いいえ | テスト・デバッグが困難 |

### ミドルウェア実行順序

```
リクエスト
  → 1. セキュリティヘッダー
  → 2. i18n ロケール検出
  → 3. 認証チェック（未認証ならリダイレクト）
  → 4. フィーチャーフラグ
  → ページレンダリング
```

### Matcher 設定

| パターン | 使用場面 |
|---------|---------|
| `matcher: ['/dashboard/:path*']` | 特定セクションを保護 |
| `matcher: ['/((?!api\|_next\|static).*)']` | 静的/API 以外を保護 |
| ミドルウェア本体内の条件分岐 | 複雑なパスベースロジック |

## アンチパターン

| パターン | 問題 | 代替案 |
|---------|------|--------|
| ページ固有ロジックにミドルウェア | ミドルウェアは全ルートで実行 | レイアウト/ページレベルのチェック |
| 深くネストされたルートグループ | レイアウト把握が困難 | 共有レイアウトでフラット化 |

## アノテーション方針（feature-map 連携）

- 各 `page.tsx` に `@screen <Name>` を付け、画面を識別子化する。
- コンポーネントに `@usedComponents` を付け、画面↔部品の依存を辿れるようにする。
- これにより `shirokuma-flow nextjs feature-map` で画面↔部品マップを可視化できる。route 階層の設計時にアノテーション粒度（どの単位を 1 画面とみなすか）も併せて決める。

## 認可を経路の一覧で一元管理する構成では route handler を選ぶ

認可を「経路（URL）の一覧」に集めて 1 か所で判定する構成（ミドルウェアや共通の判定が URL を見て許可する形）では、書き込みの口に server action ではなく route handler（`app/**/route.ts`）を選ぶ。

- **何を防ぐか**: server action は、それを呼ぶページの URL に対する POST として届き、どの action かは URL ではなくヘッダで決まる。経路の一覧は action を区別できないので、一覧の外に口ができる（ページの閲覧を許した相手が、そのページから呼べる action をすべて呼べる）。Next.js のドキュメントも、server action は UI を経ずに直接の POST で届くものとして扱い、action ごとに認証と認可を確かめるよう求めている。
- server action を使うなら、一覧での判定に頼らず action の中で認証・認可を確かめる（coding-nextjs スキルの `reference/patterns/server-action.md`）。
- 追試状況: `要確認（未追試）`。Next.js 16.4 同梱のドキュメント「data-security」の server action の節と照合した（直接の POST で届くことを手元で再現してはいない）。
